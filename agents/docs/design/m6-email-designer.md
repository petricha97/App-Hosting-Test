# M6-T4 — Email designer via shared block engine — UI/UX design spec

UI/UX Designer, 2026-07-16. Sources: `agents/docs/specs/m6-email-designer.md` (authoritative behavior — section numbers below map 1:1 to it), `agents/docs/design/m6-emails-admin.md` (M6-T2, the `EmailEditorDialog` this ticket extends — read as the template for format/depth and as the literal current-state baseline), `agents/docs/design/m4-website-blocks.md` + `src/features/event-pages/puck.tsx` + `src/features/event-pages/components/event-page-editor-workspace.tsx` (the Puck editor shell's established interaction/visual precedent this ticket reuses), `src/features/emails/components/{email-editor-dialog,email-preview-frame,merge-tag-menu,emails-workspace,lifecycle-emails-tab}.tsx` (current T2 implementation). **No prototype mockup exists for this screen** (spec's own note) — every layout decision below is derived from the spec's explicit constraints plus the established Puck/email-dialog vocabulary, not reconciled against `prototype/prototype/*.html`.

## 0. What's reused vs. added (orientation)

`EmailEditorDialog` (`src/features/emails/components/email-editor-dialog.tsx`) is **extended, not forked**. Its outer shell — `Dialog`, `DialogHeader` (name + System/Custom badge + group description), the inner `Compose | History` `Tabs`, the unsaved-changes `AlertDialog` guard, the test-send row, the footer — is **unchanged in kind**. What T4 adds, all inside the existing `Compose` tab:

1. A **mode toggle** ("Plain text" / "Block designer") bound to the definition's new `bodyMode` field.
2. A **Block-designer content region** that replaces the plain-text `Textarea` when the toggle is on "Block designer" — this region is new (`email-block-designer.tsx`) and is the bulk of this spec (§3).
3. A **definition-picker menu** replacing the disabled "Open Email Designer" button in `emails-workspace.tsx` (§1), which opens this same dialog pre-set to Block-designer mode.

The right-column `EmailPreviewFrame` (`email-preview-frame.tsx`) and the `MergeTagMenu` insertion mechanism (`merge-tag-menu.tsx`) are reused **as components**, unchanged in their own source — only *where* they're mounted and *what ref* they're pointed at changes per mode (§3.3, §6). `confirmation-preview-card.tsx` needs no changes (per spec §5, `renderEmailDefinitionPreview`'s output is opaque to it) — not respecified here.

## 1. "Open Email Designer" → definition-picker menu

`emails-workspace.tsx`'s header row currently renders a `disabled` `Button` + `Tooltip` ("Email designer arrives with M6-T4"). This becomes a live `DropdownMenu` (component: `email-definition-picker-menu.tsx`, `src/features/emails/components/`):

- **Trigger**: `Button variant="outline"` "Open Email Designer" with a `Blocks` icon (lucide) — no longer disabled, no tooltip wrapper needed. Sits in the same header-actions position, left of "+ Create email".
- **Content** (`DropdownMenuContent align="end" className="w-72"`): **grouped**, reusing the exact 3 group headers `lifecycle-emails-tab.tsx` already renders (`EMAIL_GROUP_LABELS`: "Pre-event", "Post-registration", "Debt chase & countdown") via `DropdownMenuLabel` (`text-xs uppercase tracking-wide text-muted-foreground`) + `DropdownMenuSeparator` between groups — **not** a flat list, and **not** searchable. Rationale: the group headers are already computed data (`definitionsByKind`, no new fetch per spec §4), the organizer already learned this exact 3-group taxonomy from the main lifecycle table on the same screen, and the realistic list size (8 system rows + a handful of customs) doesn't clear the bar for adding a search affordance (YAGNI — a search input can be added later if an org's custom-email count grows enough to justify it; not designed here).
- **Each `DropdownMenuItem`**: definition name (`text-sm font-medium text-foreground`) + a trailing `Badge variant="secondary" className="text-[10px]"` "Designed" **only** when that definition's `bodyMode === "blocks"` (lets an organizer see at a glance which emails already have a block design without opening each one) + a secondary line (`text-xs text-muted-foreground`) reusing `triggerDisplayLabel(...)` from `utils.ts` (same string the main table's `trigger-cell.tsx` shows), so the item reads consistently with the row an organizer already knows from the lifecycle table.
- **Selecting an item** opens `EmailEditorDialog` for that `kind`, with a new prop `forceInitialMode="blocks"` — **only this entry point forces the toggle to Block-designer mode**; ordinary row-click editing (the existing name-cell button in `email-group-table.tsx`) continues to open the dialog defaulting to whatever `bodyMode` is currently persisted on the definition (text for every pre-T4 definition), per spec §4's "opening the designer does not mutate anything" framing — the picker is a *shortcut into a specific mode*, not a *replacement entry point* for the dialog generally.
- **Empty state**: not applicable — per M6-T2 §1's zero-write-guarantee, a fresh event always has the full 8-definition virtual catalog, so this menu is never empty.

## 2. Mode toggle — placement, component, and dirty-tracking

**Placement**: directly below the Subject field, above the content region, full dialog width. Subject applies to both modes so it stays outside the toggle's scope; everything below the toggle is what changes shape.

**Component choice: a two-button segmented control (`Button` pair + explicit ARIA), not `Tabs`.** The dialog already uses Radix `Tabs` one level up for `Compose | History` — nesting a second `Tabs` instance directly inside `Compose` risks reading as *another top-level tab*, not a sub-mode of the content an organizer is already editing, and would visually compete with the outer tab strip. This app already has a proven precedent for exactly this shape of control: `event-page-editor-workspace.tsx`'s device-preview toggle (`PREVIEW_DEVICES`, three `Button variant="outline" size="sm"` with `aria-pressed` and an active-state border/background). `email-editor-mode-toggle.tsx` copies that pattern at 2 options instead of 3:

```
<div role="group" aria-label="Email content mode" className="inline-flex rounded-lg border border-border p-0.5">
  <Button size="sm" variant="ghost" aria-pressed={mode === "text"} className={active-state classes when selected} onClick={...}>Plain text</Button>
  <Button size="sm" variant="ghost" aria-pressed={mode === "blocks"} className={...} onClick={...}>Block designer</Button>
</div>
```

Active button: `bg-background text-foreground shadow-sm` (pill-inside-track look, standard segmented-control treatment); inactive: `text-muted-foreground hover:text-foreground`. A caption directly beneath, always visible in both modes (`text-xs text-muted-foreground`): *"Switching modes doesn't delete your work — only the mode you save in becomes the live email."* This directly operationalizes the Shared-decisions non-destructive guarantee so switching never *feels* risky, satisfying spec §4's "instantaneous and non-destructive... confirm-nothing operation" framing with an explicit statement rather than leaving it implied.

**Dirty-tracking (interaction detail, load-bearing for spec §4 AC-3):** the toggle must be wired into the *same* RHF form instance as every other field, as a `bodyMode` field (`form.setValue("bodyMode", next, { shouldDirty: true })`), not a separate `useState`. The dialog's existing `attemptClose()` already keys off `form.formState.isDirty` read synchronously during render (see current `email-editor-dialog.tsx` comment on why `isDirty` must be read at render time, not just in a callback) — routing the toggle through RHF means that comment's existing mechanism covers mode-only switches for free, with no new dirty-tracking path to get wrong. The same applies to the Puck canvas's `onChange` (§3.3): it must call `form.setValue("bodyBlocks", next, { shouldDirty: true })`, mirroring this, rather than a parallel `isDirty` boolean the way `event-page-editor-workspace.tsx`'s non-dialog Puck page does — that page has no RHF form to unify with; this dialog does, and using two dirty sources of truth in the same dialog is a real bug class (one could go stale while the other doesn't), so **one dirty source (`form.formState.isDirty`), full stop.**

## 3. Block-designer mode layout — resolving the canvas / palette / preview tension

*As an event organizer switching to Block designer, I want enough room to actually use a drag-and-drop builder, without losing sight of what the real email will look like.*

### 3.1 The dialog grows when this mode is active

`sm:max-w-4xl` (T2's existing divergence) is sized for a 2-column form/preview grid — a full Puck shell (palette + canvas + field-editor sidebar, the same 3-pane layout `event-page-editor-workspace.tsx`'s `<Puck>` renders for the web builder) does not fit in half of that width. **The dialog's max-width becomes conditional on the mode toggle's current value**: `sm:max-w-4xl` in Plain-text mode (unchanged), `sm:max-w-6xl` (1152px) in Block-designer mode. On mobile, Radix `Dialog`'s own `max-w-[calc(100%-2rem)]` still wins regardless of mode (§5 responsive detail). This is a further, explicit divergence from T2's already-noted divergence — flagged here, not silently introduced, exactly as T2's own doc flagged its divergence from the app's `sm:max-w-lg` default.

### 3.2 Layout restructure: a full-width top strip is shared by both modes

To keep switching modes from feeling jarring (spec §4 AC-3's spirit, beyond just the guard's correctness), **the top of the Compose tab is now identical in both modes** — only the region below the mode toggle changes shape. Concretely, the metadata fields that T2 laid out in the left half of a 2-column grid (Name, Group, Trigger, Audience, the "This is a default lifecycle email..." banner, Active + its off-banner) move into a **full-width strip above the toggle**, in a `grid gap-4 sm:grid-cols-2 lg:grid-cols-4` (locked-row displays for system definitions occupy the same cells; the Active switch + its description spans the full row since a `Switch` + `FormDescription` doesn't compress well into a quarter column). Subject sits below that strip, full width, `max-w-xl` on the input itself so it doesn't stretch edge-to-edge at `lg`.

This is an intentional, scoped restructure of the shipped T2 layout, not scope creep — see the "Divergences" callout at the end of this doc.

Below Subject: the mode toggle (§2), then:

- **Plain-text mode**: reverts to a 2-column grid (`grid gap-6 md:grid-cols-[minmax(0,1fr)_minmax(0,1fr)]`) — left = the existing Body `Textarea` + `MergeTagMenu`, right = `EmailPreviewFrame` at its current `h-72`. **Pixel-identical to what T2 shipped**, just re-anchored below the now-shared top strip instead of interleaved with it.
- **Block-designer mode**: the grid collapses to a **single column**, full dialog width, rendering `EmailBlockDesigner` (§3.3–3.6) top to bottom: disclaimer banner → merge-tag toolbar → Puck shell → authoritative preview.

### 3.3 The disclaimer banner (required) — and how it also answers "why isn't X here"

Component: `email-canvas-disclaimer.tsx`, styled with the **same neutral, non-alarming treatment** already used twice elsewhere in this exact dialog family (`email-editor-dialog.tsx`'s "This email is off" banner, `event-page-editor-workspace.tsx`'s "inherits the default page" banner): `rounded-lg border border-border bg-muted/50 px-3 py-2 text-sm`, `Info` icon (`h-4 w-4 text-muted-foreground shrink-0`) — **deliberately not amber/warning-colored**, since this is informative, always-true context, not a problem to fix (the amber treatment stays reserved for the unknown-merge-tag case in `EmailPreviewFrame`, so organizers don't learn to associate "amber = ignore it, nothing's actually wrong here" from a banner that's on every single visit).

- **Persistent single line** (always visible, non-dismissable per spec): *"Canvas preview is approximate — email clients render differently."* + inline `Button variant="link" size="sm" className="h-auto p-0 text-xs"` **"What's different? ▾"** (`aria-expanded`, toggles a `text-xs text-muted-foreground` bullet list beneath):
  - "No side-by-side layouts — every block stacks in a single column in the real email."
  - "Hero's button labels aren't clickable in email and won't appear — see the note on that field below."
  - "Call to Action isn't available here — it has no real destination. Use Registration Embed instead."
  - "Countdown timer shows a fixed date, not ticking digits."

  **Why a disclosure instead of one long paragraph**: the canvas literally reuses the web block's own React `render` functions (Shared decisions — "Puck's own canvas rendering can reuse the web render functions... it is not a faithful preview"), so the canvas *will* visibly show the two-column Hero grid, the CTA button spans, and a 3-column Highlights grid — exactly the things that disappear in the authoritative preview below. Stating that discrepancy once, persistently, and *fully*, in one required-but-collapsed disclosure is more honest and complete than a single truncated sentence, without demanding an organizer read four bullet points before every edit. This single disclosure also answers **CallToAction's exclusion** — see §4's CallToAction row for why no separate palette affordance is added.

### 3.4 Merge-tag toolbar (scoped to the focused block field)

A slim row directly below the banner: left, a caption (`text-xs text-muted-foreground`) *"Click into any text field below, then insert a tag."*; right, the **same** `MergeTagMenu` component T2 already ships, generalized to accept `RefObject<HTMLInputElement | HTMLTextAreaElement | null>` instead of only `HTMLTextAreaElement`. Its ref is populated by a shared `mergeTagFocusRef` (a plain `useRef`, created once at `EmailBlockDesigner`'s level and threaded into `createEmailPuckConfig({ ..., mergeTagFocusRef })`) that every text-bearing custom field's `onFocus` writes itself into — mirroring the existing `textareaRef` pattern, just shared across many field instances instead of one. Before any field has been focused in the session, the `MergeTagMenu` trigger button is `disabled` with a `Tooltip` — *"Click into a text field first"* — the same disabled-with-tooltip convention already used app-wide (M5 precedent, restated in T2 for the off-definition test-send button).

### 3.5 The Puck shell

`email-block-designer.tsx` wraps `<Puck config={emailPuckConfig} data={bodyBlocksAsData} ... />` in a fixed-height, internally-scrolling container: `<div className="h-[36rem] overflow-hidden rounded-lg border border-border">`. Puck's own header actions are overridden to empty (`renderHeaderActions={() => <div />}`, the exact override `event-page-editor-workspace.tsx` already uses) since Save/Cancel live in the dialog's own footer, not a second Publish-style button inside Puck's chrome. **No `viewports`/device-preview toggle is passed** in email mode — a deliberate omission (see "Judgment calls" below): the web builder's device toggle is meaningful because the *web* block set is genuinely responsive; the email block set is single-column at every width by the blanket §1 decision, so a device toggle here would falsely imply the email itself adapts by client width, when in reality its layout is fixed by the table markup regardless. The dialog's outer `max-h-[88vh] overflow-y-auto` still governs the whole Compose tab, so the fixed-height Puck shell doesn't push Save/Cancel out of reach — the shell scrolls its own panels internally (Puck's default per-pane behavior), the dialog scrolls around it.

`createEmailPuckConfig(...)` (client-side, canvas-only; see file-location note below) is built by taking `createEventPagePuckConfig(...)`'s returned `Config` and, for exactly the 8 allowed types, reusing each one's `render` closure unmodified (canvas parity, per Shared decisions) while **overriding only `fields`/`defaultProps`** to add the email-specific notes (§4) — this avoids hand-duplicating the web blocks' JSX for the canvas while keeping the email-only field annotations additive and easy to diff against the web registry. `categories` collapses to a single group (`{ email: { title: "Email blocks", components: [...8 types...] } }` — no "Content"/"Registration" split, since 8 items in one list is short enough that the split adds a click without adding scannability).

### 3.6 The authoritative preview, directly below

`EmailPreviewFrame`, unchanged component, mounted full-width below the Puck shell (not beside it) with a small heading above it (`text-sm font-semibold text-foreground`) **"Email preview (this is what sends)"** — a plain, unambiguous label rather than relying on layout position alone to communicate "this one is real," directly satisfying spec §4 AC-4 ("visible and worded plainly... not merely implied by layout"). Height bumped to `h-96` via the component's existing `className` prop (component itself needs zero changes, per spec's explicit note) — the extra height is affordable now that the preview isn't sharing a row with a form column. It receives `renderEmailDefinitionPreview`'s `bodyMode: "blocks"` output exactly as it already receives `"text"` output today — same debounced-refetch mechanism, same loading/error treatment.

## 4. Per-block field-panel divergences (all 8 blocks + the excluded one)

Shared technique for attaching a static note to a block's field panel without an associated editable prop: a synthetic `type: "custom"` field (same technique `createImageField` already uses for the image-URL control) bound to a throwaway prop key, rendering only static explanatory text — placed as the **last** entry in that block's `fields` object so it reads as a footnote after the real controls, not an interruption before them.

| Block | Field-panel divergence from the web block's panel | Copy |
|---|---|---|
| **Hero** | `primaryCtaLabel`/`secondaryCtaLabel` fields **stay visible and editable** (not hidden) — a value typed here must round-trip in storage even though it never renders (spec §1 AC-3), and hiding the control entirely would make that round-trip untestable-by-the-organizer and mysterious ("why did my label survive a save if there's no field for it"). A note attaches after `secondaryCtaLabel`: | *"Not shown in the email — see the canvas note above for why."* |
| **Highlights** | None — stacking 3 items vertically instead of in a 3-column grid doesn't change what the organizer types, only how it's laid out; no note needed. | — |
| **Story** | `imageSide` (Left/Right radio) gets a one-line clarification, since its *meaning* changes from "which side of a 2-column layout" to "which end of a single stacked column": | *"In email, this puts the image first or text first (single column) instead of side-by-side."* |
| **Schedule** | None — already a single static text block on the web, no behavior changes. | — |
| **Faq** | None — already fully expanded (no accordion) on the web, no behavior changes. | — |
| **RegistrationEmbed** | A note after `buttonLabel` explains the open/closed/zero-paths branching (spec §1 AC-5) up front, so an organizer doesn't have to guess why the preview sometimes shows a link and sometimes a static notice: | *"Renders as a real button when at least one registration path is active; otherwise shows a closed notice — never a broken form."* |
| **TicketPricingTable** | The freshness-divergence note — **spec's own verbatim copy** (§1 AC-9), used exactly as written, as the synthetic final field: | *"Prices shown reflect the moment this email is generated — not live at open time, unlike the website block of the same name."* |
| **CountdownTimer** | A static-snapshot note as the synthetic final field, explicitly ruling out any "ticking preview" expectation (spec's UI-scope requirement, no verbatim copy given): | *"Emails can't run a ticking countdown. This block renders a static date/time snapshot only — it won't update after the email is sent."* |
| **CallToAction** | **Excluded from the palette entirely** — not rendered as a disabled/greyed palette entry. See judgment call below. | — |

**Judgment call — palette exclusion needs no dedicated affordance beyond the banner's disclosure (§3.3).** Considered and rejected: a disabled palette entry with a tooltip (the M5 disabled-with-tooltip convention). Rejected because Puck's palette panel isn't a list of `Button`s this app controls directly — building a fake, non-functional palette entry inside Puck's own component-list rendering (via `overrides.componentItem`, already used for the "New" badge in the web builder) to represent a block that **isn't in the `Config` at all** is a meaningfully bigger, more fragile lift than it looks (it would need a separate, parallel "phantom entries" list threaded through the override, decoupled from the real `components` keys) for a question that's already fully answered, proactively, in the always-visible-on-expand banner disclosure (§3.3's fourth bullet: *"Call to Action isn't available here... use Registration Embed instead"*). An organizer who's used the web builder and notices the gap has an immediate, undismissable answer one click away — that clears the bar without inventing a new UI pattern for a single excluded item.

## 5. States

- **Empty canvas** (`bodyMode: "blocks"`, `bodyBlocks: []` — spec §8-1): Puck's own canvas already shows its native empty drop-zone. Above it, alongside the disclaimer banner, a **second**, amber-toned inline banner appears (this one *is* a real, actionable warning, using the same amber treatment as `EmailPreviewFrame`'s unknown-tag rows, so the two banner colors stay meaningfully distinct — neutral info vs. amber warning): *"This email has no content blocks yet — drag a block from the panel to add content."* **Design decision on gating**: this warns but does **not** disable Save (there is no existing precedent in this dialog for disabling Save on a content-quality warning — even an empty Subject only renders "(empty)" in the preview, never blocks Save) — an organizer must be able to save a work-in-progress empty block design. It **does** disable the Test-send button with a `Tooltip` — *"Add at least one content block before sending a test"* — extending the exact disabled-button-plus-tooltip mechanism `EmailEditorTestSendButton` already uses for `!enabled` definitions, just with a second, independent reason to disable.
- **Loading** (dialog just opened in Block-designer mode, canvas Config being constructed / assets not yet loaded — mirrors the web builder's asset-loading state): the Puck shell region shows a `Skeleton` matching its `h-[36rem]` box (three stacked `Skeleton` bars approximating palette/canvas/field-column proportions) in place of `<Puck>` until the config's dependencies (image asset list, if reused) resolve; the disclaimer banner and merge-tag toolbar render immediately (they don't depend on any fetch).
- **Error** (canvas Config or preview fetch fails): the authoritative preview inherits `EmailPreviewFrame`'s existing inline error treatment (`text-xs text-destructive` under the iframe, last-good content stays) — no new error UI needed there. If the Puck shell itself fails to mount (a genuine JS error, not a data-fetch error), it is out of scope to newly handle here — Puck mounting failures are not a state this ticket's spec calls out, and inventing bespoke recovery UI for a library-mount failure is speculative; a plain error boundary fallback consistent with the app's existing dashboard error boundary is sufficient and is not respecified per-component here.
- **Permission-denied**: identical posture to every other control in this dialog (M6-T2 §7) — a read-only member can open the dialog and see the canvas/preview render from server data, but Save/Test-send fail server-side with the shared `toast.error("You don't have permission to do that.")` copy; no new client-side role-gating is introduced (same deliberate parity choice T2 already made).
- **Narrow-viewport notice** (Block-designer mode, `<768px`): see §6 — a small, honest, non-blocking notice rather than pretending the builder is equally usable at 320px.

## 6. Responsive behavior (320 / 768 / 1024 / 1440)

- **320–767px**: Dialog uses Radix `Dialog`'s own `max-w-[calc(100%-2rem)]` regardless of mode (the conditional `sm:max-w-6xl` never applies below `sm`, matching T2's existing mobile behavior). Metadata strip collapses to 1 column (`sm:grid-cols-2` doesn't activate). Mode toggle stays a compact 2-button row, full width. In Block-designer mode, a small inline notice (`text-xs text-muted-foreground`, sits between the toggle and the disclaimer banner) reads: *"Block designer works best on a larger screen — you can keep editing here, but the canvas may need horizontal scrolling."* This is an honest disclosure, not a block: the Puck shell still renders (with its own internal `overflow-x-auto`, matching this app's established "scroll inside the box, never blow out the page" convention for tables), and the mode toggle stays reachable so an organizer can drop back to Plain-text mode for a quick mobile edit at any time. This mirrors the spec's own posture toward Puck's drag-and-drop limitations — disclosed, not silently patched over.
- **768–1023px (`md`–`lg`)**: Plain-text mode's 2-column grid activates at `md` exactly as it does today. Block-designer mode's dialog width is still capped by the viewport (`max-w-[calc(100%-2rem)]` effectively still governs up to just under `lg`, since `sm:max-w-6xl` = 1152px exceeds the viewport here) — the Puck shell's 3 internal panes remain tight; no special-cased layout is added beyond the shell's own internal scrolling, consistent with how the web page builder itself has no bespoke sub-1024 Puck layout either.
- **1024–1439px (`lg`–`xl`)**: Block-designer mode's dialog reaches its authored `sm:max-w-6xl`; the Puck shell has comfortable room for palette + canvas + field sidebar without internal horizontal scrolling. Metadata strip reaches its full `lg:grid-cols-4`.
- **1440px+**: no further change — the dialog's max-width still caps it (consistent with "no new max-width container" convention carried from every other dashboard screen); extra viewport width is idle backdrop.

## 7. Accessibility & interaction summary

- **Mode toggle**: `role="group"` + `aria-label="Email content mode"` on the wrapper, `aria-pressed` on each button reflecting selection — same convention as the existing device-preview toggle precedent, not a newly-invented pattern.
- **Definition-picker menu**: standard `DropdownMenu` roving-focus/Escape-to-close (free from Radix); each item's accessible name includes the definition name + trigger label (not just the bare name), matching the merge-tag menu's existing "give screen readers the same context sighted users get" convention.
- **Disclaimer disclosure**: the "What's different?" toggle is a real `<button>` with `aria-expanded`, not a `details`/`summary` pair (keeps styling consistent with the rest of the dialog's `Button variant="link"` usage) — content it reveals is regular flow content, not `aria-live` (it's user-triggered, not ambient).
- **Merge-tag toolbar**: identical `DropdownMenu` behavior to T2's existing menu; the only change is its target ref being dynamic (whichever field last had focus) rather than fixed — this is invisible to a screen-reader user beyond the trigger's own disabled/enabled state and tooltip, already covered by the disabled-with-tooltip convention.
- **Puck canvas/palette/drag-and-drop**: **unchanged from upstream Puck behavior, mouse-first by library design** — this ticket does not attempt to fix any pre-existing Puck keyboard-drag-drop gap, per spec's own Non-goals and §4 AC-5. What *is* this ticket's responsibility: once a block is selected (by whatever means, including a future keyboard-accessible path if Puck ships one), its field-editor sidebar inputs are ordinary native `Input`/`Textarea`/`radio` controls reachable via Tab in DOM order, exactly like every other Puck-driven field panel in this app already is.
- **Authoritative preview iframe**: `title="Email preview"` (existing, unchanged), not a live region — same rationale already documented for the T2 preview (debounced re-render is visually adjacent via a loading indicator, not chattily announced).
- **Contrast**: the disclaimer banner reuses the exact `bg-muted/50 border-border` treatment already contrast-verified elsewhere in this dialog (the "email is off" banner); the empty-canvas warning reuses the exact amber treatment already contrast-verified in `EmailPreviewFrame`'s unknown-tag rows — no new color introduced anywhere in this spec.
- **Both themes (dashboard chrome only)**: the mode toggle, disclaimer banner, merge-tag toolbar, Puck shell's border/skeleton, and the "Designed" badge all follow the app's existing light/dark tokens (`bg-muted`, `border-border`, `text-muted-foreground`, the existing amber/emerald pairing) — no new palette. The Puck **canvas's own rendered block content** stays light-only (it's reusing the web blocks' hard-coded `slate`/`orange`/`white` vocabulary, per `m4-website-blocks.md` §0's own "light-only by design" note) and the **authoritative preview iframe's `srcDoc`** stays light-only (carried forward from T2 §8-1, restated in spec §6/§8-4) — this is a decision on both surfaces, not a theming bug to flag in QA.

## Divergences from the M6-T2 shipped layout (explicit, so this reads as intentional continuity work, not scope creep)

1. **Metadata fields (Name/Group/Trigger/Audience/Active) move from the left half of the 2-column grid into a full-width strip above Subject**, shared by both modes — needed so the top of the dialog stays visually identical when switching modes (§3.2).
2. **Dialog max-width becomes mode-dependent** (`sm:max-w-4xl` text / `sm:max-w-6xl` blocks) — T2's own doc already flagged its `sm:max-w-4xl` as a divergence from the app's `sm:max-w-lg` default; this is a further, explicitly-flagged divergence on top of that one (§3.1).
3. **`EmailPreviewFrame`'s height varies by mode via its existing `className` prop** (`h-72` text / `h-96` blocks) — the component itself is unmodified, only the caller's sizing choice changes (§3.6).

## Judgment calls made (flagging for Research/FS awareness, none blocking)

- **Hero's CTA-label fields stay visible+editable with a footnote**, rather than being hidden — chosen because spec §1 AC-3 tests a real round-trip, which needs an editable control to be meaningful, and hiding the field would make an organizer's saved-but-invisible value feel like a bug rather than a documented limitation.
- **No device-viewport toggle on the email canvas** — the web builder's toggle is meaningful because web blocks are genuinely responsive; showing one on a canvas whose real output is single-column at every width (by §1's blanket decision) would misrepresent the email as more adaptive than it is.
- **`CallToAction`'s exclusion gets zero dedicated palette UI**, answered instead by the always-available banner disclosure — building a phantom disabled palette entry for one excluded block type is disproportionate lift for a question the banner already answers proactively, one click away, on every visit.
- **Empty canvas warns but does not block Save**, only blocks Test-send — consistent with this dialog's existing precedent (no other content-quality issue blocks Save today) while still preventing an organizer from firing a genuinely empty test email at a real inbox.

## Open questions back to Research

- **File location for `createEmailPuckConfig`** (raised as spec's own OQ-5, not newly introduced here): this design assumes it's callable from a `"use client"` component (the Puck canvas needs it in the browser) and built by reusing `createEventPagePuckConfig`'s already-exported factory rather than duplicating JSX — whichever file FS picks (co-located with `puck.tsx` vs. under `src/features/emails/`), the design here only requires that the *canvas* config be reachable client-side; the *server* HTML renderers must stay under the enforced `server-only` boundary regardless, per spec's own leaning. No design decision here depends on the answer.
- **Should the "Designed" badge in the definition-picker menu (§1) be tested as ready-to-ship, or deferred?** It's cheap (derived from data already loaded, no new fetch) but is an addition beyond what spec §4 explicitly asked for. Flagging in case Research/PM wants it cut for scope discipline on a stretch ticket — it isn't load-bearing for any acceptance criterion.
- **Narrow-viewport notice copy (§6)** is my own addition (spec doesn't mandate mobile-specific messaging for the block designer) — flagging in case QA's actual mobile Puck testing reveals the experience is materially worse than "may need horizontal scrolling" suggests, which would call for either fixing the copy's honesty level or reconsidering whether Block-designer mode should be reachable at all below `sm`.
