## 0. Screen shell — `iam-dashboard.tsx` (rebuilt) / route `/dashboard/iam`

`src/features/iam/components/iam-dashboard.tsx`, page shell in the standard workspace-page pattern (`getDashboardScope()`-fed Server Component page → Client Component browser, same split as `promotion-templates-browser.tsx`/`organization-responses-browser.tsx`):

- Header row (`flex flex-wrap items-start justify-between gap-3`): `h1` "Users & Access" + `p` "Workspace members and their roles. Roles map to what each person can edit." (verbatim `users.html` copy, lines 36–37). Trailing action: primary `Button` **"+ Invite member"** (`UserPlus` icon), rendered **only** when `canManageMembers` (§2's server-computed boolean, `scope.userDoc.permissions.includes("write:user")` — mirrors `reports/page.tsx:101`'s exact pattern) is `true`. Per D-collab with spec §2: for an Editor/Viewer caller the button is **omitted entirely**, not disabled-with-tooltip — the roster itself is view-tier for everyone, but "invite" is a distinct write action with no ambiguity to explain (unlike M6's "Email Designer arrives later" case, there's nothing forthcoming to hint at), so omission over a disabled-and-explained control is the right read per D1's "no speculative chrome" posture.
- Page body (`space-y-6`): **Members & invitations table** (§1) directly under the header, then the **role-description cards** grid (§6) below it — matching `users.html`'s vertical order (table, lines 41–51; cards, lines 53–57) exactly.
- Data: one `GET /api/dashboard/iam` call on mount (Client Component `useEffect`, matching `report-schedules-dialog.tsx`'s `fetchSchedules` idiom exactly — `loading`/`error`/data state trio), returning `{ members, invitations }`. Actions (invite, revoke, role-change, remove) locally patch this same state on success, matching `report-schedules-dialog.tsx`'s `setSchedules((current) => ...)` in-place-update idiom — no full re-fetch after every mutation.

**States:** loading = `EntityScreenSkeleton` (`entity-table-states.tsx`, reused verbatim — header skeleton + table-shell skeleton with 5 placeholder rows; the role-cards grid gets its own `Skeleton h-28` × 3 appended below, since `EntityScreenSkeleton` doesn't natively cover a second section — see §5); error = `EntityTableError entityLabel="members and invitations"` replaces the table region only (header stays interactive, cards render — same "shell stays interactive" convention as M6 §0); permission = none needed beyond the button-omission above — the page itself never 403s for any signed-in org member (§2 AC-1), so there is no permission-denied *page* state, only the granular per-row/per-action omissions and 403-on-attempt toasts described below.

## 1. Members & invitations table

One combined table, adapting `users.html`'s 4-column structure (`Member | Email | Role | Status`) with a 5th **Actions** column added only when management controls are present:

**Component tree:**
- `members-table.tsx` — `Table`/`TableHeader`/`TableBody`/`TableRow`/`TableCell` (`src/components/ui/table.tsx`), wrapped `overflow-hidden rounded-2xl border border-border bg-card` + inner `overflow-x-auto`, `Table className="min-w-[40rem]"` (5-col with actions) / `min-w-[32rem]` (4-col read-only) — same horizontal-scroll-inside-its-own-box discipline as every M1–M7 table (M6 §1's `email-group-table.tsx` precedent).
- Columns: **Member** (`TableHead`, sr-hidden-visually? no — visible "Member"), **Email**, **Role**, **Status**, **Actions** (sr-only header text via `<span className="sr-only">Actions</span>`, right-aligned cell — same convention as M6 §1's Actions column, present only for `canManageMembers` callers).
- **Member cell**: `flex items-center gap-3` — `Avatar` (`h-8 w-8`) with `AvatarFallback` = first-letter initial (no `AvatarImage` source exists in `UserDoc` today, so every row is initials-only, consistent with there being no avatar-upload feature for org members) + `font-medium text-foreground` display name (falls back to the email's local-part, title-cased, for invitation rows that have no name yet — an invited person has no `UserDoc.name`).
- **Email cell**: `text-sm text-muted-foreground font-mono` (emails read better in a monospace-leaning tone; matches no strict prior precedent but is a reasonable, low-risk choice — plain `text-sm text-foreground` is an acceptable substitute if Full-Stack prefers strict precedent-only reuse; not a hard requirement).
- **Role cell** → `role-badge.tsx` (shared by table + dialogs): `Badge` variants mapped to the 4-tier model, adapting `users.html`'s violet-Owner / plain-others distinction into this app's existing badge system (no new CSS variables — reuse the emerald/amber/violet-equivalent tokens already established in M1–M6, see Spacing/typography notes below for the exact classes):
  - **Owner** — `bg-violet-100 text-violet-900 dark:bg-violet-950 dark:text-violet-200` "Owner" (violet, matching `users.html`'s `badge violet` exactly — this app has no prior violet badge use, so this is the one net-new color token this spec introduces, chosen because the prototype names it explicitly and Owner is deliberately the single most visually distinct role).
  - **Admin** — `Badge variant="secondary"` "Admin" (neutral, matching `users.html`'s plain `<span class="badge">Admin</span>` — no color implies "not visually distinguished from Editor/Viewer at a glance," which is the deliberate point: D5 says Admin's only real distinction is the hierarchy guardrail, not a permission tier, so a loud badge color would overstate a difference that doesn't exist at the permission layer. See §6 for how the nuance is instead surfaced via tooltip.)
  - **Editor** — `Badge variant="secondary"` "Editor".
  - **Viewer** — `Badge variant="secondary"` "Viewer".
  - *(Legacy `"member"` role value, D2: rendered as "Viewer" — the alias is invisible in the UI, never surfaced as a 5th label.)*
- **Status cell** → `status-badge.tsx`: **Active** — `bg-emerald-100 text-emerald-900 dark:bg-emerald-950 dark:text-emerald-200` with a leading dot (`<span aria-hidden className="mr-1 inline-block h-1.5 w-1.5 rounded-full bg-current" />`, replicating `users.html`'s `.badge.dot` convention, text-carries-meaning per accessibility notes below) "Active"; **Invited** — `bg-amber-100 text-amber-900 dark:bg-amber-950 dark:text-amber-200` + dot "Invited" (amber, matching `users.html` lines 47–48 exactly and the M6 email-status amber convention).
- **Actions cell** (rendered only when `canManageMembers`, i.e. caller is Owner or Admin — §2's `write:user` gate mirrored client-side as UX-only, D10/AC-2): `role-actions-menu.tsx` — `DropdownMenu` (ghost icon `Button size="icon" variant="ghost" aria-label="Actions for {name}"`, `MoreVertical` icon) containing:
  - `DropdownMenuItem` **"Change role"** → opens `role-change-dialog.tsx` (§3/§4).
  - `DropdownMenuItem variant="destructive"` **"Remove"** (member rows) or **"Revoke invitation"** (invitation rows) → `DeleteEntityDialog` (member removal, §3) or a lighter inline confirm (invitation revoke — see below).
  - **D10 hierarchy applied to the menu itself, not just the mutation endpoint** (client-side UX mirror of the server 403, since D10 says an Admin caller "cannot touch an Owner/Admin row at all"): for an **Admin-tier caller**, rows whose *current* role is Owner or Admin render **no DropdownMenu trigger at all** — a plain `<span className="text-xs text-muted-foreground">—</span>` (em dash) fills the Actions cell instead, matching the M6 §1 "system rows render nothing, not even a disabled icon" terminal-affordance precedent cited in that spec. This is a deliberate stronger read than "disabled with tooltip": an Admin fundamentally cannot act on these rows under any circumstance (not a permission the org could grant them), so a disabled-and-explained control would overstate that it's a settable thing — the em dash communicates "not applicable to you," full stop.
  - For rows the Admin caller **can** act on (Editor/Viewer targets), the menu behaves identically to an Owner's, except the role-change dialog's role `Select` never offers "Owner"/"Admin" as options for an Admin caller (§3).
- **Editor/Viewer callers** (`canManageMembers === false`): the whole Actions column is omitted from the table (not rendered with disabled controls) — table is genuinely 4-column for these callers, matching spec §2's "sees the roster read-only — no action buttons" instruction literally.
- **Row order**: Owners first, then Admins, then Editors, then Viewers (role-hierarchy order, matching `users.html`'s own row order — Petri/Owner, Carlos/Admin, Marketing/Editor, Finance/Viewer), active members before invitations within each role tier, then alphabetical by name/email as a stable tiebreak.

**Empty state:** unreachable for the members portion (every org has ≥1 Owner, spec §8) — never rendered. For **zero pending invitations** specifically (not the whole table — the table always has at least the caller's own row): render a single `TableRow` spanning all columns with `EntityEmptyState`-style copy **inline**, not the full boxed `EntityEmptyState` component (which assumes it owns the whole container) — a `TableCell colSpan={N} className="py-8 text-center text-sm text-muted-foreground"` reading **"No pending invitations"** appended after the last active-member row, only when `invitations.length === 0`. This keeps the "members always present, invitations sometimes empty" distinction legible without a jarring boxed empty-state interrupting a non-empty table (a full `EntityEmptyState` card is reserved for whole-table emptiness, which — per the spec — never happens here).

**Loading:** `EntityScreenSkeleton` (§0) covers this — 5 skeleton rows with 4 `Skeleton` cells each, already shaped correctly for this table.

**Error:** `EntityTableError entityLabel="members and invitations"`, `onRetry` re-fetches `GET /api/dashboard/iam`.

## 2. Invite dialog

`invite-member-dialog.tsx`, `Dialog sm:max-w-md` (default width — simple 2-field form, no divergence needed, matching `sender-settings-dialog.tsx`'s "no divergence needed" sizing call). Opened from the header's "+ Invite member" button (§0). Two internal views mirroring `report-schedules-dialog.tsx`'s `view: "list" | "form"` state-machine idiom: `"form" | "sent"`.

**`"form"` view:**
- `DialogHeader`: "Invite a teammate" / "They'll get a link to join this workspace at the role you choose."
- Fields (`space-y-4`, RHF + Zod, same `Form`/`FormField`/`FormItem`/`FormLabel`/`FormControl`/`FormMessage` composition as every entity dialog in this app):
  1. **Email** — `Input type="email"`, `FormLabel` "Email address", placeholder "teammate@company.com".
  2. **Role** — `Select` (`FormLabel` "Role"), options **Admin / Editor / Viewer** — never Owner, per D10, so "Owner" is not present in the option list at all (not shown-disabled — an invite literally cannot mint an Owner, there is nothing to explain). Default selection: **Viewer** (lowest-privilege default, matching D9's "self-serve joins default to Viewer" spirit applied here too — an inviter must deliberately upgrade, not deliberately downgrade).
     - **D10 Admin-option gating:** when the signed-in caller is an **Admin** (not Owner), the "Admin" `SelectItem` renders `disabled` with a trailing `Info` icon; the whole item is wrapped so its `Tooltip` ("Only an Owner can invite someone as Admin") is reachable via the same `<span tabIndex={0}>`-wrapper convention M5/M6 already use for disabled-with-tooltip controls — concretely, since a disabled `SelectItem` doesn't natively support hover/focus tooltips well inside a Radix `Select` popup, the simpler, tested-pattern choice is: **hide** the "Admin" option from an Admin caller's `Select` entirely and instead render a `FormDescription` line under the Role field, always visible for Admin callers only: "Only an Owner can invite someone as Admin." This trades a live inline tooltip for a static, always-legible explanation — more robust inside a `Select` popover (which closes on any interaction, making hover-tooltip timing awkward) and equally informative. For an **Owner** caller, all three options (Admin/Editor/Viewer) render normally with no extra copy.
- `DialogFooter`: Cancel + primary `Button` "Send invite" (`Loader2` while pending).
- **Validation/error handling:** "already an active member" (§3 AC-2) and other typed rejections render as `FormMessage` under the Email field (inline, not a toast — matches the M6 §6 "validation is expected/recoverable input" convention), e.g. "This person is already a member of this workspace."

**`"sent"` view** (D8 — no real email, copy-the-link UX):
- `DialogHeader`: "Invite sent" / "Share this link with {email} — it expires in 14 days."
- Body: a read-only `Input readOnly value={acceptUrl} className="font-mono text-sm"` + adjacent icon `Button variant="outline" size="icon" aria-label="Copy invite link"` (`Copy`/`Check` icon swap on success, 2s revert) — **exact pattern reuse of `add-team-member-dialog.tsx`'s `copyCode()`** (`navigator.clipboard.writeText`, `setCopied(true)`, `window.setTimeout(() => setCopied(false), 2000)`, silently-caught denial since the value stays visible for manual copying regardless). On copy success, also fire `toast.success("Invite link copied")` (a supplementary confirmation the check-in precedent didn't need since its icon-swap was sufficient in a smaller context — here the value is copied to be pasted somewhere else entirely, e.g. Slack/email, so an explicit toast reduces "did that work?" uncertainty).
- Below: a `Badge` showing the assigned role (reusing `role-badge.tsx`, §1) + `text-sm text-muted-foreground` line "Role: {role}".
- `DialogFooter`: single `Button` "Done" (closes dialog, triggers the table refresh/local-patch adding the new invitation row).
- **Re-invite (upsert) case:** if the submitted email already has a pending invitation (§3 AC-1, spec's upsert semantics), the `"sent"` view's header copy becomes "Invite updated" / "The role and link were refreshed for {email}." — same view, different copy, sourced from whether the API response indicates a create vs. an update (a `wasExisting` boolean the route can return) — no separate UI path needed.

## 3. Role-change confirmation

`role-change-dialog.tsx`. Two visual weights depending on what's being changed, both opened from the row's "Change role" menu item (§1):

- **Standard change** (target's current role AND new role are both Editor/Viewer, or Editor↔Viewer either direction — i.e. nothing Owner/Admin-tier is involved on either side): a lightweight `Dialog sm:max-w-sm` — `DialogHeader` "Change {name}'s role" / "{name} is currently {currentRole}.", body = a single `Select` (`FormLabel` "New role") pre-populated to the current role, options filtered by the caller's own D10 ceiling (an Admin caller seeing an Editor/Viewer row only ever sees Editor/Viewer as selectable — Owner/Admin options are absent, not disabled, same reasoning as §2's invite-role gating). `DialogFooter`: Cancel + primary `Button` "Save".
- **Owner-tier change** (new role is Owner or Admin, OR current role is Owner or Admin being changed to anything — i.e. **any** action that promotes into, demotes out of, or otherwise touches the Owner/Admin tier): escalates to an `AlertDialog` (not a plain `Dialog`) — a genuine confirm step, per the spec's own framing ("should feel deliberate, not a stray dropdown click"). Flow: the role `Select` (same as above) sits inside a first-step `Dialog`; selecting a new value that crosses into Owner/Admin territory does **not** immediately submit — instead a "Continue" button (replacing "Save" for this case) advances to a second, distinct `AlertDialog` confirm:
  - `AlertDialogTitle`: role-specific, e.g. **"Make {name} an Owner?"** / **"Remove Owner access from {name}?"** / **"Make {name} an Admin?"**.
  - `AlertDialogDescription`, role-specific:
    - Promoting to Owner: "{name} will have full control of this workspace, including managing other Owners and Admins."
    - Demoting an Owner (to Admin/Editor/Viewer): "{name} will lose Owner-level control, including the ability to manage other Owners and Admins." (If this action would leave zero Owners, the dialog never reaches this state — §4 intercepts before the confirm step, see below.)
    - Promoting to Admin: "{name} will be able to manage Editors and Viewers, and will gain full workspace access — but won't be able to manage Owners or other Admins."
    - Demoting an Admin (to Editor/Viewer): "{name} will lose Admin-level access and the ability to manage other members."
  - `AlertDialogFooter`: `AlertDialogCancel` "Cancel" + a **role-colored** confirm button (not the generic `variant="destructive"` `DeleteEntityDialog` uses, since promotions aren't destructive) — promotions use the default primary `Button` styling with the target role name, e.g. "Make Owner" / "Make Admin"; demotions use `variant="outline"` with a `text-amber-700 dark:text-amber-400` label tone (cautionary, not destructive-red, since demoting isn't data loss) reading "Remove Owner access" / "Remove Admin access".
- **Self-targeting note** (spec §5 AC-4, an Owner demoting/removing themselves): identical dialog, plus one extra line in the `AlertDialogDescription`: "You are changing your own role. This won't affect your current session until your next action (§ D11)." — surfaces D11's "next request, not next login" behavior honestly rather than implying an instant kick-out.
- On confirm: `PATCH /api/dashboard/iam/members/{email}`; success closes both dialog layers, patches the row in place, `toast.success("{name}'s role updated to {role}")`; failure surfaces per §4 below (does **not** just toast-and-silently-fail — the dialog stays open with an inline error when the failure is the last-Owner guardrail).

## 4. Last-Owner-guardrail error state (spec §5 AC-3)

This is a **typed, specific rejection**, not a generic toast, per the spec's explicit ask. Two trigger surfaces need it: role-change (§3) and removal (member row's "Remove" action). Both reuse one shared presentation:

- **In the role-change `AlertDialog` (§3):** if `PATCH` returns the typed "last Owner" error, the dialog does **not** close — instead the `AlertDialogFooter`'s confirm button is replaced by an inline error block above the footer (`rounded-lg border border-destructive/30 bg-destructive/5 px-3 py-2 text-sm text-destructive`, `role="alert"`) with an `AlertTriangle` icon + the exact copy: **"This organization must have at least one Owner. Promote another member to Owner first, then try this change again."** The Cancel button remains available; the confirm button becomes disabled (there is nothing more this dialog can do — the fix requires a *different* action first, so re-attempting the same submit is pointless: disabling it, rather than leaving it clickable to fail again, is the honest affordance).
- **In `DeleteEntityDialog` for member removal:** this is exactly what `DeleteEntityDialog`'s existing `blockedMessage` prop already models (§ calibration file, `delete-entity-dialog.tsx` lines 27–29, 49, 53–54) — a `409`-shaped "removal is blocked" case that replaces the description and offers only "Close," no destructive action. Reuse verbatim: `blockedMessage="This organization must have at least one Owner. Promote another member to Owner before removing this one."` — the dialog opens normally (title "Remove {name}?"), and if the server rejects, `blockedMessage` is set from the typed error and the dialog re-renders in its blocked shape (Close-only), matching the exact mechanism M3/M7 already use for "can't delete, N things reference this" cases. This is a strict, low-risk reuse: **no new component needed** for the removal path.
- **Copy consistency:** both surfaces use the same core sentence ("This organization must have at least one Owner...") with a surface-appropriate second clause (promote-first for both, phrased for "try this change again" vs. "before removing this one"). Never a raw Firestore/500-shaped error string (spec §8 "Never" list).
- **Self-demotion special case (AC-3, "an Owner cannot demote themselves out of being the last Owner either"):** identical error presentation — the UI does not pre-detect "you are the last Owner" client-side (that would require a client-side Owner-count query this spec doesn't add) and instead always attempts the action and surfaces the server's typed rejection uniformly. This is consistent with D11's "server-side re-check is the real boundary" posture threaded through this whole spec — no client-side guess-ahead disabling.

## 6. Role-description cards

Adapting `users.html`'s 3-card grid (lines 53–57: Owner/Editor/Viewer, no Admin card) to the 4-role model per D5's guidance that **Admin is permission-identical to Owner** and the mock's own silence on Admin is itself informative:

**Decision: Owner and Admin share one card, with a footnote — not 4 separate cards, not a merged "Owner/Admin" card without explanation.** Reasoning: D5 is explicit that inventing a distinct "what Admin can't do" card would overstate a difference that's invisible everywhere except one guardrail on this exact screen; but silently reusing the Owner card for Admin with zero acknowledgment would look like an oversight (a QA/reviewer would reasonably ask "why does the Admin badge appear nowhere in the cards?"). A single card with a one-line footnote threads this: explains the real nuance exactly once, at exactly the right (and only) place it's true, without repeating "identical to Owner except member-management hierarchy" as a full paragraph on every Admin-tagged row in the table.

Grid: `grid gap-4 sm:grid-cols-3` (three cards — Owner/Admin combined as one, Editor, Viewer — same 3-column visual weight as the prototype's `grid c3`, so the layout doesn't look unbalanced despite modeling 4 roles):

- **Card 1 — "Owner & Admin"** (`Card`, `CardHeader` `CardTitle` "Owner & Admin", `CardContent` `text-sm text-muted-foreground`): "Full control, including members and workspace settings." (adapted from `users.html`'s Owner copy, "billing" dropped per D5's grounding that no real billing feature exists to reference). Footnote row beneath, visually distinct (`mt-3 flex items-start gap-1.5 text-xs text-muted-foreground border-t border-border pt-2`): a small `Info` icon + **"Only an Owner can manage other Owners and Admins, or invite someone as Admin."** — this is the entire surfacing of D5's nuance; no tooltip needed here since the card already has room for a static line (unlike the table's compact badge, where a tooltip is the better fit if ever added later — not required by this spec since the footnote card already covers the explanation once, app-wide).
- **Card 2 — "Editor"**: "Build events, forms, and emails. Can't manage members." (near-verbatim `users.html` copy, "emails" retained though not literally gated per D3's table — Editor does hold `write:promotion` but not a literal "emails" permission; this is descriptive marketing-style copy matching the prototype's own looseness, not a literal permission enumeration, consistent with how the prototype itself describes roles in plain language rather than as a permission list).
- **Card 3 — "Viewer"**: "Read-only: reports, attendees, and responses." (verbatim `users.html` copy — matches D6's view-tier work making this promise literally true for the first time).

**Card component:** `Card` / `CardHeader` / `CardTitle` / `CardContent` (`src/components/ui/card.tsx`), `rounded-2xl border border-border bg-card` (no custom shadow/gradient — this app's newer convention drops the old mock's `shadow-[0_24px_60px...]` treatment in favor of the flatter, bordered-card look used by `report-schedules-dialog.tsx`'s siblings). No icon per card (the prototype has none; the current mock's icon+colored-chip header treatment is part of what's being replaced, not carried forward per the "don't invent a new layout" instruction).

- Role cards grid: `grid gap-4 sm:grid-cols-3` (stacks to 1 column below `sm`/640px — three short cards don't need the `lg` breakpoint M6's 2-column debt-chase grid needed, since these cards are much shorter and read fine stacked at any width above the smallest phones).
- Dialog widths: invite dialog and role-change (standard) `sm:max-w-md`/`sm:max-w-sm` respectively (simple forms, default-scale dialogs — no divergence like M6's `sm:max-w-4xl` editor is needed, since nothing here needs a two-column compose/preview layout).
- Color tokens used (all pre-existing in this app's palette except the one Owner-violet addition, noted below):
  - Active/success: `emerald-100/900`, dark `emerald-950/200`.
  - Invited/pending/caution: `amber-100/900`, dark `amber-950/200`.
  - Owner (**new**): `violet-100/900`, dark `violet-950/200` — the one net-new color pairing this spec introduces, directly justified by `users.html`'s own explicit `badge violet` for Owner; Full-Stack should verify contrast (Tailwind's default violet-900-on-violet-100 and violet-200-on-violet-950 both clear WCAG AA per Tailwind's own documented lightness steps, consistent with how emerald/amber are already used elsewhere in this app at the same 100/900 and 950/200 pairing depth).
  - Destructive: `text-destructive` / `variant="destructive"` (removal, revoke).
  - Demotion-caution (non-destructive but consequential): `text-amber-700 dark:text-amber-400` (§3's demotion confirm button label tone — distinct from the Invited-status amber background use, applied only as text color here).

## Interaction details

- **Row hover/focus:** default `TableRow` hover (`hover:bg-muted/50`, already in the primitive) — no override.
- **DropdownMenu (Actions):** standard Radix roving-focus, `Escape` closes, opens on Enter/Space when the trigger `Button` is focused — no custom keyboard handling needed (free from Radix, same as M6 §1's Actions column).
- **Role `Select` inside dialogs:** standard Radix `Select` keyboard nav (arrow keys, type-ahead, `Escape`) — free from the primitive.
- **Copy-to-clipboard (invite "sent" view):** icon swap `Copy` → `Check` for 2s on success (verbatim `add-team-member-dialog.tsx` timing), plus `toast.success("Invite link copied")` as the supplementary confirmation (§2's stated addition over the check-in precedent).
- **Optimistic vs. server-confirmed updates:** unlike M3's Switch-toggle optimistic-then-rollback pattern, role changes and removals in this spec are **not** optimistic — they wait for the server response before patching table state, because (a) the last-Owner guardrail (§4) can reject the action outright and an optimistic flip would have to un-flip visibly, which is worse UX than a brief `Loader2` wait for an infrequent, deliberate action, and (b) these are exactly the "consequential, not a stray click" actions the spec asks to be treated deliberately — a `Loader2`-then-commit pattern reinforces that deliberateness better than instant-optimistic-flip does. Invite creation and revoke similarly wait for confirmation (both are already gated behind an explicit dialog submit, so there's no separate optimistic layer to add).
- **Toasts:** `sonner` via the app's existing `Toaster` mount — success copy is short and specific ("{name}'s role updated to {role}", "Invite sent", "Invitation revoked", "{name} removed from the workspace"); error copy follows the two-tier convention in §5's table (generic network toast vs. permission toast vs. §4's dialog-scoped guardrail block).
- **Dialog dismissal:** standard Radix `Dialog`/`AlertDialog` focus trap + return-focus (automatic). No unsaved-changes guard is needed anywhere in this spec (unlike M6's email editor) — every form here is short enough (1–2 fields) that an accidental close has low re-entry cost, consistent with `DeleteEntityDialog`'s own lack of a guard.

## Responsive behavior (320 / 768 / 1024 / 1440)

- **320–767px:** Header row wraps (h1 block, then "+ Invite member" button below, full-width or auto-width per the existing header-wrap convention — matches `emails-workspace.tsx`'s `flex flex-wrap` header). Table scrolls horizontally **inside its own rounded container** (`min-w-[40rem]`/`min-w-[32rem]` per §1) — no page-level horizontal scroll. Role-cards grid is single-column (`sm:grid-cols-3` only activates ≥640px). Invite dialog and role-change dialogs use the Dialog primitive's own `max-w-[calc(100%-2rem)]` mobile behavior — both are single-field-per-row forms already, so no internal layout collapse is needed beyond the primitive's default. The `AlertDialog` confirm step (§3) similarly uses its default mobile width.
- **768–1023px:** Role-cards grid activates at `sm` (640px), so it's already 3-column by this breakpoint. Table remains within its rounded container at comfortable width; no further change.
- **1024–1439px:** No structural change — table and cards already reached their target layout at smaller breakpoints. Dialogs remain their fixed max-widths (content doesn't need to grow with viewport).
- **1440px+:** No further layout change — table/card widths are capped by their container, consistent with every other dashboard screen (no new page-level max-width container introduced for this screen specifically).

## Accessibility notes

- **Table semantics:** real `<th>` headers via `TableHead`; role/status badges carry text, never color-only (Owner-violet, Active-emerald, Invited-amber all pair a color with a text label + the `.dot`-style leading indicator, matching `users.html`'s own dot convention and this app's established "never color-only" rule from M6 §1's Active/Off badges).
- **Role `Select` (dialogs):** native Radix `Select` — full keyboard support (arrow keys to move, type-ahead by first letter, `Enter`/`Space` to select, `Escape` to close) free from the primitive; `FormLabel` "Role"/"New role" is programmatically associated via `Form`/`FormField`'s existing `htmlFor`/`id` wiring (same as every RHF form in this app).
- **DropdownMenu (row actions):** trigger `Button` has `aria-label="Actions for {name}"` (name, not just "Actions" — disambiguates when a screen reader user tabs through multiple rows' menus in sequence); `DropdownMenuItem`s have their own accessible text ("Change role", "Remove"/"Revoke invitation") — no icon-only items without text.
- **Dialogs:** Radix `Dialog`/`AlertDialog` focus trap and return-focus are automatic; the two-step role-change flow (§3, `Dialog` → `AlertDialog` for Owner/Admin-tier changes) hands focus correctly between the two layers since each is a separate Radix root — verify in implementation that closing the first `Dialog` when advancing to the `AlertDialog` doesn't return focus to the row trigger prematurely (a brief intermediate state); the simplest correct implementation keeps the first `Dialog` mounted-but-hidden (or renders the `AlertDialog` nested within the same open `Dialog`'s content) rather than fully unmounting-and-remounting between steps, avoiding a focus round-trip — an implementation detail for Full-Stack, flagged here so it isn't accidentally two independently-triggered overlays fighting for focus.
- **Last-Owner guardrail block (§4):** `role="alert"` on the inline error block so assistive tech announces it immediately when the rejection arrives (matches the live, unexpected nature of a failed mutation — consistent with how `FormMessage` validation errors are already announced via `aria-live` wiring in the `Form` primitive, though this block is a plain `role="alert"` div rather than a `FormMessage` since it isn't tied to a specific field).
- **Copy-to-clipboard button (§2):** `aria-label="Copy invite link"` (icon-only button), icon swap on success is supplemented by the `toast.success` (§ interaction details) so success is communicated to screen-reader users too, not just visually via the icon change — `sonner` toasts are announced via its own `aria-live` region by default, so no extra work needed here.
- **Contrast, both themes:** all badge pairings (violet, emerald, amber) use the same `-100/-900` light / `-950/-200` dark structure already verified ≥4.5:1 elsewhere in this app for emerald/amber (M1–M6 precedent); the new violet pairing should be spot-checked by Full-Stack/QA against Tailwind's default violet scale at the same lightness steps, since it's the one net-new color this spec adds — flagged, not assumed safe by inheritance alone.
- **Focus order:** table → row action menus (in row order) → role-cards grid (in card order) — natural DOM order, no `tabIndex` overrides needed anywhere in this spec (no disabled-with-tooltip `tabIndex={0}` wrapper pattern is needed here either, since §2's Admin-invite-option handling was resolved via a static `FormDescription` line instead of a disabled+tooltip control — see §2's reasoning for why that pattern was deliberately avoided in this one spot).
