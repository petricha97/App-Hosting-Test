## 1. Lifecycle emails tab (grouped tables + preview card)

`lifecycle-emails-tab.tsx` composes, in order:

- `h2 className="text-sm font-semibold text-foreground mb-3"` **"Pre-event"** + `email-group-table.tsx` (columns: Email | Trigger | Audience | Active) rendering `invitation`, `abandoned-reminder`, then any custom `group:"pre-event"` rows (sortOrder → createdAt).
- `h2` **"Post-registration"** + another `email-group-table.tsx` (same 4 columns): `approval-pending`, `confirmation-paid`, `confirmation-payment-due`, then customs.
- `grid gap-6 lg:grid-cols-2` (spec's "c2" — **stacks below `lg` / ~1024px**, per §1 AC-7): left = `h2` **"Debt chase & countdown"** + `email-group-table.tsx` variant with **3 columns** (Email | Trigger | Active — no Audience, per prototype); right = `confirmation-preview-card.tsx` (§4).

**`email-group-table.tsx`** (shared, `columns: "4col" | "3col"` prop): same container as every M1–M5 table — `overflow-hidden rounded-2xl border border-border bg-card`, inner `overflow-x-auto`, `Table className="min-w-[40rem]"` (3-col) / `min-w-[48rem]` (4-col) so it scrolls horizontally inside its own wrap rather than blowing out the page at 320px. `TableHead` per column; rows:
- **Name cell**: `font-medium text-foreground`, clickable — the whole row (`TableRow onClick`, `role="button" tabIndex={0}` semantics via a wrapping button-like pattern: since `TableRow` isn't natively interactive, make the **name cell's text** a `button` (`text-left font-medium text-foreground hover:underline focus-visible:underline`) that opens `email-editor-dialog.tsx` (§3) pre-loaded for that `kind` — safer a11y than an onClick row (keeps Switch/Trash2 hit targets from double-firing the row handler, no need for stopPropagation gymnastics).
- **Trigger cell** → `trigger-cell.tsx` (below).
- **Audience cell** (4-col only): humanized label (`All invitees`, `Abandoned`, `Pending approval`, `Accepted (paid)`, `Accepted (invoice)`, `Accepted (all)` — mapping owned by `src/features/emails/utils.ts`, never inline strings per-row).
- **Active cell** → `email-active-switch.tsx`: `Switch` (`aria-label="Toggle {name} active"`) + adjacent `Badge` — checked: `bg-emerald-100 text-emerald-900 dark:bg-emerald-950 dark:text-emerald-200` "On"; unchecked: `variant="secondary"` "Off" (dot+text via the Switch's own visible state, not color-only — the badge text carries the meaning). Optimistic: flips immediately, PATCH `.../emails/definitions/{kind}`, `toast.error` + flip-back on failure (verbatim `toggleActive` pattern from `registration-paths-workspace.tsx`, including the deterministic-id materialize-on-first-write semantics — no client awareness needed, the route upserts).
- **Actions** (sr-only header, right-aligned cell, **custom rows only** — system rows render nothing, not even a disabled icon, matching the "accepted rows render no menu, an em-dash" terminal-affordance precedent from M3 responses): ghost `Trash2` icon `Button size="icon" aria-label="Delete {name}"` → `DeleteEntityDialog` ("Delete {name}?" / "This removes the custom email permanently. Its send history is kept." / destructive Delete) → `DELETE .../emails/definitions/{id}`, row removed, `toast.success("Email deleted")`.

**`trigger-cell.tsx`**: renders the canonical string (§1 spec table — `Manual`, `Auto · on submit`, `Auto · on accept`, `Auto · 24h after drop-off`, `Auto · +7 / +14 / +21d unpaid`, or the formatted scheduled datetime "Sep 8, 9:00 ET" / muted "Not scheduled" when a scheduled kind has no derivable date). Every **non-manual** row appends a small `Info` icon (`h-3.5 w-3.5 text-muted-foreground`) inside `<span tabIndex={0}>` + `Tooltip`: "Automation arrives with M6-T3; this email will not send automatically yet." (keyboard-reachable per the M5 disabled-tooltip convention). Manual rows render no icon (they are honest — a real per-definition test-send exists, §5).

**States:** loading — `emails-screen-skeleton.tsx` renders two 2-row table skeletons + a 3-row table skeleton + a card skeleton (`Skeleton` blocks matching each region's box, same idiom as `EntityScreenSkeleton`); zero-write guarantee (§1 AC-1) means there is **no** empty state distinct from "8 default rows" — a fresh event always shows the full virtual catalog, so no `EntityEmptyState` is needed here (divergence from the M1–M5 empty-state convention, called out explicitly since every other design doc in this repo specs one); error — `EntityTableError entityLabel="lifecycle emails"` replaces the whole tab body, retry re-fetches (server component refresh).

## 2. `EmailDefinition` editability surface (drives §3's field states, no standalone screen)

No dedicated UI — this section governs how §3's editor renders **locked vs editable** fields:
- **System definitions** (`isSystem:true`): Name, Group, Trigger *type*, Audience render as **read-only display rows**, not disabled form controls — a `LockKeyhole` icon (`h-3.5 w-3.5 text-muted-foreground`) + the value in plain text (`text-sm text-foreground`), so screen readers get real text content instead of a disabled `<select>` announcing nothing useful. Subject, Body, Enabled, and (for scheduled kinds) the trigger datetime remain live form controls.
- **Custom definitions** (`isSystem:false`): all fields are live controls; Trigger-type `Select` offers only **Manual | Scheduled** (OQ-1 default) — no lifecycle auto-trigger options rendered at all (not disabled-and-hidden-reason, simply absent, since T3 hasn't defined that contract yet).
- A one-line banner (`text-xs text-muted-foreground`) sits under the field group for system definitions: "This is a default lifecycle email — its name, group, trigger type and audience are fixed." For custom definitions creating with a lifecycle-only intent, no banner (nothing to explain).

## 3. Compose / edit surface

`email-editor-dialog.tsx`, `Dialog` sized `sm:max-w-4xl` (wide enough for the two-column compose/preview layout the merge-tag workflow needs — a deliberate divergence from the `sm:max-w-lg` default used by every other entity dialog in this app, noted so it doesn't read as an inconsistency), `max-h-[88vh]` with the content area `overflow-y-auto`. On mobile the Dialog primitive's own responsive width (`max-w-[calc(100%-2rem)]`) takes over — see Responsive below.

- **`DialogHeader`**: `DialogTitle` = the definition name (or "New email" on create) + inline `Badge variant="secondary"` "System" / "Custom" next to it. `DialogDescription` = the group label, e.g. "Post-registration".
- Inside the content, a small `Tabs` (`Compose` | `History`) — **not** URL-synced (dialog-scoped state): `Compose` is default and holds everything below; `History` renders `email-history-tab.tsx` = `send-log-table.tsx` (§5) pre-filtered `kind={definition.kind}`, no filter controls (the kind is fixed), reused wholesale — "one preview/table implementation, not two" mirrors the §4 AC-3 rule.
- **Compose tab layout**: `grid gap-6 md:grid-cols-[minmax(0,1fr)_minmax(0,1fr)]` (stacks to one column below `md`/768px — form first, preview second in DOM order so keyboard/reading order matches visual stacking):
  - **Left (form)**, RHF + Zod exactly like `path-dialog.tsx`/`ticket-type-dialog.tsx` (`Form`/`FormField`/`FormItem`/`FormLabel`/`FormControl`/`FormMessage`), `space-y-4`:
    1. Name (`Input`, custom only — locked display per §2 otherwise).
    2. Group (`Select`, custom only).
    3. Trigger — custom: `Select` Manual/Scheduled, Scheduled reveals a datetime picker (native `<input type="datetime-local">` styled as `Input`, labelled "Send at (event time zone)" with the tz abbreviation shown as `FormDescription`); system scheduled kinds show **only** the datetime picker (type is locked); system non-scheduled kinds show the locked trigger-type display row from §2.
    4. Audience — `Select` (custom only; system shows the locked row) with `FormDescription`: "Used for display only — audience targeting arrives with M6-T3."
    5. Enabled — `Switch` + `Label` "Active", `FormDescription` "Registrants receive this once automation is live (M6-T3)." row.
    6. Subject — `Input`, ≤255, live char count only if it starts exceeding (`text-xs text-muted-foreground` "230/255" style, matches Input conventions elsewhere — none currently show counters, so introduce only if space allows; otherwise server 400 + inline `FormMessage` on submit is sufficient and is the safer default — **decision: no live counter, rely on FormMessage**, avoids inventing an uninstalled pattern).
    7. Body — `Textarea` (`rows={10}`, `font-mono text-sm` for tag scannability) preceded by a small toolbar row: `merge-tag-menu.tsx` — `DropdownMenu` trigger `Button variant="outline" size="sm"` "Insert merge tag" (`Plus`/`Braces` icon) → `DropdownMenuContent` listing all 14 `EMAIL_MERGE_TAGS` as `DropdownMenuItem`s, each showing the tag `font-mono text-xs` + a human label + source hint (`text-xs text-muted-foreground`, e.g. "First name — attendee or submission"); `qr_code`'s item carries the extra line "HTML body only — blank in plain text." Selecting an item inserts `{tag}` at the tracked cursor position (`textareaRef.selectionStart`) and refocuses the textarea with the cursor placed after the inserted tag.
  - **Right (preview)**: `email-preview-frame.tsx` (shared with §4) — subject line (`text-xs text-muted-foreground` "Subject: {rendered subject}"), then the sandboxed `<iframe sandbox="" srcDoc={renderedBodyHtml} className="h-72 w-full rounded-lg border border-border bg-white" title="Email preview">` (deliberately **not** theme-following per spec §8-1 — email bodies stay light-bodied; the frame's own border/container follows the app theme). Below the iframe: warning rows, only rendered when present — amber (`text-amber-700 dark:text-amber-400 text-xs`) "Unknown tag `{frist_name}` — check spelling" per unknown tag, and muted (`text-xs text-muted-foreground`) "`{event_date}` renders blank for this recipient" per missing tag. A `Loader2 animate-spin` micro-indicator replaces the subject line briefly while a debounced (400 ms) re-render request is in flight after a subject/body edit; render errors show an inline `text-xs text-destructive` line under the iframe, iframe keeps its last-good content.
- **`DialogFooter`**: left-aligned "Send test" (`Button variant="outline" size="sm"`, `Send` icon) which expands an inline row above the footer (`space-y-2`, not a nested dialog — nesting overlays hurts focus management) with an email `Input` (`type="email"`, placeholder "you@example.com") + `Button size="sm"` "Send" (disabled while the definition is `enabled:false`, with `Tooltip` "This email is off — turn it on to send a test"); success → collapses back to the button with a transient `text-xs text-muted-foreground` "Test sent to name@example.com just now" line for ~5s + `toast.success`; failure → inline `role="alert"` error under the input, row stays open; the button gets a short (≥1s) `disabled` in-flight guard to satisfy the spec's double-click dedupe test. Right-aligned: `Button variant="outline"` "Cancel" (routes through the unsaved-changes guard) + primary `Button` "Save" (`Loader2` while pending, disabled while pending or while an in-flight preview render hasn't resolved isn't required — save doesn't block on preview).
- **Unsaved-changes guard**: `formState.isDirty` tracked; closing via Esc, overlay click, or Cancel with dirty state opens a small `AlertDialog` ("Discard changes?" / "Your edits to this email haven't been saved." / Cancel + destructive "Discard") before the editor actually closes; clean state closes immediately. Radix `Dialog`'s `onOpenChange` is intercepted (return `false`/re-open) to insert this check — same pattern any RHF dialog in this app would need, first instance of it here since it's the first template-editing surface with real data-entry cost on accidental close.

**Acceptance-critical rendering notes:** the `<script>` XSS case (§3 AC-3) is guaranteed by construction, not by iframe sandboxing alone — `bodyHtml` is server-derived via HTML-escape (per M6-T1's `escapeHtml`), so literal `<script>` text arrives pre-escaped; `sandbox=""` is defense-in-depth for the T4 future, documented as such so QA doesn't expect the iframe attribute alone to be "the" fix.

## 5. Send log (event-wide tab + per-definition History)

`send-log-tab.tsx` (event-wide, no definition filter) wraps the shared `send-log-table.tsx`:

- **Toolbar** (`flex flex-wrap items-center gap-2 border-b border-border px-4 py-3`, same shell as `ResponsesToolbar`): count `Badge variant="secondary" rounded-full tabular-nums` inside `aria-live="polite"` "{n} sent"; status `Select` (All statuses / Queued / Sent / Failed) and kind `Select` (All kinds / each definition's name / "Test send" / "Unknown" grouping raw kinds with no definition match) sit side by side but are **mutually exclusive** (§5 spec constraint, mirrors the T1 index shape) — selecting one programmatically resets the other to "All", and a `text-xs text-muted-foreground` line under the toolbar states "Filter by status or by email — not both at once." (documents the constraint instead of hiding it). Both drive the query via URL params (`?status=` / `?kind=`), not client-side filtering, per the M3 responses-toolbar precedent.
- **Table** (`min-w-[56rem]`, `overflow-x-auto`): columns Recipient (two-line cell: `font-medium text-foreground` name, `text-xs text-muted-foreground` email beneath) | Email (definition name resolved from `kind`, or `Badge variant="outline" className="font-mono text-xs"` showing the raw kind for deleted/unknown/test kinds — §8-4, never a crash or hidden row) | Subject (`truncate max-w-64`, full text in the `title` attr) | Status (badge: queued `variant="secondary"` "Queued"; sent `bg-emerald-100 text-emerald-900 dark:bg-emerald-950 dark:text-emerald-200` "Sent"; failed `bg-red-100 text-red-900 dark:bg-red-950 dark:text-red-200` "Failed") | Time (`tabular-nums`, sentAt/failedAt/queuedAt as applicable, relative-then-absolute on hover via `title`) | Attempts (`tabular-nums text-center`) | row-expand chevron (ghost icon `Button`, `aria-expanded`, `aria-controls` pointing at the detail row's id) | Retry (failed rows only: `Button variant="outline" size="sm"` "Retry", `Loader2` while pending; success updates the row in place + `toast.success("Email resent")`, a 409 `NOT_RETRYABLE` race surfaces `toast.error("This email was already sent")` and the row refreshes to its true status — never a duplicate-send appearance).
- **Row detail** (`send-log-row-detail.tsx`): expanding renders an extra `TableRow` with a single `colSpan`-ing `TableCell` containing the frozen snapshot via `email-preview-frame.tsx` (read-only, same component — one implementation) + a small key/value list (`providerMessageId`, and for failed rows `lastError.message` rendered as **plain text**, never interpreted as HTML, `line-clamp-2` with a "Show more" text-button expanding to full text — §5 AC-7).
- **Load more**: `Button variant="outline"` full-width-on-mobile below the table, cursor-paged 50 at a time, `Loader2` while loading, hidden once the cursor is exhausted.

**`email-history-tab.tsx`** (used inside §3's editor) reuses `send-log-table.tsx` with `kind` locked and the status filter still available, but no kind selector (there's nothing to switch between) and no page-level count-badge chrome (the dialog is already tightly framed).

**States:** empty — `EntityEmptyState` icon `Inbox`, "No emails sent yet", "The log fills when automations go live (M6-T3) or when you send a test."; loading — 6 skeleton rows matching column widths (attendees-table precedent); error — `EntityTableError entityLabel="the send log"`; filtered-empty (a status/kind filter yields zero rows) — reuse the M3 `ResponsesFilteredEmptyState` copy pattern with a "Clear filter" action.

## 6. Sender settings

`sender-settings-dialog.tsx`, `Dialog` `sm:max-w-lg` (default width — this is a simple 3-field form, no divergence needed), opened from the meta line's from-address link (§0):

- `DialogHeader`: "Sender settings" / "Who your event's emails appear to come from."
- Fields (`space-y-4`, RHF + Zod): From name (`Input`, ≤100), From address (`Input type="email"`, ≤254), Reply-to (`Input type="email"`, optional, placeholder "Same as from address"). When no `EmailSettings` doc exists, each field's **value** is the resolved default (event name / `EMAIL_DEFAULT_FROM` / empty) with a `Badge variant="secondary" className="text-[11px]"` "Platform default" beside the label — viewing performs no write (§6 AC nothing-on-view), the badge simply communicates "this is inherited, not saved."
- **Disclaimer** (`InfoNote`-shaped but neutral, not alarmist — reuse `InfoNote` component verbatim): "Emails aren't delivered in this environment yet — sends land in an internal log only. Using your own domain will require verification (SPF/DKIM) once real delivery ships." Rendered above the footer, always visible (matches `InfoNote`'s "always visible, explains the concept" convention).
- Field-level errors render via `FormMessage` from the typed `VALIDATION` result (invalid email shape, control chars, `<`/`>`/`"` in from-name) — inline, not toasts, matching every other entity-dialog convention in this app.
- When a doc **exists**, a `Button variant="link" size="sm"` "Reset to platform default" appears under the fields (only relevant once there's an override to remove) — confirms via a lightweight inline note rather than a second dialog ("Cleared — showing platform defaults" toast on success), calling the delete-override route.

**States:** loading (dialog opened before initial settings resolve) — three `Skeleton h-9` rows in place of the inputs; save error — inline `FormMessage`s per §6 AC-2, no toast (validation is expected/recoverable input, not a system failure).

## 7. Permissions, tenancy

No new visual states beyond the standing convention: server page 403/404 renders the existing dashboard error boundary (no bespoke "Emails" copy needed — matches M5 §3's "existing 403/404 dashboard handling, no new UI"). For a same-org **read-only** member: the page shell, tables, cards and log render fully from server-fetched data (read is membership-gated only, per spec §7), but every mutating control — Active switches, Save in the editor, Retry, Send test, Sender-settings Save, custom-email Delete — fails its `write:events` check server-side; the client shows the same optimistic-then-rollback pattern already spec'd per control, with `toast.error("You don't have permission to do that.")` (the shared M2 §5 phrasing) rather than inventing new copy. No field/button is client-side `disabled` for role alone in T2 (Viewer read-only variant is explicitly M8-T1 — §7, non-goal here) — this is a deliberate parity choice with the M5-shipped convention cited in the spec, not an oversight.

## 8. Cross-cutting states (design notes)

1. **Both themes**: every color-coded element in this spec (Active on/off, send-log status badges, unknown/missing-tag warning text, System/Custom badge) uses the emerald/amber/red/-100/-900/dark:-950/-200 pairing already established across M1–M5 — no new palette introduced. The preview iframe's *content* (`srcDoc`) stays light/white regardless of theme (decision, §8-1) — only its bordered container follows `bg-white` fixed, not `bg-background`, so QA doesn't flag a dark-mode "bug" that's actually intentional (emails render the same for every recipient).
2. **Disabled definitions**: Off toggle → neutral "Off" badge (§1) + in the editor, a banner above the form fields (`text-sm rounded-lg border border-border bg-muted/50 px-3 py-2`) "This email is off — it won't send when automations arrive." Send-test button disabled with the tooltip noted in §3.
3. **Trigger-not-built honesty**: the info-tooltip pattern in §1's `trigger-cell.tsx` is the single source of this messaging — no other surface (editor, log) repeats or contradicts it.
4. **Deleted/unknown kinds**: send-log rows always render (raw-kind `Badge`, §5) — never filtered out, never crash the "Email" column resolver.
5. **No periods → "Not scheduled"**: `trigger-cell.tsx` renders muted "Not scheduled" text (no icon) instead of a date; the editor's datetime picker for that row shows empty with placeholder "No date set."
6. **Zero attendees**: §4's card and §3's preview both fall back to the sample context transparently — no error, no placeholder text swap beyond the name itself reading "Sample Attendee."
7. **Concurrent edits**: no UI lock/merge affordance — documented last-write-wins, consistent with every other single-doc editor in this app (no optimistic-concurrency UI exists anywhere else either).
8. **Stuck `queued` rows**: render as the plain "Queued" badge with age (`Time` column) — no retry affordance (retry is failed-only per §5), no spinner, no "stuck" language — T2 doesn't diagnose what T3's scheduler will own.

## Responsive behavior (320 / 768 / 1024 / 1440)

- **320–767px**: header row wraps (h1 block, then action buttons wrap to their own row); meta line wraps to two lines; Tabs list scrolls horizontally if needed (`overflow-x-auto`, matches Attendees/Pricing tabs). Each `email-group-table.tsx` scrolls horizontally **inside its own rounded container** — no page-level horizontal scroll (§1 AC-7 hard requirement). The debt-chase/preview grid is single-column full-width (grid only activates ≥`lg`). `email-editor-dialog.tsx` uses the Dialog primitive's own `max-w-[calc(100%-2rem)]` mobile behavior with the compose/preview grid collapsed to one column (form fields, then preview pane, in DOM/reading order) and the dialog content scrolling vertically (`max-h-[88vh] overflow-y-auto`). Send-log table scrolls horizontally within its wrap; Recipient/Email columns get slightly wider min-widths so the scroll starts predictably.
- **768–1023px**: same single-column grid for §1's debt-chase+preview (breakpoint is `lg`, ~1024px, per spec — 768 is still stacked); editor dialog's compose/preview grid activates at `md` (768px) — two columns already at this width, since the dialog's own max-width (`sm:max-w-4xl`) comfortably fits two ~28rem columns.
- **1024–1439px**: §1's grid becomes 2-column (table | preview card); send-log toolbar's two selects sit inline without wrapping.
- **1440px+**: no further layout change — content max-widths already cap table/card widths; extra space is idle margin (consistent with every other dashboard screen — no new max-width container introduced).

## Accessibility & interaction summary

- Tables: real `<th>` headers via `TableHead`; status/active pills carry text, never color-only; timestamps `tabular-nums`.
- Row-level "open editor" affordance is a real `<button>` inside the name cell (not a `TableRow onClick`), so it's a native tab stop with correct `role` for free — avoids the custom `role="button"` + keydown-handler pattern entirely.
- Dialogs: Radix focus trap + return-focus is automatic; `email-editor-dialog.tsx`'s unsaved-changes guard intercepts `onOpenChange` (Esc, overlay click, and the Cancel button all funnel through the same dirty-check) so Esc never silently discards; destructive confirms (`Delete`, `Discard changes?`) always use `AlertDialog`, never a bare `Dialog`.
- Disabled-with-tooltip (Open Email Designer, wallet badges, disabled Send-test): keyboard-reachable `<span tabIndex={0}>` wrapper per the M5 convention, so tooltip content is available without a mouse.
- Merge-tag menu: standard `DropdownMenu` roving-focus/`Escape`-to-close behavior is free from Radix; each `DropdownMenuItem`'s accessible name is the tag + human label (not just the raw `{tag}` token), so screen-reader users get the same context sighted users get from the two-line item.
- Preview iframe: `title="Email preview"` always set; it is **not** a live region (content changes are user-driven via the form, not ambient) — no `aria-live` needed, but the debounced-render loading state gets a visually-adjacent `Loader2` with no separate announcement (avoids chatty live-region noise on every keystroke-triggered re-render).
- QR in the confirmation preview card stays `aria-hidden` (decorative admin preview, M5 badge-preview precedent) — this is **not** the attendee-facing confirmation QR, which already carries `role="img"` per the M5 design spec and is unchanged here.
- Contrast: every badge/text pairing reuses -900/-200 dark-mode pairs already verified ≥4.5:1 elsewhere in this app (no new color introduced) — `lastError.message` truncation uses `line-clamp-2` (visual only) with the full text always present in the DOM for assistive tech via the "Show more" expand, never `title`-only.
