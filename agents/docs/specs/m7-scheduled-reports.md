Research Lead, 2026-07-17. Screen reference: `prototype/prototype/event-reports.html` line 38 — the topbar action bar carries exactly two buttons, `<button class="btn">Schedule</button>` and `<button class="btn primary">Export table</button>`, both **page-level**, not per-template-row (every template row in the "Report templates" table below only has a `Run` button — confirmed by direct read of the full file, lines 69–81). ## Shared decisions

**D1 — Delivery mechanism: a dashboard deep-link, never a CSV/attachment. This is the ticket's first and most consequential call, made explicit here because the "easy" implementation (attach the CSV) is actively unsafe and the infrastructure doesn't support it anyway.**
- **`EmailTransport.send()`'s own input shape has no attachment field** (`src/lib/email/transport.ts`, `SendEmailInput`: `messageId, from, replyTo, to, subject, bodyHtml, bodyText` — nothing else). `sendEventEmail`/`sendEventEmailBatch` (`src/lib/email/send-service.ts`) pass exactly this shape through end-to-end; `EmailMessageDoc` (`src/types/collection.ts`) has no attachment field either. **Adding attachment support would mean touching the transport interface, the dev outbox transport, the `EmailMessageDoc` schema, and — critically — a future real provider adapter (SES/SendGrid/etc., M6-T1's still-open Q2) would need to actually implement MIME attachment encoding, none of which exists today.** This is real, non-trivial new infrastructure this ticket's scope does not justify building speculatively (same YAGNI posture M7-T2's D2 took toward a streaming exporter).
- **Even if attachment support existed, this spec would still reject it as the wrong default**, for the exact reason M7-T2's D4 already established for the Abandoned template's masked email: a CSV attachment is a **higher**-risk exposure surface than an on-screen dashboard view — a file in an inbox can be forwarded, auto-synced to a personal device, retained indefinitely outside this app's own access logs, and (per M7-T2 D1) a CSV *download* is already treated by this codebase's own convention as the "mutating-route-adjacent," `write:events`-gated tier specifically **because** it's a data *exit*. Emailing that same exit-class artifact on a recurring, unattended schedule to a stored recipient list is a strictly worse version of the exact risk D1 already named — it removes the one control (a live, `write:events`-gated HTTP request) that makes today's on-demand CSV export acceptable.
- **Decision: the scheduled email contains a link back into the dashboard (`/dashboard/events/[eventId]/reports`, deep-linked to the relevant template — §4) and nothing else PII-bearing.** No row data, no attendee names/emails, no financial totals in the email body itself. Clicking the link requires a live, authenticated session with org membership (Run) or `write:events` (Export CSV, unchanged from M7-T2) at **click time** — access is enforced by the exact same gates M7-T2 already shipped, not by anything new this ticket invents. A recipient whose access has since been revoked (removed from the org, or downgraded below `write:events`) gets exactly the same 403/404 any other now-unauthorized user gets clicking a stale dashboard link — this ticket adds zero new access surface, only a notification that a page exists.
- **Consequence, stated plainly:** the delivery mechanism itself is the primary defense against the backlog's named exfiltration concern — an attacker who somehow got themselves onto a schedule's recipient list (see D2 for why that's already hard) still gets nothing but a notification email and a login wall, never a payload. §2 (recipient model) is therefore genuine defense-in-depth on top of D1, not the only control.

**D2 — Recipient model: verified current org members only, server-validated on add and RE-verified at every send — never free-text, never a client-trusted list. This is the ticket's central security decision (backlog's own SEC flag: "no exfiltration to arbitrary emails without role check"), and it is made here, not punted to Security wholesale, for the same reason M7-T2's D1 gave: the codebase already has the pieces to answer it correctly.**
- **A real gap, named honestly: this codebase has no "list all members of an organization" query today.** `UserDoc.organizations` is an array embedded on each user's own doc (`src/types/collection.ts`), not a reverse-indexed collection — there is no Firestore query shaped "give me every member of org X" anywhere in `src/lib/db/` (confirmed by exhaustive grep). `src/features/iam/components/iam-dashboard.tsx` (M8-T1, still Todo) is 100% hardcoded mock data with no real DAL behind it. Building a real org-roster **picker** (a dropdown/autocomplete enumerating every member) would mean either a new reverse-lookup query (a new `organizationId`-scalar-filtered `User` query, which only catches members whose *currently active* org happens to be this one — a real, silent undercount for anyone who has since switched their active org elsewhere) or new denormalized infrastructure — genuinely **M8-T1's job** (real IAM), not this ticket's.
- **Decision: this ticket does NOT build a roster-picker.** Instead, adding a recipient is a **validate-on-submit** action: the organizer types (or picks from a small "add myself" default) an email address; the server validates it via `getAdminUserMembership(email, organizationId)` (`src/lib/db/adminUserOrganization.ts`, already shipped, already correct — it reads the *authoritative* embedded `organizations[]` array directly off that user's own doc, so unlike a hypothetical `organizationId`-scalar query it has **zero** false negatives regardless of that user's currently-active org) — a non-member email is rejected with a typed, visible error ("not a member of this organization"), **zero silent acceptance, zero free-text fallback.** This is smaller in scope than a real picker, avoids inventing IAM infrastructure prematurely (YAGNI — M8-T1 is exactly the ticket that should add real roster enumeration), and is *more* correct on the one axis that matters for the anti-exfiltration goal: it can never accept a non-member, whereas a picker sourced from the currently-buildable (incomplete) roster query could give a false sense of completeness while still being bypassable by typing an email not shown in the dropdown if the "add" action itself weren't independently validated.
- **Recipients are NOT restricted to `write:events` holders specifically — any current, verified org member (any role) is a valid recipient.** Rationale: D1 already means a recipient's link only ever grants what their own live session independently entitles them to (Run = org-membership gate, Export CSV = `write:events` gate, both re-checked at click time, unchanged from M7-T2) — a Viewer-tier recipient who clicks the link sees exactly the Run table they could already see by visiting the Reports screen directly today; restricting the recipient *list* to `write:events` holders would add a redundant, un-argued-for restriction on top of a gate that already exists downstream, the same reasoning M7-T2's D1 used to reject gating Run's on-screen preview more strictly than the roster page it's built from.
- **Re-verification at send time, not just at add time (the actual "role check," matching the backlog's literal wording) — this is the part that makes the model durable, not just correct at creation:** immediately before each scheduled fire enqueues a recipient's send, re-run `getAdminUserMembership(recipientEmail, organizationId)` fresh (never cached from add-time). A recipient no longer found in the org's roster is **silently dropped from that send** (no error surfaced to the organizer who configured the schedule, no removal of the stored recipient from the schedule's own config — matching T2/T3's established "enabled is re-checked at fire time, not cached" discipline, applied here to *membership* instead of a boolean toggle). If that person is re-added to the org later, they resume receiving future scheduled deliveries automatically (their stored recipient entry never had to be removed) — same "derived, not invented" spirit as M6-T3's dedupeKey philosophy, applied to the eligibility check instead of the dedupe mechanism.
- **`write:events` is required to CREATE/EDIT the schedule itself (§7), but not to be a recipient of it** — matches M7-T2's D1 "download/export tier" reasoning: *configuring* a recurring distribution mechanism is an export-adjacent action (an ongoing commitment to send data somewhere, repeatedly, unattended); *receiving* a notification email whose payload is gated identically to the Reports screen itself is not.
- **External (non-org-member) recipients are explicitly NOT supported in this ticket — named as an open question, not silently solved.** No verification mechanism exists in this codebase today for "this outside email address is trusted for recurring PII-adjacent delivery" (no invite-and-verify flow scoped to a single report, no email-ownership confirmation step). The one legitimate real-world case (an accountant or auditor who isn't an org member) is a genuine future need, but the safe way to support it is **through the org membership system itself** — invite them as a real (ideally low-privilege, read-only "Viewer") member via M8-T1's eventual invite flow, so they go through the same domain-verification/invite-acceptance path every other member does, rather than adding a parallel free-text recipient channel that bypasses membership entirely. See OQ-2.

**D3 — Frequency options and "next due" computation reuse T2's event-timezone conversion exactly, extended (not forked) for recurrence.**
- Three frequencies: `daily`, `weekly` (+ `dayOfWeek`, 0=Sunday..6=Saturday, JS `Date`-convention, documented explicitly to avoid ISO-vs-JS ambiguity), `monthly` (+ `dayOfMonth`, 1–31) — plus a single `hour`/`minute` (0–23 / 0–59) fired **in the event's own timezone**, reusing `resolveEventTimeZone()` (`src/features/registration/utils.ts`) verbatim, the exact helper T2's `scheduled` trigger type already uses to materialize `trigger.at` from event-local time.
- **Monthly clamping rule (stated explicitly, not left ambiguous):** a schedule configured for `dayOfMonth: 31` fires on the last real day of any shorter month (`min(dayOfMonth, daysInMonth(year, month))`) — e.g., fires on Feb 28/29, not silently skipped and not rolled over to March 1. This is the same "documented, deliberate simplification" posture M6-T3 §4 used for its own date-math edge case (measuring debt-chase offsets from `Order.createdAt` because no due-date field exists) — a real, named rule, not an accidental gap.
- **Period identity (`periodKey`) is a deterministic string computed from the schedule's own config + a calendar instant, never a random id and never separately persisted as "already fired" state** — matching M6-T3's "dedupe is derived, not invented per-send" philosophy exactly:
  - `daily` → the event-local calendar date, `YYYY-MM-DD`.
  - `weekly` → the event-local calendar date of that week's configured `dayOfWeek` occurrence, `YYYY-MM-DD`.
  - `monthly` → `YYYY-MM` (the clamped day is a fixed function of the month, so the month alone is a sufficient, unambiguous period key).
- **A period's "due" instant** = `resolveEventTimeZone`-based conversion of `(periodKey's calendar date, schedule.hour, schedule.minute)` to an absolute UTC instant — the same event-local-time → UTC-instant conversion T2 already performs for `trigger.at`, extended with an hour/minute offset rather than always midnight (`eventLocalDateToUtcMs`-family helper, `src/features/registration/utils.ts` / `src/lib/email/lifecycle/event-schedule.ts` — Backend's exact call shape, not forked logic).
- **`dedupeKey = scheduleId + ":" + periodKey`** — no recipient component needed in the string itself: `emailMessageId()` (`src/lib/db/emailMessageId.ts`) already hashes `(organizationId, eventId, kind, recipientEmail, dedupeKey)` as five separate tuple elements, so two recipients sharing one `dedupeKey` naturally land on two distinct outbox docs (the exact same property M6-T3 §7's "Email all" already relies on with `dedupeKey: draftId` shared across a batch of *different* drafts — here it's one dedupeKey shared across a batch of different *recipients* for the *same* draft-equivalent, i.e., the same period). One schedule, one period → each currently-verified recipient gets **at most one** send, ever, no matter how many sweep ticks re-observe that period as due.

**D4 — Catch-up window: bounded, not open-ended, and never predates the schedule's own creation — mirrors M6-T3 §5's exact posture, applied to a repeating (not one-shot) trigger.**
- A poll tick attempts delivery for **every period whose due-instant has already passed**, back to a hard ceiling of **`MAX_CATCHUP_PERIODS = 4`** most-recent periods (so a daily schedule catches up at most 4 days back, weekly at most 4 weeks, monthly at most 4 months) — **and never earlier than the schedule's own `createdAt`** (a schedule created today must never backfill periods that predate its own existence, the same "no backlog of missed-while-disabled sends is invented" rule M6-T3 §3 AC-6 already established, generalized here to also cover "missed because the schedule didn't exist yet").
- **No pre-check query is needed to decide which periods are "already sent" before attempting them** — exactly like every M6-T3 trigger, the evaluator simply *attempts* `sendEventEmailBatch` for every in-window due period on every tick; `createAdminEmailMessageIfAbsent`'s create-if-absent semantics at the id-tuple level make already-sent periods a zero-write, zero-side-effect `duplicate` outcome (M6-T3 §3 AC-2's exact precedent: "re-evaluating the same still-eligible candidate on every subsequent poll tick produces zero additional rows"). This is deliberately simpler than a stored "last sent period" cursor and cannot drift out of sync with reality, because the outbox itself *is* the state.
- **Why a bounded window, not unbounded catch-up:** unlike M6-T3's one-shot `scheduled` trigger type (whose catch-up window naturally ends at the event's first-period-start cutoff), a report schedule repeats indefinitely — an unbounded catch-up on a schedule that was paused for months, or on a sweep that was broken for a long stretch, would otherwise silently queue a burst of dozens of backdated report emails the moment it resumes. `MAX_CATCHUP_PERIODS = 4` is a named, changeable ceiling (one constant, `src/features/reports/schedule-constants.ts` or similar), not an arbitrary inline magic number — same discipline M7-T2's `REPORT_EXPORT_ROW_LIMIT`/`ABANDONED_EXPORT_MAX_RAW_PAGES` already established.
- **Recipient-dimension volume is NOT a concern this ticket needs paging infrastructure for** — unlike M6-T3's audience-segment triggers (which can fan out to thousands of attendees and therefore need `run-sweep.ts`'s cursor-paged, budget-limited evaluation), a report schedule's recipient list is small **by construction** (D2: verified org members only, capped at `MAX_RECIPIENTS_PER_SCHEDULE = 20`, §4) — worst case per schedule per tick is `4 periods × 20 recipients = 80` send attempts, trivial next to the thousands-of-attendee case M6-T3 §8 was built to bound. The only volume dimension that still needs the existing paging discipline is the **event-sweep** dimension (many events, each with up to a handful of schedules) — reused as-is from `run-sweep.ts`'s `maxEvents` bound, not reinvented.

**D5 — Scheduling mechanism: extend the SAME M6-T3 internal evaluator, not a parallel one — confirmed genuinely reusable, one real difference named below.**
- The Cloud Scheduler → `POST /api/internal/email-triggers/evaluate` → fail-closed shared-secret → `runLifecycleTriggerSweep()` → per-event `evaluateEventLifecycleTriggers()` architecture (`src/lib/email/lifecycle/*`, confirmed by direct read of `run-sweep.ts` and the route itself) is **the correct, already-reviewed shape to extend**, not fork: same unattended-caller authentication posture (§9 of M6-T3's own spec: "not a normal session-authenticated `write:events` route... MUST be protected from public invocation by a fail-closed shared secret"), same event-level pagination (`listAdminPublishedEventsPage`), same per-event budget model, same idempotent-by-construction safety property. Recommended (non-binding, same posture M6-T3 §8 took toward its own mechanism choice): Backend adds report-schedule evaluation as a **new step inside the existing per-event evaluator** (`evaluate-event.ts`'s fan-out, alongside the 3 existing periodic trigger types), so **one** Cloud Scheduler job continues to drive everything — rather than a second scheduler job hitting a second route, which would double the operational surface (a second cadence to tune, a second secret to rotate, a second runbook entry) for zero architectural benefit given the two workloads share every precondition (org/event scoping, fail-closed auth, idempotent sends).
- **The one real difference from M6-T3's three trigger types, named explicitly so it isn't silently glossed over:** M6-T3's triggers are either real-time (on-submit/on-accept) or audience-driven periodic (query a segment, send to whoever's currently in it). A report schedule is **neither** — it has no "audience query" at all; its "recipients" are a small, static, organizer-configured list stored directly on the `ReportSchedule` doc (§4), re-verified per-recipient at fire time (D2) rather than re-queried as a segment. This means `queryAudiencePage()` (`src/lib/email/lifecycle/audience-queries.ts`) is **not reused** for this trigger — there is no new audience type to add to that module's table, and Backend should not force this into the `EmailDefinitionAudience` enum (`all-invitees` / `abandoned` / `pending-approval` / `accepted-*`) since none of those six values describe "the schedule's own stored recipient list." A `ReportSchedule` is a materially different, smaller entity than an `EmailDefinition` (§4) for exactly this reason.

## 1 — What gets scheduled, and where the button lives

*As an event organizer with edit access, I want to set up a recurring email that reminds me (or a colleague) to check a specific report, without having to remember to open the Reports screen myself every week.*

- **Entry point (matches the prototype exactly):** the Reports screen's existing topbar `Schedule` button (`prototype/prototype/event-reports.html` line 38, currently unimplemented — confirmed no `Schedule` handler exists anywhere in `src/features/reports/`) opens a **management surface** (dialog, per the recommendation below) listing the event's existing report schedules (0–5 of them — see §4's one-per-template cap) with a **+ Add schedule** action.
- **One schedule targets exactly one of the 5 existing report templates** (`ReportTemplateId` from `src/features/reports/templates.ts`, reused verbatim — no new template concept). The "+ Add schedule" flow is: pick a template (dropdown of the 5, matching D6's names) → pick frequency/day/time (§3) → add recipients (§2) → Save.
- **Interaction shape, flagged for UX to finalize (not decided here, same posture M7-T2's own §6 OQ-1 took):** a dialog (mirroring M6-T2's `sender-settings-dialog.tsx` — a proven "one global settings surface opened from a single button" pattern already shipped on the sibling Emails screen) is this spec's recommendation, given the topbar button is singular and the whole feature's config surface is small (≤5 schedules, ≤20 recipients each). A dedicated `/dashboard/events/[eventId]/reports/schedules` sub-route is an equally valid alternative UX may prefer; both satisfy this spec's behavioral requirements.
- **Deep-link requirement on the OTHER end (the email's own link target) needs one small, additive change to already-shipped code, named explicitly:** `report-templates-section.tsx` currently holds `activeTemplate` in local `useState` with no URL sync (confirmed by direct read) — there is today no URL that opens the Reports screen with a specific template's Run panel already expanded. This ticket requires adding a `?template=<slug>` query-param read (initial state only, one-way) so the emailed link (§2's D1 dashboard-link) actually lands the recipient on the right panel rather than a generic "go find it yourself" page. This is a small, scoped, backward-compatible addition to an existing client component, not a rearchitecture — Full-Stack's implementation, not Backend's.

**Acceptance criteria**
1. Clicking "Schedule" from the Reports screen topbar opens the management surface; a fresh event with zero schedules shows an empty state ("No scheduled reports yet") with the "+ Add schedule" action, not a crash or a blank dialog.
2. The "+ Add schedule" flow cannot submit without a template, a complete frequency configuration (§3), and at least one verified recipient (§2) — client + server validation both refuse an incomplete schedule (server is the authority; client validation is UX only).
3. A link of the form `/dashboard/events/{eventId}/reports?template={slug}` opens the Reports screen with that template's Run panel already expanded (the accordion state in `report-templates-section.tsx` initializes from the query param) — regression test for the FS wiring named above.
4. An org member without `write:events` sees the "Schedule" button in a disabled/tooltip state (or the dialog opens read-only) — matching §7's permission gate; they can still be *added as a recipient* to a schedule someone else configures (D2 — creating vs. receiving are different tiers).

## 2 — Recipients: add, validate, remove, re-verify (implements D2)

*As an event organizer, I want to send a scheduled report to myself and a couple of teammates, and I want the system to refuse anything that isn't a real member of my organization — not because I'd try to abuse it, but because I don't want a typo or a copy-paste mistake to quietly leak a report link to the wrong address either.*

- **Add:** a recipient-entry control (email input, "+ Add" action) — **not** a free-text list stored as-is. On submit, the server calls `getAdminUserMembership(email, organizationId)` (`src/lib/db/adminUserOrganization.ts`); a `null` result is a typed rejection ("This email isn't a member of your organization — invite them first.") with **zero** write. A successful match stores `{ email: lowercased, name: <the matched User doc's name> }` — the *matched* member's real name, never a client-supplied display name (prevents a UI-only spoofed label from ever appearing on a real send).
- **A default, frictionless first recipient:** the schedule creator's own account is offered as a one-click "Add myself" default in the add-recipient UI (their email is already known and already verified by definition — their own live session) — not auto-added silently, since an organizer may intentionally want a schedule that goes to a colleague only, not themselves.
- **Cap:** `MAX_RECIPIENTS_PER_SCHEDULE = 20` per schedule — a named, small ceiling consistent with this feature's realistic usage (a handful of stakeholders per report, not a mailing list; a genuine mailing-list need is out of scope and would be better served by a real distribution-list/group feature, not this ticket).
- **Remove:** any recipient can be removed from a schedule at any time by anyone with `write:events` on the event (§7) — takes effect on the schedule doc immediately; already-sent historical `EmailMessage` rows for that recipient are untouched (audit retention, same principle as every other outbox row in this app).
- **Re-verification at every fire (D2's durability guarantee, restated as its own testable behavior):** immediately before a period's batch send, each stored recipient is re-checked via `getAdminUserMembership` fresh — a recipient no longer a member is silently excluded from that batch (no error surfaced anywhere, no auto-removal from the schedule's stored config) and simply resumes receiving future deliveries automatically if/when they rejoin.

**Acceptance criteria**
1. Adding a real org member's email succeeds and stores their *matched* name, not any client-supplied text.
2. Adding an email with no membership in the org (typo, external address, ex-member) is rejected with a clear, typed error and produces **zero** write to the schedule doc — a two-org fixture proves a real member of a *different* org is also correctly rejected (cross-tenant IDOR-shaped test, same convention as every other cross-org test in this codebase).
3. A 21st recipient add attempt on a schedule already at the cap is rejected with a typed error, not silently truncated.
4. A schedule with 3 recipients, one of whom is removed from the organization (roster mutation, hand-seeded) between schedule creation and the next sweep tick, delivers to the remaining 2 and produces **zero** send attempt (and zero rejection-error row) for the removed one — verified via `getAdminUserMembership` mock/fixture returning `null` for that one email on the fire-time re-check.
5. Removing a recipient from a schedule via the management UI takes effect on the very next sweep tick — no in-flight "already queued for this period" leftover state to worry about, since D4 explicitly performs no pre-check/cursor (the removed recipient's `getAdminUserMembership` re-check on the next tick is simply never reached, because they're no longer iterated as a stored recipient at all).

## 3 — Frequency configuration (implements D3/D4)

*As an event organizer, I want to choose daily, weekly, or monthly delivery, at a time that makes sense in my event's own timezone, and I never want to get the same report twice for the same period or silently miss one because the system was down for a bit.*

- **UI fields:** frequency selector (Daily / Weekly / Monthly), conditional day-of-week (weekly) or day-of-month (monthly) selector, and an hour/minute time picker — all rendered and interpreted in the **event's own timezone**, matching T2's `trigger.at` display convention exactly ("Sep 8, 9:00 ET" — tz abbreviation shown, never left ambiguous as to which timezone the configured time means).
- **Monthly day-of-month picker range is 1–31 with inline copy disclosing the clamping rule** (D3) — e.g., a helper note under the field: "Fires on the last day of shorter months." No separate "Last day of month" special option is offered — the clamp behavior covers that case without a second UI affordance.
- **No timezone picker of its own** — the event's timezone (already configured elsewhere in the event's settings, per T2's precedent) is the only timezone a schedule can fire in; this avoids inventing a second, potentially-conflicting timezone concept for one narrow feature.

**Acceptance criteria**
1. A daily schedule set for 09:00 event-local fires (produces outbox rows for every current recipient) at the first sweep tick where `now >= that day's 09:00 event-local instant`, and produces zero additional rows on every subsequent tick that same day (dedupe, D3).
2. A weekly schedule set for Monday 09:00 fires once per week, on the Monday occurrence, never on any other day even if the sweep tick lands mid-week.
3. A monthly schedule set for day 31 fires on Feb 28 (non-leap year fixture) and Feb 29 (leap year fixture) — the clamp rule (D3), asserted for both.
4. A schedule created at 2pm event-local for a "daily 09:00" cadence does **not** immediately fire for "today's already-passed 09:00 period" if that period's due-instant predates the schedule's own `createdAt` (D4's floor) — it first fires tomorrow at 09:00, never retroactively for a period before the schedule existed.
5. A schedule paused (`enabled: false`, §4) for 10 days and then re-enabled catches up **at most** the last `MAX_CATCHUP_PERIODS` (4) periods, never the full 10-day gap — a daily-schedule fixture proves exactly 4 backfilled sends, not 10, on the first tick after re-enabling.
6. Disabling a schedule mid-tick (between processing period N and N+1's send) stops period N+1 (and any later period) from firing on that tick or any later one, while period N's already-enqueued sends stand (T1's "sent is terminal" — no un-send), matching M6-T3 §3 AC-6's exact precedent.

## 4 — `ReportSchedule` entity + schedule CRUD (implements D5's "not an EmailDefinition" call)

*As Backend, I need a small, purpose-built entity for this — not a bent-to-fit reuse of `EmailDefinition`, because a report schedule has no audience query, no subject/body template to edit, and a recipient list `EmailDefinition` has no field for.*

- **Entity `ReportSchedule`** (new, root collection, `write:events`-gated, no client repo pair — matches `EmailDefinition`'s own server-only precedent since this also carries organizer-configured recipient data): `{ organizationId, eventId, templateSlug: ReportTemplateId, frequency: "daily" | "weekly" | "monthly", dayOfWeek: number | null (0–6, weekly only), dayOfMonth: number | null (1–31, monthly only), hour: number (0–23), minute: number (0–59), recipients: Array<{ email: string, name: string }> (≤ `MAX_RECIPIENTS_PER_SCHEDULE`), enabled: boolean, createdBy: string (creator's email, audit only), createdAt, updatedAt }`.
- **Deterministic doc id, one active schedule per (event, template) — decision, not an oversight:** `reportScheduleId = sha256(JSON(["ReportSchedule", organizationId, eventId, templateSlug]))`, the exact tuple-hash family every other deterministic id in this codebase already uses (`emailDefinitionId`, `emailMessageId`, `attendeeId`, `formDataId`). Consequence: an event can have **at most one** schedule per template (5 max total), and "editing a schedule" is an upsert onto this same id — matching `EmailDefinition`'s own "materialized on first edit" create-if-absent pattern. **This is a deliberate scope simplification, named explicitly (YAGNI):** nothing in the prototype or the backlog goal implies an organizer needs *two different* cadences for the *same* report simultaneously (e.g., both a daily and a weekly Registration-overview delivery) — if that need materializes, relaxing this to a freely-creatable list (a real per-schedule uuid instead of the deterministic per-template id) is a small, backward-compatible follow-up, not a breaking migration.
- **`enabled` toggle = pause/resume**, not delete — matches every other toggle-state entity in this codebase (`EmailDefinition.enabled`, `CheckinConfig` toggles). **Delete** removes the `ReportSchedule` doc entirely (hard delete, no soft-delete/archive concept introduced) — historical `EmailMessage` rows already sent under that schedule are untouched (audit retention, unchanged).
- **CRUD routes**, all under `src/app/api/dashboard/events/[eventId]/reports/schedules/` (new — `route.ts` for list/create, `[templateSlug]/route.ts` for get/update/delete, matching the deterministic-per-template-id addressing above), every one gated **`write:events`** via `resolveReportsRouteScope(eventId, { requireWriteEvents: true })` (`src/features/reports/server/reports-route-scope.ts`, reused verbatim — zero new auth helper, this ticket's routes are just new callers of the exact same, already-reviewed function M7-T2 shipped) — 403 for a member without `write:events`, 404 for cross-org/unknown `eventId`, Zod-validated request bodies (≤32 KB, matching the M1–M7 mutating-route body-cap convention carried from M5's L-2 backlog note), rate-limited (`src/lib/rate-limit.ts`, same posture as every other mutating dashboard route).

**Acceptance criteria**
1. Creating a schedule for a template that already has one (same event) upserts the existing doc rather than creating a second — proven by asserting exactly one `ReportSchedule` doc exists for that `(eventId, templateSlug)` pair after two sequential "create" calls with different frequencies (the second call's frequency wins).
2. Every schedule CRUD route returns `403` for an org member without `write:events` and `404` for a cross-org/unknown `eventId` — the same two-test shape M7-T2 §7 AC-1/AC-2 already established for the export routes, applied here.
3. Toggling `enabled` off stops the schedule from firing on the next sweep tick (§3 AC-6); deleting it removes it from the management UI's list immediately and stops all future firing, while historical `EmailMessage` rows for it remain queryable in the Email overview report (§5, M7-T2) under their stored `kind`.
4. A malformed body (unknown `frequency` value, `dayOfMonth` out of 1–31, more than `MAX_RECIPIENTS_PER_SCHEDULE` recipients, a `templateSlug` not among the 5 real `ReportTemplateId` values) is rejected `400` with field errors, zero write.

## 5 — Delivery content, `kind`, and Email overview integration (implements D1's link + D3's dedupeKey together)

*As an organizer reading the Email overview report (M7-T2 §5) later, I want to see that a scheduled-report notification went out, same as any other email this event has sent — not a mysterious gap in the audit trail.*

- **Send substrate:** `sendEventEmailBatch` (`src/lib/email/send-service.ts`, "T3's 'Email all' substrate" — reused a second time by a second ticket, exactly as its own header comment already anticipated for *some* future batch use), called once per due period per schedule, with one batch entry per currently-verified recipient (§2).
- **`kind = "scheduled-report:" + templateSlug`** (e.g., `"scheduled-report:registration-overview"`) — a **new, free-text `kind` value**, not routed through `EmailDefinition` at all (`definitionId: null`, matching how `SendEventEmailInput.definitionId` is already optional) since a `ReportSchedule` is not an `EmailDefinition` (D5). Using a `templateSlug`-suffixed kind means the Email overview report's existing `kind → name` resolution (`mergeEmailDefinitions()`, M7-T2 §5) automatically falls back to the raw `kind` string verbatim for these rows (its own already-documented, already-tested behavior for any kind with no catalog match) — a scheduled-report delivery shows up there for free, correctly labeled, with **zero** change to that template's own code.
- **No organizer-editable subject/body in this ticket's scope (explicit non-goal, named to keep scope tight):** the email's subject and body are **fixed, code-defined copy** (e.g., subject "Your {report_name} report is ready — {event_name}", body: one or two sentences + the D1 dashboard link) — reusing T1's `renderEmailTemplate`/merge-tag pipeline verbatim for the substitution (no new render pipeline), but with **no** editor UI, no "Insert merge tag" menu, no live preview surface built for it (all of which are real, T2-shipped infrastructure this ticket deliberately does not extend to a sixth editable template — a genuine future polish item, not silently assumed away).
- **Content is intentionally minimal and non-PII (D1's own consequence, restated as a content rule):** the body names the report and links to it; it never includes row counts, row data, dollar amounts, or attendee names — the whole point of the dashboard-link model is that the email itself carries nothing worth intercepting.

**Acceptance criteria**
1. A fired schedule's resulting `EmailMessage` rows have `kind: "scheduled-report:<templateSlug>"`, `definitionId: null`, and a `dedupeKey` matching D3's `scheduleId:periodKey` formula exactly.
2. The Email overview report (M7-T2, unmodified code) lists these rows with the raw `kind` string shown (no crash, no blank "Email" cell) — a direct regression test proving zero required changes to that template's loader.
3. The rendered email body contains the `/dashboard/events/{eventId}/reports?template={slug}` link (§1 AC-3) and contains **no** row-level data of any kind — a fixture-based assertion scanning the rendered body for any seeded attendee name/email/dollar amount from that event's data confirms none leak into the notification.
4. `bodyHtml`/`bodyText` render through the same size/content validation `sendEventEmail` already enforces for every other send (`validateRenderedEmailContent`) — no new bypass introduced for this call site.

## 6 — Permissions & tenancy (cross-cutting)

- **Create / edit / pause / delete a schedule:** `write:events`, via `resolveReportsRouteScope(eventId, { requireWriteEvents: true })` — the exact same tier and the exact same helper M7-T2's 5 CSV export routes already use (D5, §4).
- **Be a recipient of a schedule:** any current, verified org member (D2) — deliberately broader than `write:events`, justified in D2.
- **View the linked report (Run or Export) after clicking the emailed link:** unchanged from M7-T2 — org membership for Run, `write:events` for Export CSV — this ticket adds no new gate here, only a notification pointing at gates that already exist.
- **The internal sweep entrypoint** (whichever of D5's two wiring options Backend picks) inherits M6-T3's exact tenancy contract unchanged: every DAL call it makes carries both `organizationId` and `eventId`, and the route itself is never session-authenticated — protected only by the fail-closed shared secret, same posture, same secret, same rate limit (6/min) if folded into the existing route; an equivalent new limiter if Backend instead stands up a sibling route.

**Acceptance criteria**
1. A `write:events`-holding member of Org A cannot create, view, edit, or delete a `ReportSchedule` belonging to Org B's event — two-org IDOR test, same shape as every other cross-org test in this codebase.
2. A member of the correct org without `write:events` gets `403` attempting any schedule-mutating route, but is unaffected as a *recipient* if someone else with `write:events` added them (proves the two tiers are genuinely independent, not accidentally coupled).

## 7 — States & edge cases (cross-cutting)

- **Empty (zero schedules for the event):** management surface shows "No scheduled reports yet" with the "+ Add schedule" CTA — not a blank dialog, not confused with a load failure.
- **Loading / error:** the management surface follows the same skeleton/error/retry conventions every other dashboard dialog in this app already uses (`EntityTableError`-family or dialog-scoped equivalent) — no new pattern invented.
- **A schedule targeting a template that is later... nothing changes about, since templates are a fixed, code-defined set of 5 (`REPORT_TEMPLATES`, `src/features/reports/templates.ts`) — there is no "template deleted out from under a schedule" case to handle, unlike a hypothetical user-deletable entity.** Stated explicitly so QA doesn't invent a test for a state that cannot occur.
- **A schedule whose every recipient has left the org (D2's re-verification drops all of them for a given fire):** the sweep still "fires" in the sense of attempting the batch, but `sendEventEmailBatch` correctly no-ops on an empty (post-filter) recipient list (already-documented "empty recipient list is a calm success no-op," `send-service.ts`) — zero error, zero crash, the schedule silently produces no mail for that period and tries again next period. **Not** surfaced to the organizer as a warning in this ticket's scope (a genuine future polish item — "this schedule currently has zero deliverable recipients" — named here, not built).
- **Never:** a raw Firestore error, an unhandled promise rejection, a PII-bearing string anywhere in a sent notification's subject/body (§5 AC-3), a recipient stored on a schedule who was never independently verified as an org member (§2 AC-2), a CSV attachment on any outbound message (D1).

**Acceptance criteria**
1. Each named empty/error/no-recipients state renders/behaves exactly as described above, individually tested.
2. Both themes, responsive (320/768/1024/1440) for the management dialog — same convention as every other dashboard dialog, one thorough pass sufficient (M7-T2 §8 AC-2's proportionality precedent).

## Non-goals for T3 (explicit)

- **No new report types** — exactly M7-T2's 5 templates, unmodified columns/CSV mechanics/permission gates.
- **No CSV/attachment delivery** — D1's dashboard-link model is final for this ticket's scope; a future ticket revisiting this would need to build real transport-level attachment support first (named gap, D1).
- **No free-text/external recipients** — D2's org-roster-only model is final; external delivery is OQ-2, deferred to ride on M8-T1's eventual invite infrastructure, not solved here.
- **No organizer-editable subject/body for the scheduled-report notification email** — fixed, code-defined copy only (§5); no sixth entry added to the `EmailDefinition` editor surface.
- **No real org-roster picker/dropdown** — D2's validate-on-submit model is deliberately smaller in scope than a real enumeration UI, which is M8-T1's job once real IAM member listing exists.
- **No changes to `EmailDefinition`, `EmailMessage`'s schema (beyond using its existing free-text `kind` field with a new value), or any of M7-T2's 10 report routes/loaders** — every existing gate, cap, and column spec from M7-T2 is reused completely unmodified.
- **No new audience-segment type, no `EmailDefinitionAudience` enum change** — a `ReportSchedule`'s recipients are a static stored list, not a queried segment (D5).
- **No unlimited catch-up / backlog replay** — `MAX_CATCHUP_PERIODS = 4` is a hard, named ceiling (D4); a schedule paused or broken longer than that permanently and silently forfeits the older missed periods, same accepted-truncation posture M7-T2's D2/§3 already used for its own ceilings.

## Open questions

- **OQ-1 (UX, non-blocking — §1):** dialog vs. dedicated sub-route for the schedule management surface. This spec recommends the dialog (matches M6-T2's Sender settings precedent, matches the topbar button's singular/global nature) but does not mandate it.
- **OQ-2 (product, non-blocking but named for a reason — D2):** should a future ticket support genuinely external (non-org-member) recipients, and if so, through what verification path? This spec's position: route it through M8-T1's real invite/membership infrastructure (even a low-privilege Viewer-only membership scoped to Reports would satisfy the "verified, revocable, auditable" bar D2 sets) rather than a parallel free-text channel — not decided here, flagged for the Orchestrator to weigh once M8-T1 ships.
- **OQ-3 (Backend, blocking implementation, not this spec — D5):** fold report-schedule evaluation into the existing `/api/internal/email-triggers/evaluate` route's per-event fan-out, or stand up a sibling internal route. This spec recommends folding it in (one Cloud Scheduler job, one secret, one rate limit) but leaves the final wiring call to Backend, same posture M6-T3 §8 took toward its own mechanism choice.
- **OQ-4 (product, non-blocking — §4):** is "one schedule per (event, template)" too restrictive for a real organizer workflow (e.g., wanting both a daily internal ops digest and a weekly stakeholder summary of the same report)? This spec's default (deterministic per-template id, D5) can be relaxed to a freely-creatable list later without a breaking migration if this proves true in practice — named, not solved.
- **Carried from M6-T3, still relevant here:** the real-provider question (M6-T1 Q2/OQ-1) — a real transport eventually landing is the actual prerequisite for D1's rejected "attachment" alternative ever becoming buildable at all, since the dev outbox transport that exists today has nowhere to send a real file even if the schema supported one.
