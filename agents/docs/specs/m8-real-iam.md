## Shared decisions

**D1 — Scope: a fixed 4-tier role model only (Owner/Admin/Editor/Viewer). No "permission groups," no per-user manual permission overrides.** `docs/iam-v1-plan.md` (a non-agent-loop planning doc found in the repo, read in full) recommends a richer 3-layer model (role + optional reusable `PermissionGroup` bundles + optional manual overrides, "Recommended v1 Access Model," lines 116–162) and the current mock UI already renders a "Permission groups" card built on that ambition. **This spec deliberately does not build that.** `users.html`, the ticket's own named screen reference, shows nothing but a 4-role table and 3 role-description cards — no groups UI, no manual-override UI. Building groups now would be speculative generality on a ticket whose backlog goal line is explicitly "Owner/Admin/Editor/Viewer," not "a general-purpose permission-bundle engine" (YAGNI, same posture M7-T3's D2 took toward not building a roster picker prematurely). The mock's `permissionGroups` section (`iam-dashboard.tsx` 64–86, 307–356) and `groups` field on member/invite rows are replaced, not extended.

**D2 — Role type: extend `OrganizationMembership.role` / `UserDoc.organizationRole` from `"owner" | "admin" | "member"` to `"owner" | "admin" | "editor" | "viewer"`. Legacy `"member"` is a permanent read-time alias for `"viewer"` — no backfill migration.** Every membership ever written by this codebase (`signupCreateOrgAndUser`, `addAdminUserToOrganization`, `createAdminOrganizationWithOwner`) stamps `"owner"` or `"member"`, never `"admin"` in practice (the `"admin"` value in the union has been reachable in the type system since before M2 but no code path writes it — confirmed by the exhaustive `organizationRole`/`membership.role` grep: only `user-organization.ts`, `adminUserOrganization.ts`, and tests reference it, and every write site literalizes `"owner"` or defaults to `"member"`). Because `"member"` already carries `MEMBER_PERMISSIONS` (the 4 `view:*` strings — see D3), which is exactly the Viewer permission set, treating `role === "member"` as `role === "viewer"` inside `permissionsForOrganizationRole()` (D4) is a correct, zero-cost alias — every existing org/member in the (currently empty-in-production, dev-only) dataset keeps working without a migration script. New writes after this ticket ships always use `"viewer"`, never `"member"`; `"member"` is not removed from the type (removing it would be a breaking change for zero benefit) but is documented as legacy-only.

**D3 — Permission-string matrix: reuse the existing 12 `UserPermission` strings unchanged. No new permission strings are added.** The existing set (`view`/`write` × `events`/`form`/`invoice`/`promotion`/`organization`/`user`) already has exactly the granularity a 4-tier model needs — this is confirmed by mapping every permission string this ticket's own inventory (§6) found actually enforced in code today (`write:events`, `write:form`, `write:promotion`, `write:organization` — four strings, zero others) plus the two currently-unused-but-declared `write:user`/`view:user` strings this ticket newly activates for the member-management routes it adds. The matrix:

| Role | `view:events` | `write:events` | `view:form` | `write:form` | `view:invoice` | `write:invoice` | `view:promotion` | `write:promotion` | `view:organization` | `write:organization` | `view:user` | `write:user` |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| **Owner** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| **Admin** | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| **Editor** | ✓ | ✓ | ✓ | ✓ | ✓ | — | ✓ | ✓ | — | — | — | — |
| **Viewer** | ✓ | — | ✓ | — | ✓ | — | ✓ | — | — | — | — | — |

Owner = `OWNER_PERMISSIONS` unchanged, verbatim reuse (`types/collection.ts` 47–60). Viewer = `MEMBER_PERMISSIONS` unchanged, verbatim reuse (62–67) — this is why D2's legacy-`"member"`-as-`"viewer"` alias is exact, not approximate. **Admin is byte-identical to Owner at the permission-string layer** (D5 explains why, and where the real Owner/Admin distinction actually lives). Editor is new: `["view:events","write:events","view:form","write:form","view:promotion","write:promotion","view:invoice"]` — matches the mock's own card copy exactly ("Build events, forms, emails; can't manage members" → gets `write:events`/`write:form`/`write:promotion`, sees but never mutates invoices, has zero `*:organization`/`*:user`).

**D4 — `permissionsForOrganizationRole()` becomes a 4-way switch; every existing route call site is untouched.** This is the ticket's single lowest-risk, highest-leverage change: because Editor's write-permission set (`write:events`/`write:form`/`write:promotion`) is a superset match of exactly what every M1–M7 route already checks (§6's inventory: every enforced permission string is one of those three, plus the one `write:organization` route), **the ~50 existing route files that call `userDoc.permissions.includes("write:events")` or `resolveRegistrationRouteScope()` need zero code changes to correctly admit Owner/Admin/Editor and correctly reject Viewer**, once `permissionsForOrganizationRole()` (`adminUserOrganization.ts` 47–51) is extended to the 4-way switch in D3's table and every membership-mutating flow (join, invite-accept, role-change) calls it to (re-)stamp `UserDoc.permissions`. This is a deliberate, named consequence — Full-Stack's enforcement sweep is NOT "rewrite 50 routes," it is "extend one function correctly, then verify (not modify) that the 50 routes' existing checks now correctly gate 4 roles instead of 2." The two real code changes the sweep DOES need are named precisely in D6 and §5.

**D5 — Admin vs. Owner (resolves backlog Q7): identical at the permission-string layer (D3); the only real distinction is a role-hierarchy guardrail on the NEW member-management surface this ticket adds, never expressed as a `UserPermission` string.** `users.html` describes Owner as "Full control incl. billing & members" and gives Admin no distinct card at all — the honest reading is that Admin is "does everything an Owner can operationally do" (matches the mock's own second row: Carlos Lalanda, Admin, same full-workspace tone as Petri the Owner) minus the handful of *organizational-survival* actions that must have exactly one authority: minting/demoting other Owners, and removing the organization's last Owner. There is no real billing feature in this codebase today (Q1 in the backlog is still open — payments are simulated), so "billing" in the mock's copy has no concrete backend meaning to gate on; this spec does not invent one. Concretely or (§5, D10): only an **Owner** can (a) invite someone directly as Admin, (b) promote a member to Admin or Owner, (c) demote or remove an Admin or Owner, (d) act on the organization's last-Owner constraint. An **Admin** can do everything else the member-management surface offers (invite/role-change/remove Editor and Viewer members) plus everything Owner can do everywhere else in the app (identical `permissions[]`).

**D6 — Read-tier vs. write-tier gating: `resolveRegistrationRouteScope()` gates every method (including `GET`) on `write:events` uniformly (route-scope.ts 62–68), which is now provably too strict for the Viewer tier `users.html` promises ("Read-only: reports, attendees, responses"). One concrete, named reclassification; every other candidate is explicitly kept as-is with a stated reason, not silently left ambiguous.**
- **Reports "Run"** (`resolveReportsRouteScope`, `requireWriteEvents` defaults `false`) and **Responses list** (`resolveResponsesReadScope`) are **already** view-tier — zero work, already satisfy the Viewer promise for "reports" and "responses."
- **Attendees roster is the one real gap, and it's a provable, already-existing inconsistency, not a hypothetical one:** the SSR page (`src/app/dashboard/(event)/events/[eventId]/attendees/page.tsx`, via `getDashboardScope()`) renders the **first page of the roster to any org member today, permission-check-free** (lines 18, 64). But the "load more" pagination `GET /api/dashboard/events/[eventId]/attendees` (`attendees/route.ts`, whose own header comment 4–6 says "write:events-gated... deliberately stricter than the M3 responses list GET") requires `write:events`. **A future Viewer would see attendees 1–50 fine and then get a 403 clicking "load more."** This spec's decision: reclassify this one route's `GET` to view-tier (org membership only, matching the SSR page it paginates and matching `resolveResponsesReadScope`'s precedent) — implemented by giving `resolveRegistrationRouteScope()` the same `options: { requireWriteEvents?: boolean }` shape `resolveReportsRouteScope()` already has, **defaulting `true`** (so every existing call site is unaffected unless it explicitly opts out), with `attendees/route.ts`'s `GET` the one caller passing `{ requireWriteEvents: false }`.
- **Explicitly NOT reclassified, named so QA doesn't assume a silent broader sweep happened:** `drafts/route.ts` `GET` (abandoned registrations — its own comment says this write:events gate was a deliberate, uniform M5 "every admin surface gates write:events" simplification, not a Viewer-specific call; abandoned/incomplete-registration PII is a step more sensitive than confirmed attendees and re-scoping it needs its own sign-off, not a drive-by in this ticket — OQ-1), `checkin/config/route.ts` `GET` (configuration, not "reports/attendees/responses" content), `emails/definitions|settings|messages` `GET`s (campaign content, not in the Viewer promise list), `promotions/templates/[templateId]/eligible-events` `GET` (template-application tooling). All CSV/export `GET`s (`attendees/export`, `responses/export` ×2, all 5 report `export` routes) correctly **stay** `write:events`-gated — that split is M7-T2's own D1 ("export is a data exit, gated stricter than the on-screen view it exports"), reused unchanged, not revisited here.

**D7 — Invitation is a new, distinct entity and flow — not a reuse of `join-organization-dialog.tsx` / the invite-code-and-link surface.** The existing join surface (D-grounding above) is a **shared-secret, self-serve** mechanism with no per-recipient identity or pre-assigned role; `InvitationDoc` (declared, unused) and `createInvitationSchema` (declared, unused, and its `type: "link"|"code"` variants would just re-implement the already-shipped `Organization.inviteCode`/`inviteLinkToken` fields a second, redundant way) are both superseded by a narrower, email-only shape: an Owner/Admin types one email, picks one role (Admin/Editor/Viewer — **never Owner**, D10), and the system creates exactly one `InvitationDoc` scoped to `(organizationId, email)`.

**D8 — No real email delivery for invites in this ticket. A copy-the-accept-link UX, matching `docs/iam-v1-plan.md`'s own v1 recommendation ("the simplest realistic path is: create invite, show/copy invite link. Email sending can come later," lines 379–384).** Grounded in a real infra gap, not a preference: `sendEventEmail`'s input shape (`send-service.ts` 49–72) requires `eventId`/`eventName` — there is **no org-level (event-less) send path anywhere in this codebase**. Building one is real, non-trivial, out-of-scope infrastructure (the same posture M7-T3's D1 took toward CSV attachments) for a ticket whose backlog goal is the role model + enforcement, not email infra. The invite-creation response returns an opaque accept URL (`/invite/{token}`, mirroring the shape of the existing invite-link token UX) that the inviter copies and sends however they currently communicate with teammates — identical operational pattern to the org-wide invite link already shipped.

**D9 — Self-serve joins (invite code / invite link / domain auto-join) default new members to Viewer, not Editor.** Extends the existing, already-deliberate comment at `adminUserOrganization.ts` 95–98 ("Join flows only ever grant `member`... owner/admin roles are assigned by org-management surfaces (M8-T1), never by a join") to the 4-tier model: an unvetted, shared-secret join is weaker provenance than an Owner/Admin explicitly typing a specific person's email and picking their role, so it lands at the lowest tier. An Owner/Admin can upgrade a self-serve joiner's role afterward via the same role-change action used for anyone else (§5).

**D10 — Owner-scarcity and role-hierarchy guardrails, making `iam-dashboard.tsx`'s own existing hint text (line 300) real:**
- An org can never reach zero Owners. Removing or demoting the organization's **last** Owner is rejected with a typed error, server-side (not just a disabled button) — same "UI-only gating is not a security boundary" posture this codebase has held since the M2 SEC findings.
- An Owner **may** remove or demote **themselves**, but only if at least one other Owner exists after the action (self-service departure without an "ownership transfer" ritual is fine as long as the org survives; departing the *last* Owner slot is not).
- Only an **Owner** may create/promote/demote an Admin, or act on any Owner-role member's row at all (promote-to-owner, demote-an-owner, remove-an-owner). An Admin's role-change/removal/invite actions are capped at Editor/Viewer targets and Editor/Viewer invite-roles — attempting to touch an Owner- or Admin-role member, or to invite/promote someone to Admin, returns `403` for an Admin caller even though Admin otherwise holds every `UserPermission` string an Owner does (D5's whole point: this guardrail is role-hierarchy, not permission-string, and is therefore invisible to every other M1–M7 route's `permissions.includes(...)` check by design).

**D11 — Permission changes take effect on the caller's *next server request*, not "next login."** Justified by how sessions already work here, not invented: every route-scope helper (`resolveRegistrationRouteScope`, `resolveReportsRouteScope`, `resolveResponsesReadScope`, `getDashboardScope`) re-reads `UserDoc` fresh via `getAdminUserByEmail()` on every single request (`route-scope.ts` 44, `get-dashboard-scope.ts` 17) — there is no permission/role claim baked into the Firebase ID token itself (`decodeUser()` only extracts `uid`/`name`/`picture`/`email`, `auth-utils.ts` 34–37) and no server-side session cache that outlives one request (`cache()` in `session.ts`/`get-dashboard-scope.ts` is React's per-request request-memoization, not a cross-request cache). So role/permission changes are correct-by-construction on the very next request with **zero new mechanism required** — a demoted Editor's next `POST` to a `write:events` route is already re-evaluated against the freshly-read `UserDoc.permissions`. The one caveat, named honestly: the client-side SPA state (whatever the dashboard shell holds in memory about "my own permissions" for conditionally rendering buttons) can go stale mid-session until the next navigation/refetch — this is a UX-polish gap, not a security gap, since every mutating action is independently re-checked server-side regardless of what the stale client believes it can do.

**D12 — Multi-tenant isolation for IAM's own data: the existing `organizationId`/roster-verification pattern (`org-membership.ts`) extends cleanly to every new IAM route, with exactly one new piece of infrastructure required — a real member-enumeration index, the gap M7-T3's own D2 named and deferred here (`agents/docs/specs/m7-scheduled-reports.md` lines 17–18).** `UserDoc.organizations[]` is embedded per-user, not reverse-indexed; `UserDoc.organizationId` is the *active* org only and would silently undercount members whose active org is currently elsewhere. Recommended (Backend's implementation call, not mandated here, same posture this loop has taken toward DAL shape choices in every prior spec): a new root collection, deterministic doc id `organizationId + "_" + lowercasedEmail` (matching the `ReportSchedule`/`EmailDefinition` tuple-id convention), written **in the same transaction** as every roster mutation (`addAdminUserToOrganization`, `createAdminOrganizationWithOwner`, and this ticket's new accept/role-change/remove mutations) so it can never drift out of sync with the authoritative embedded roster — listing an org's members becomes a plain `where(organizationId == X)` query (`adminBase.ts`'s existing `findWhere`/`findMany`, no new base-layer code needed). New Firestore index (`organizationId ASC`), new `firestore.rules` deny-all entry (same server-only pattern as `EmailDefinition`/`ReportSchedule`, rules 340–354).

## 1 — Role model & permission matrix

*As an Owner, I want Admin/Editor/Viewer to mean something concrete and consistent everywhere in the app, not just on the Users & Access screen.*

- The 4-tier matrix (D3) is the single source of truth `permissionsForOrganizationRole()` (D4) stamps onto `UserDoc.permissions` on every membership mutation (join, invite-accept, role-change).
- The `Organization Admin`/`Events Manager`/`Forms Manager`/`Read Only` "permission groups" concept from `docs/iam-v1-plan.md` and the current mock is **not built** (D1) — role names on the member table are exactly `Owner`/`Admin`/`Editor`/`Viewer`, matching `users.html`'s badges verbatim (`<span class="badge violet">Owner</span>`, plain `<span class="badge">Admin</span>` etc., lines 45–48).

**Acceptance criteria**
1. `permissionsForOrganizationRole("owner")` and `permissionsForOrganizationRole("admin")` both return all 12 `UserPermission` strings (D3); `("editor")` returns exactly the 7-string Editor set; `("viewer")` and the legacy `("member")` both return the 4-string `MEMBER_PERMISSIONS` set — a table-driven unit test asserts all four (plus the legacy alias) against D3's matrix exactly.
2. Every existing M1–M7 route's `write:events`/`write:form`/`write:promotion`/`write:organization` check correctly **admits** a freshly-seeded Owner, Admin, and Editor fixture and correctly **rejects** (403) a freshly-seeded Viewer fixture — this is the regression proof that D4's "zero route code changes" claim holds; it is a test-suite assertion (Full-Stack/QA), not a route-code change.
3. No `PermissionGroupDoc`, no `groupIds`/`manualPermissions` field is added to `UserDoc` or anywhere else — a deliberate non-goal (D1), verified by its absence.

## 2 — Members list & Users & Access nav visibility

*As any org member (including a Viewer), I want to see who else is on my team — that's useful, low-sensitivity information, not something only Owners should see. As an Owner or Admin, I want to see pending invitations and manage everyone's access from the same screen `users.html` shows.*

- `GET /api/dashboard/iam` (new) returns `{ members: MemberRow[], invitations: InvitationRow[] }`, gated on **org membership only** (any role, mirroring D6's view-tier convention) — a Viewer can see the full roster and who's pending, exactly as an ordinary login already lets any member see the mock today (there is currently zero restriction, so this is at minimum not a regression, and matches `users.html` rendering the table without any role-conditional markup).
- `member.role` change / `member.remove` / `invitation.create` / `invitation.revoke` actions are `write:user`-gated (Admin/Owner only, D3) with the D10 hierarchy guardrails layered on top; a Viewer/Editor sees the roster **read-only** — no action buttons, mirroring how `reports/page.tsx` already computes `canManageSchedules={scope.userDoc.permissions.includes("write:events")}` (line 101) to conditionally show/hide a management affordance. Server-side, every mutating IAM route independently re-checks `write:user` — client-side hiding is UX only, never the security boundary (same posture as everywhere else in this app).
- **Nav visibility:** the "Users & Access" nav item stays visible to **everyone** (matches the roster being view-tier) — `DashboardNavItem` does not need a new permission field for this ticket's scope; the page itself does the gating. (If a future ticket wants per-item nav hiding for a different feature, that's a separate, general mechanism — not invented here for one item.)

**Acceptance criteria**
1. A Viewer fixture calling `GET /api/dashboard/iam` gets `200` with real roster + invitation data, not `403` — proves the roster is genuinely view-tier, not accidentally inherited from a stricter default.
2. A Viewer fixture calling any mutating IAM route (`PATCH`/`DELETE` on a member, `POST`/`DELETE` on an invitation) gets `403` — `write:user` is enforced server-side regardless of what the UI renders.
3. `iam/page.tsx` calls `getDashboardScope()` (or the roster route's server-side equivalent) and renders real data — the zero-gating placeholder (`src/app/dashboard/(workspace)/iam/page.tsx` today) is gone.
4. Cross-org: a member of Org A calling `GET /api/dashboard/iam` sees only Org A's roster/invitations — never Org B's, even via a crafted `organizationId` query param (the route derives org scope from the roster-verified session exactly like every other dashboard route, never from client input).

## 3 — Invitation lifecycle

*As an Owner or Admin, I want to invite a specific teammate by email, assign their role up front, and know at a glance whether they've accepted yet — matching the "Invited" amber badge `users.html` already shows for Marketing/Finance (lines 47–48).*

- **`InvitationDoc` (revised shape, supersedes the unused declaration at `types/collection.ts` 85–99):** `{ organizationId, email (lowercased), role: "admin" | "editor" | "viewer" (never "owner", D10), status: "pending" | "accepted" | "revoked", token, invitedBy (inviter's email, audit), createdAt, updatedAt, expiresAt, acceptedAt?, acceptedBy? }`. **Deterministic doc id** `sha256(["Invitation", organizationId, lowercasedEmail])` — one live invitation per `(org, email)` pair, upsert semantics (same tuple-id convention as `ReportSchedule`, M7-T3 §4).
- **`"expired"` is derived at read/accept time from `expiresAt < now`, never a stored status** — same "derived, not invented" discipline this codebase already applies to abandoned-draft detection (`isAbandoned` computed from `ABANDONED_AFTER_MS`, not a stored flag) and `ReportSchedule`'s dedupe-via-outbox. `INVITATION_EXPIRY_DAYS = 14`, a named, changeable constant (matches the `MAX_CATCHUP_PERIODS`/`MAX_RECIPIENTS_PER_SCHEDULE` naming convention already established in M7-T3).
- **Create (`POST /api/dashboard/iam/invites`):** `write:user` + D10's role-hierarchy guardrail (only Owner may set `role: "admin"`). Server checks, in order: (a) is this email already an **active member** of this org (via a roster lookup) → reject, typed error, zero write, "already a member"; (b) upsert the `(org, email)` `InvitationDoc` — this single upsert step is what naturally solves **re-inviting an already-invited email** (refreshes `role`/`token`/`expiresAt`, no duplicate doc, no separate "resend" endpoint needed) and what makes **inviting someone who's a member of a *different* org** a complete non-issue (invitations are keyed per-org, and `addAdminUserToOrganization` already supports one user holding multiple simultaneous org memberships — no special-case code required, D-grounded in `adminUserOrganization.ts`'s existing `organizations[]`-array-append behavior).
- **Revoke (`POST /api/dashboard/iam/invites/{email}/revoke`):** `write:user` (+ D10 for revoking an Admin-role invite — Owner only), sets `status: "revoked"`; only meaningful against a `"pending"` invitation (a revoke on an already-accepted or already-revoked one is a no-op success, not an error — idempotent, matching this codebase's general idempotency convention).
- **No real email is sent (D8)** — the create response includes the accept URL; the inviter copies/shares it manually, same operational shape as the existing org-wide invite link.

**Acceptance criteria**
1. Inviting `carlos@economist.com` as Admin, then inviting the same email again as Editor, results in exactly **one** `InvitationDoc` for that `(org, email)` pair with `role: "editor"` (the second call wins) — proven by asserting doc count == 1 after two sequential creates, mirroring `ReportSchedule`'s own upsert acceptance-criterion shape (M7-T3 §4 AC-1).
2. Inviting an email that is already an active member of this org is rejected with a typed error and **zero** write to `InvitationDoc`.
3. Inviting an email that is a member of a *different* org succeeds normally — a two-org fixture proves no cross-org leakage or rejection.
4. An Editor or Viewer attempting to create/revoke any invitation gets `403`; an Admin attempting to invite someone as `role: "admin"` gets `403` (D10 — Admin-role invites are Owner-only); an Admin inviting someone as `role: "editor"` or `"viewer"` succeeds.
5. An invitation whose `expiresAt` has passed is treated as expired by the accept flow (§4) without requiring any background sweep/cron to have run — the check is a plain comparison at accept time.
6. Revoking an already-accepted or already-revoked invitation is a `200` no-op, not an error.

## 4 — Accept flow

*As someone who was just invited, I want to click a link, sign in (or sign up, if I'm brand new), and land in the org with exactly the role I was invited at — never a role I could pick myself.*

- **New route, top-level `/api/organizations/`, matching where `join`/`lookup`/`switch` already live (not under `/api/dashboard/`, since the invitee is not yet a member of the target org and dashboard routes assume that):** `POST /api/organizations/invitations/accept`, body `{ token }`, auth via session cookie **or** `Authorization: Bearer <idToken>` (identical dual-auth shape to `POST /api/organizations/join`, `join/route.ts` lines 16–19 — the signup-flow case where the Firebase user exists but no session cookie has been minted yet applies here too).
- **Server validation, in order:** (a) resolve the `InvitationDoc` by token (a token-to-invitation lookup, not by the deterministic `(org,email)` id, since the caller only has the opaque token); (b) `status !== "pending"` or `expiresAt < now` → typed rejection ("This invitation is no longer valid," covers revoked/expired/already-accepted uniformly — no need to distinguish which for the caller); (c) **the authenticated caller's own token email must case-insensitively equal `invitation.email`** — a signed-in user cannot accept someone else's invitation by guessing/leaking a token meant for a different address (this is the one security-critical check in this whole flow: the token proves "an invite to this address exists," the token email match proves "you ARE that address," and only both together authorize the join).
- **On success:** call `addAdminUserToOrganization()` (extended — D7/D9 already established its `role` param needs to accept the invited role, not just default `"member"`/`"viewer"`) with `role: invitation.role`, `joinMethod: "invite_email"` (new value added to `OrganizationMembership.joinMethod`'s existing union), inside the **same transaction** mark the `InvitationDoc` `status: "accepted"` + `acceptedAt`/`acceptedBy`, and (D12) write/update the reverse-index `OrganizationMemberDoc`.
- **New-user case (invitee has no Firebase Auth account yet):** identical to the existing join flow's `profile`-supplied branch (`addAdminUserToOrganization`'s `profile` param, `adminUserOrganization.ts` 99–106, 169–191) — sign up first (creating the Firebase Auth user + no org yet), then accept, exactly mirroring how `join-organization-dialog.tsx`'s "no user yet" branch already redirects to `/signup?code=...` (line 110) before joining. This spec's accept flow reuses that exact pattern with `?inviteToken=...` in place of `?code=...`.

**Acceptance criteria**
1. Accepting a valid, pending, unexpired invitation as the matching authenticated email succeeds, stamps the invited `role` (not a default), and the invitation transitions to `"accepted"`.
2. Accepting with a **different** authenticated email than `invitation.email` is rejected `403`, zero membership write, zero invitation-status change — a two-fixture (Alice's token, Bob's session) IDOR-shaped test proves this explicitly.
3. Accepting an expired invitation is rejected with a typed "no longer valid" error — a time-shifted fixture (`expiresAt` in the past) proves the derived-not-stored check works without any sweep job.
4. Accepting an already-accepted invitation a second time is rejected the same way (status is no longer `"pending"`) — idempotent-safe, no double membership grant, no `memberCount` double-increment.
5. A brand-new user (no Firebase Auth account) can sign up via the invite-token-carrying URL and land as a member with the invited role — regression-tested against the existing signup redirect pattern, not a forked implementation.

## 5 — Role change & removal (implements D10's guardrails as testable behavior)

*As an Owner, I want to promote a trusted Editor to Admin, demote someone who no longer needs write access, or remove someone who's left — without ever being able to accidentally lock myself and everyone else out of the organization.*

- **`PATCH /api/dashboard/iam/members/{email}` `{ role }`** — `write:user`, D10 hierarchy: an Admin caller may only set the target's `role` to `"editor"` or `"viewer"` and may only act on a target whose **current** role is `"editor"` or `"viewer"` (cannot touch an Owner or Admin row at all, in either direction); an Owner caller may set any role on any target, subject to the last-Owner check below.
- **Last-Owner check (applies to both role-change-away-from-owner and removal):** before writing, count the org's current Owners (via the D12 reverse-index query, `where(organizationId==X, role=="owner")`); if the target is the **only** Owner and the action would leave zero, reject with a typed error ("An organization must have at least one Owner") — regardless of whether the caller is demoting/removing themselves or someone else.
- **`DELETE /api/dashboard/iam/members/{email}`** — same `write:user` + D10 hierarchy + last-Owner guardrails. Mechanism: read-modify-write the target's `UserDoc.organizations[]` (filter out the matching entry — **not** a raw `arrayRemove`, since `arrayRemove` needs exact map equality and `joinedAt` timestamps make that unreliable, the same reason `findOrganizationMembership()` already uses predicate matching instead of equality), decrement `Organization.memberCount`, delete the `OrganizationMemberDoc` reverse-index entry — one transaction, mirroring `addAdminUserToOrganization`'s own atomicity discipline.
- **If the removed user's currently-*active* org is the one they were just removed from:** no special re-pointing logic is needed — `resolveActiveOrganizationId()` (`org-membership.ts`) already treats an active `organizationId` with no matching roster entry as "not a member," which is exactly correct post-removal; their very next request simply 403s/redirects like any other stale-active-org case already handled today (D11's "next request" propagation applies identically here).

**Acceptance criteria**
1. An Owner can promote an Editor to Admin and demote an Admin to Editor; both changes take effect on the target's next request (D11) — no re-login required in the test.
2. An Admin attempting to change any member's role to/from `"owner"` or `"admin"`, or attempting to change an Owner's or Admin's row at all, gets `403`.
3. Removing or demoting the organization's sole Owner is rejected with a typed error and zero writes — proven for both the self-removal and other-caller-removal shapes (an Owner cannot demote themselves out of being the last Owner either).
4. An Owner CAN demote/remove themselves when at least one other Owner remains — a two-Owner fixture proves the action succeeds and the acting Owner's own session is unaffected until their next request per D11.
5. Removing a member deletes their `OrganizationMemberDoc` reverse-index row and decrements `Organization.memberCount` atomically with the roster removal — no orphaned index entry, no drifted counter (same class of invariant `addAdminUserToOrganization`'s transaction already protects on the join side).

## 7 — Multi-tenant isolation (implements D12)

**Acceptance criteria**
1. `GET /api/dashboard/iam` for Org A never returns Org B's members or invitations, even when Org B has members with emails alphabetically adjacent to Org A's (rules out an unscoped/prefix-style query bug in the new reverse-index lookup) — two-org fixture, standard IDOR-shaped test matching every prior spec's convention.
2. 4. `firestore.rules` gets new deny-all entries for `Invitation` and the reverse-index collection (matching the `EmailDefinition`/`ReportSchedule` precedent, rules 340–354) — both are server-only, no client-SDK access path exists or is needed.

## 8 — States & edge cases (cross-cutting)

- **Empty (zero members besides self, zero invitations):** unreachable in practice (every org always has at least its Owner), but a fresh org's invitations list renders "No pending invitations" not a blank/broken section.
- **Loading/error:** the IAM screen follows the same skeleton/error/retry conventions every other dashboard surface already uses — no new pattern invented.
- **Re-inviting an already-invited (still-pending) email:** upsert, not duplicate (§3, D-grounded in the deterministic `(org,email)` id).
- **An Owner removing themselves as the org's last Owner:** blocked (D10, §5 AC-3).
- **Inviting someone already an active member of this org:** rejected before any write (§3 AC-2).
- **Inviting someone who's a member of a different org:** succeeds normally, no special handling needed (§3 AC-3).
- **Permission changes for an already-logged-in session:** next-request, not next-login (D11) — explicitly not a "silent no-op until re-login" bug, and not a bug this ticket needs a websocket/push mechanism to fix.
- **A Viewer attempting any mutating IAM or M1–M7 action:** `403` everywhere, uniformly, server-side (§1 AC-2, §6 AC-1).
- **Accepting an invitation with a mismatched authenticated email:** `403`, the one security-critical check in the whole flow (§4 AC-2).
- **Never:** a raw Firestore error, a role change or removal that succeeds client-side but was rejected server-side without a visible error, an Admin able to touch an Owner/Admin-tier row (D10), a permission string this ticket invents that isn't one of the existing 12 (D3), a "Permission groups" UI surface (D1).

**Acceptance criteria**
1. Each named state/edge case above is individually tested, not merely implied by the happy-path tests.
2. Both themes, responsive (320/768/1024/1440) for the members table, invite dialog, and role-change confirmation — same convention as every other dashboard surface, one thorough pass sufficient.
