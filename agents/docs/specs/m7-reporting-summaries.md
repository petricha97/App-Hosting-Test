## Shared decisions

- **"Registered" = `Attendee.status === "accepted"`, not "every completed order" and not `TicketType.registeredCount`.** This is the ticket's central definitional call, made explicit because two other candidate sources exist in the codebase and would give a *different* number:
  - `TicketTypeDoc.registeredCount` is a **capacity-tracking counter**, incremented inside `createAdminOrderWithFinalize` (`src/lib/db/adminOrder.ts`) at the moment a public registration **completes checkout** — which happens when the `FormData` doc is still created at `status: "new"` (M3-T3/M6-T3 §1: `createAdminFormDataForDraft` writes `status:"new"`, review happens after). It exists to enforce sell-out limits, not to answer "who is registered" — it counts submissions still sitting in New/Pending/Reviewed that the organizer hasn't accepted yet, and never decrements if a submission is later left un-accepted indefinitely (M2-T4 AC-9's cancellation path is a stub/TODO).
  - Counting `Order` docs directly has the same problem (an `Order` exists the instant checkout finalizes, independent of approval status) plus it under-counts free/legacy paths that never produced an order (`Attendee.orderId: null`, M5 data model, "legacy flat submissions").
  - `Attendee` is the record M5-T1 designed specifically to mean "a real, organizer-approved registrant" (born only at accept, 1:1 with an accepted `FormData` doc) and is exactly what M6-T3 already standardized on for every audience segment (`accepted-all`, `accepted-paid`, `accepted-invoice` all gate on `Attendee.status === "accepted"` first, §6 of that spec). Reusing that convention here — rather than inventing a third "registered" definition — is a deliberate consistency choice: an organizer reading "Registrations by ticket type" and an organizer reading "Auto · on accept" audience counts should mean the same thing by "registered" everywhere in this product.
  - **Consequence, stated plainly:** a large backlog of pending/reviewed (not-yet-accepted) submissions will show as ticket-type bars *smaller* than what `TicketType.registeredCount` (or a raw Order count) would show. This is correct, not a bug — those registrants are not yet confirmed. `status: "cancelled"` attendees (model-only in M5, no UI cancels anyone today) are excluded from every count in this spec; the field exists for forward-compat and this ticket treats it as "not registered" the moment any cancel UI ships.
- **Money metrics read `Order`, never `Attendee`.** `Attendee` carries no payment fields (by design — payment is `Order`'s domain, M2). Finance figures are computed from `Order.paymentStatus` + `Order.amounts`, independent of whether the underlying submission has been accepted yet (see §2 for why this is the correct, deliberate divergence from the "accepted-only" rule above).
- **Aggregation strategy (the ticket's other central call): Firestore server-side `count()` and `sum()` **aggregate queries**, not full-document reads and not a new distributed-counter system.** This is not "query-time reads with an unbounded read at scale" — it is a third option the ticket description didn't name. Every number on this screen is computed by Firestore counting/summing **index entries** server-side (no documents transferred, billed ~1 read per 1,000 index entries scanned for `count()`; `sum()`/`average()` bill similarly), the same primitive `countAdminAttendeesForEvent` (`src/lib/db/adminAttendee.ts`) and `countAdminEmailMessagesForEvent` (`src/lib/db/adminEmailMessage.ts`, M6-T1) already use in this codebase today. §3 spells out exactly which queries, why none need a new composite index, and the one real scaling axis (query *count*, not document *count*) that does need an explicit ceiling.
- **firebase-admin `^13.6.1` / `firebase` `^12.9.0` (`package.json`) both support `count()`, `sum()`, and `average()` aggregate queries** (Admin SDK since ~v11.3, well below the pinned floor here). No dependency bump required. Grounded by the two existing call sites above, which already prove `count()` works against this project's live Firestore configuration; `sum()`/`average()` are the same API family (`AggregateField`), added by Google in the same release train — Backend Agent should smoke-test the exact `sum()` call shape against a nested field path (`amounts.totalMinor`, §3) during Implement, but this is implementation verification, not a design risk.
- **No chart library exists in this repo and none is needed for this ticket.** `package.json` has no `recharts`/`chart.js`/`visx`/`d3`/`nivo`/etc. — only `framer-motion` (animation, not charting). The prototype's own "Registrations by ticket type" chart (`event-reports.html`) is **plain CSS**: a flex row per ticket type with a `<div>` track and a width-percentage `<div>` fill, no JS charting at all. §6 recommends building it the same way (a small presentational React component, Tailwind-styled bars) rather than introducing a charting dependency for what is a four-to-a-dozen-row horizontal bar list — consistent with YAGNI and the web performance bundle budget (`< 300kb` JS for an app page). This is a recommendation for FS to follow or deviate from with justification, not a hard mandate; if M7-T2's future report outputs need real charting (trend lines, etc.), that is a separate, later evaluation.
- **Permissions diverge from the M5/M6 `write:events` convention on purpose — this is a pure read surface.** Every mutating ticket to date (M1–M6) gates its API routes on session → org membership → `write:events`. M7-T1 ships **zero mutating routes** (no export, no schedule — both are later tickets, §7/Non-goals) and its data (counts and currency-minor-unit sums, no attendee names/emails/order line items) is not PII. Per the backlog's own framing ("Viewer-role read access only") and the already-established M5 L-4 / M6-T2 §7 convention for *read* surfaces (`getDashboardScope()` org-membership check, no permission-tier check beyond that — real Viewer-vs-Editor role enforcement is explicitly deferred to **M8-T1**, "Real IAM"), this screen's server page gates the same way every other read surface in this codebase already does: signed-in session + org membership, nothing more. See §7 for the full statement and why this is *less* restrictive than M5/M6's write surfaces, not an oversight.
- **Currency is per-`Order`, not per-`Event`.** `EventDoc` has no currency field (`src/types/collection.ts`) — currency is pinned per `RegistrationPath` (M3-T1) and stamped onto each `Order` at finalize. An event can legitimately sell the same ticket in USD and GBP simultaneously (M2-T1's own worked example: "same ticket priced in USD/GBP"). Summing `totalMinor` across orders of different currencies as one number would silently produce a meaningless blended figure (M2 §5, Q5: "no currency conversion anywhere" — nothing in this codebase can even convert them to compare). §4 is the currency-handling decision this creates, which the prototype's single `$74,250` mock number does not surface at all (a genuine gap between the mockup and the real multi-currency data model, flagged for UX).

## 1 — Registrations by ticket type (bar chart)

*As an event organizer, I want to see how many people registered under each ticket type, at a glance, so I know which offers are landing and which aren't.*

- **Metric:** for each `TicketType` belonging to the event, the count of `Attendee` docs with `status === "accepted"` and `ticketTypeId` equal to that ticket type's id (Shared decisions). An attendee with `ticketTypeId: null` (legacy flat submission pre-dating M1, or a manual registration that skipped ticket selection — both documented gaps in the M5 data model) is bucketed into a synthetic **"No ticket type"** row, shown last, only when its count is > 0 (never a phantom zero row).
- **Rows:** one per `TicketType` for the event (bounded ≤ `TICKET_TYPE_LIST_LIMIT` = 50, `src/lib/db/adminTicketType.ts`), **including ticket types with zero registrations** (an organizer needs to see "GC super early bird: 0" as much as the ones with high uptake — a chart that only shows non-zero rows hides exactly the "this offer isn't landing" signal the feature exists for). Sorted **descending by count**, ties broken by the ticket type's existing list order (`createdAt` asc, i.e. creation order) for stability.
- **Bar rendering:** width proportional to `count / max(counts across all rows)`, i.e. the largest bar is always 100%-scaled (visually may render at e.g. 90% of the track to leave label room — a UX/FS layout call, not a data one). A non-zero count renders a visually non-trivial minimum bar width (so "1" is still visible next to "97" — exact minimum is a UX call); a zero count renders an empty track with "0" as the value, never a missing/collapsed row. All-zero event (every ticket type has 0 registrations) renders every bar at empty width — not an error state, not the chart's empty state (§5 defines that separately, for zero *ticket types*, not zero *registrations*).
- **Ticket type deleted after registrations exist:** cannot happen in the current data model — M1-T2 AC-11 blocks ticket-type delete while `registeredCount > 0`, and registrations only ever increase that counter (no decrement path ships anywhere through M6). Documented as "currently unreachable," not defended with extra code, so QA doesn't need to fabricate an orphaned-ticketTypeId fixture that the app cannot otherwise produce — the "No ticket type" bucket above already covers the *actual* reachable null-id case.

**Acceptance criteria**
1. An event with 4 ticket types and attendees distributed as in the prototype's mock (97 / 13 / 3 / 1) renders 4 rows, descending by count, each bar's width monotonically increasing with count and the largest row visually dominant.
2. A ticket type with 0 accepted attendees still renders as a labeled row with an empty bar and "0" — never omitted.
3. Non-accepted attendees do not affect any row: seed one `pending`/`reviewed` `FormData` with no `Attendee` doc (not yet accepted) and confirm it contributes 0 to every row (proves the metric reads `Attendee`, not `FormData`/`TicketType.registeredCount`).
4. A `cancelled`-status `Attendee` fixture (model-only, hand-seeded since no UI produces one yet) contributes 0 to its row.
5. Legacy attendees with `ticketTypeId: null` are grouped into one "No ticket type" row at the bottom, present only when count > 0.
6. Zero ticket types for the event → the chart's own empty state (§5), not an empty array silently rendering nothing.
7. The full computation is served by ≤ (ticket type count) Firestore `count()` aggregate calls with **zero full-document reads** of `Attendee` (assert via the test double / a spy on `.get()` vs `.count().get()` — the same test technique already used to characterize `countAdminAttendeesForEvent`, M5 QA precedent).

## 2 — Finance summary card (key-value list)

*As an event organizer, I want to see, at a glance, how much money has actually come in, how much is still owed, how much I've given away for free, and how many discount codes have been used.*

Four values, each independently defined against `OrderDoc` (`src/types/collection.ts`) — **no new payment states, no new order lifecycle, this ticket only reads what M2-T4 already writes**:

| Card row | Definition | Source |
|---|---|---|
| **Paid (card)** | `sum(Order.amounts.totalMinor)` over orders where `paymentStatus === "paid"`. Per the M2-T4 lifecycle (`agents/docs/specs/m2-pricing-commerce.md` §"Lifecycle"), `paymentStatus: "paid"` is reachable **only** via a successful card charge (`invoice` → `outstanding`; `comp`/zero-total → `comped`) — so filtering on `paymentStatus` alone already means "paid by card," matching the prototype's own "(card)" qualifier with no extra `paymentMethod` filter needed. | `Order`, `paymentStatus` |
| **Outstanding (invoice)** | `sum(Order.amounts.totalMinor)` over orders where `paymentStatus === "outstanding"`. Same reasoning: `outstanding` is reachable only via the invoice path. This is the exact same predicate M6-T3 §6 already uses for the `accepted-invoice` audience's `Order` half — reused, not reinvented. | `Order`, `paymentStatus` |
| **Comped value** | `sum(Order.amounts.subtotalMinor)` (**not** `totalMinor`) over orders where `paymentStatus === "comped"`. See the dedicated explanation below — this is the one non-obvious definition on the card and is exactly the kind of ambiguity the backlog flagged. | `Order`, `paymentStatus`, `amounts.subtotalMinor` |
| **Discount codes used** | `count` of the event's `EventPromotion` docs where `usedCount ≥ 1` (distinct codes that have been redeemed at least once — **not** total redemption count, **not** a sum of `usedCount`). Reuses the **already-existing, server-owned `usedCount` counter** (M2-T2, incremented exactly once per successful order finalize, `src/lib/db/adminOrder.ts`) — zero new aggregation, zero new reads of `Order` docs at all for this row. | `EventPromotion` (subcollection of `Event`), `usedCount` |

- **Why "Comped value" sums `subtotalMinor`, not `totalMinor` (the non-obvious call):** a `comped` order's `totalMinor` is **always 0 by construction** (M2-T4 AC-5: "`totalMinor === 0` orders finalize as `comped`") — summing `totalMinor` over comped orders would always show **$0**, which is not what "value" means on this card (the prototype shows a large `$121,000`, larger than the paid total, which only makes sense as *foregone revenue* / the notional worth of what was given away for free). Two distinct paths reach `comped`: (a) a genuinely-free fee (`basePriceMinor: 0`, e.g. "Complimentary delegate" — `subtotalMinor` is also 0 here, correctly contributing $0 "value," since there was never a price to forgo), and (b) a paid fee fully wiped by a 100%-discount promo (`snapshot.discountValue: 100`% — `subtotalMinor` is the fee's real list price, `discountMinor` cancels it, `totalMinor` is 0). Summing `subtotalMinor` captures both correctly: free-by-design tickets contribute their true $0 value, and comp'd-via-100%-discount tickets contribute their real list value — which is the number an organizer actually wants when asking "how much did I give away."
- **Excluded order statuses (explicit, not silent):** `pending` (card charge mid-flight, never settled) and `failed` (declined card) contribute to **none** of the four rows — they represent no completed commercial outcome. This mirrors the M2-T4 lifecycle's own framing ("failed: order kept, counters untouched") and is stated here so QA doesn't misread a seeded `failed` order as a missing dollar somewhere.
- **Currency:** every one of the three money rows is currency-scoped — see §4. "Discount codes used" is currency-agnostic (a plain count).

**Acceptance criteria**
1. The M2-T4 worked-examples fixtures (`agents/docs/specs/m2-pricing-commerce.md`'s 4-row table: plain card → paid, %+tax → paid, fixed+cap → outstanding, partner comp → comped) roll up correctly: row 1+2's totals sum into "Paid," row 3's total into "Outstanding," row 4's `subtotalMinor` (145000, pre-discount) into "Comped value" — not its `totalMinor` (0).
2. A comp order from a genuinely-free fee (`basePriceMinor: 0`, no promo) contributes exactly 0 to "Comped value" (both `subtotalMinor` and `totalMinor` are 0 for this path — proves the metric isn't accidentally right only because of the 100%-discount case).
3. `pending` and `failed` orders (seeded fixtures) contribute to none of the three money rows and are invisible to "Discount codes used" even if they reference a `promotionId` (a failed/pending order never incremented `usedCount` in the first place, per M2-T4 AC-11 — "only this transaction mutates it," and the finalize transaction never completes for these two statuses).
4. "Discount codes used" counts **distinct codes**, not redemptions: a promotion with `usedCount: 6` from six separate orders shows as **1**, not 6, in this row; a second, never-used promotion for the same event contributes 0 and is excluded from the count.
5. Zero orders of any kind for the event → all three money rows render as the zero-amount format (§5), never `NaN`/`undefined`/a crash; "Discount codes used" renders `0`.
6. Money values render formatted in their currency's minor-unit-aware display (existing money-formatting utility from M2, reused verbatim — no new formatter), never raw integer minor units.

## 3 — Aggregation strategy & DAL

**Decision (the backlog's flagged BE concern, scoped by this spec, not fully resolved by it — matching how M6-T3 left its own scheduling-mechanism decision to Backend while fixing the behavioral requirement):**

- **Default and recommendation: Firestore server-side `count()`/`sum()` aggregate queries, computed at page-load time, no new counter infrastructure.** This is deliberately *not* "read every `Attendee`/`Order` doc for the event and reduce in memory" (the query-time approach the backlog worried would degrade at scale) — aggregate queries never transfer documents; Firestore computes the count/sum server-side from index entries and returns one number. This means the approach's cost scales with **index entries scanned** (billed ~1 read/1,000 entries), not with document payload size, and stays cheap and exact from a "dozens of attendees" event up through an event with tens of thousands — well beyond this app's realistic per-event ceiling. The real scaling axis to watch is described below.
- **The actual queries, all equality-filter-only (no new composite indexes needed — this codebase's own established convention, e.g. `countAdminAttendeesForEvent`'s doc comment: "equality-only filters — served by index merging"):**
  1. **Registrations by ticket type (§1):** one new DAL method, e.g. `countAdminAttendeesForEvent` extended with an optional `ticketTypeId` filter (or a sibling `countAdminAttendeesByTicketTypeForEvent`), called once per ticket type: `Attendee` where `eventId ==`, `organizationId ==`, `status == "accepted"`, `ticketTypeId == X`. Run in parallel (`Promise.all`) across the event's ticket types (≤ 50, `TICKET_TYPE_LIST_LIMIT`) plus one more call for the "No ticket type" bucket (`ticketTypeId == null` — Firestore supports equality against `null`). **Query count ceiling: ≤ 51 parallel aggregate calls per page load**, bounded by the existing `TICKET_TYPE_LIST_LIMIT`, not by attendee volume.
  2. **Finance rows (§2):** one new DAL method on `adminOrder.ts`, e.g. `sumAdminOrderTotalsForEvent({ eventId, organizationId, paymentStatus, currency })` using Firestore's `sum('amounts.totalMinor')` aggregate (nested-field path — Backend to confirm the exact dotted-path call shape works against this SDK version during Implement; if it does not, the field-level fallback is denormalizing `totalMinorFlat`/reading `subtotalMinor` as a top-level field is **not** required by this spec unless the nested-path sum genuinely fails, which is not expected). Filters: `eventId ==`, `organizationId ==`, `paymentStatus ==`, `currency ==`. Run once per (status, currency) pair actually in use — §4 bounds this to a small number.
  3. **Discount codes used (§2):** no new aggregate query at all — `getAdminEventPromotionsForEvent` (existing, bounded, small per-event collection) already returns every promotion; count `usedCount >= 1` in memory over that already-bounded list. This is the one row where "read the (small, bounded) docs and reduce in memory" is the right call, precisely because the collection is small by construction (an event realistically has single-digit-to-low-dozens of discount codes, not thousands) — the spec is not dogmatic about aggregate-queries-always, it picks the right tool per data shape.
- **Explicit ceiling / degrade condition (so this isn't an open-ended promise):** the approach above is correct and cheap up to the *existing* per-event bounds this codebase already enforces elsewhere (`TICKET_TYPE_LIST_LIMIT = 50` ticket types, a handful of currencies in practice, `EventPromotion` collections that are naturally small). If a future event needs **more than 50 ticket types**, the registrations-by-ticket-type chart would need more than 50 parallel aggregate calls — at that point, Backend should either raise the ticket-type list bound (a product decision, not this ticket's) or reconsider batching. This is not expected to occur in this product's realistic usage and is documented here only so a future agent doesn't have to re-derive the ceiling from scratch.
- **Counter-based alternative (documented, not adopted — the same posture M6-T3 took toward its own scheduling-mechanism decision):** a distributed-counter pattern (e.g., a denormalized per-`TicketType` "accepted count" field incremented transactionally at accept, alongside the existing `registeredCount` capacity counter; or per-event finance rollup docs incremented at order finalize) would make this screen's reads O(ticket-type-count) *document gets* instead of *aggregate queries* — marginally cheaper per read, but introduces a category of infrastructure that **does not exist anywhere in this codebase today** (M0–M6 are uniformly query-time reads with pagination/aggregate `count()`, never a write-time-maintained business-metric counter beyond the two *capacity* counters `TicketType.registeredCount`/`RegistrationType.registeredCount`, which — per Shared decisions — already mean something different from "accepted"). Introducing one here would mean: (a) a new write path threaded through the accept hook (`onSubmissionAccepted`, already carrying M5/M6-T3 side effects) and the order-finalize transaction, (b) a backfill story for existing events with no counter doc, (c) a new class of "counter drift" bug surface this app has never had to reason about. **Recommendation: do not build this for M7-T1.** Reconsider only if Backend measures real per-event aggregate-query latency or cost that the default approach cannot meet at this product's actual scale — not speculatively.

**Acceptance criteria**
1. No new Firestore composite index is registered for §1/§2's aggregate queries (all equality-only, per the ceiling above) — the one existing exception already in `firestore.indexes.json` (`Order: eventId, organizationId, paymentStatus, createdAt` from M6-T3) is not required by this ticket's own queries (they add no `orderBy`) but continues to serve other callers unaffected.
2. All three query groups (§1 per-ticket-type, §2 per-currency-per-status sums, §2 promotions list) run in parallel (`Promise.all`) at page load, not sequentially — asserted by a timing/call-order test consistent with the pattern the attendees page (`src/app/dashboard/(event)/events/[eventId]/attendees/page.tsx`) already establishes for its own multi-source parallel load.
3. A fixture with 200 accepted attendees across 5 ticket types produces identical results whether computed via the aggregate-query DAL or a brute-force in-memory reduction over every seeded doc (cross-check test, proves the aggregate math is correct, not just "doesn't crash").
4. Zero `.get()` calls that transfer full `Attendee`/`Order` documents occur anywhere in the report page's data-loading path (spy-based assertion, mirroring the existing `countAdminAttendeesForEvent` test technique) — the only full-document reads on this page are the small, already-bounded `TicketType` and `EventPromotion` lists.

## 4 — Currency handling (gap the prototype's mockup doesn't show)

- **Enumerate currencies from the event's `RegistrationPath` docs** (`getAdminRegistrationPathsForEvent`, already bounded, already read by sibling screens) — each path pins exactly one `currency` (M3-T1), so the distinct set of `path.currency` values across the event's paths is the definitive "currencies this event actually sells in." (`Fee.currency` is a viable alternative source and gives the same answer in practice, since every fee is created against a ticket×regType×currency combination that a path's checkout ultimately uses — `RegistrationPath` is preferred here because it's the smaller, more directly "this is what checkout currency options exist" source, and is already read on other event-overview-adjacent screens.)
- **Single-currency event (expected common case, matches the prototype exactly):** exactly one distinct currency → render the finance card precisely as the prototype shows it, three single-line money rows, no currency label/switcher needed.
- **Multi-currency event (real, supported by the data model, not shown in the mockup):** render **one finance card section per currency** (e.g., "USD" and "GBP" each with their own Paid/Outstanding/Comped three-line group), sharing one "Discount codes used" count underneath (that row is currency-agnostic, per §2). This is new layout beyond the prototype's single-currency mock — **flagged explicitly for the UI/UX Designer** to design during the Design step (not decided here beyond "must not silently blend currencies into one wrong number" and "must not crash/omit data for the less-common non-primary currency").
- **Zero `RegistrationPath` docs for the event** (e.g., a very early-stage event with no paths configured yet, or M3-T1 hasn't been reached in that event's setup flow): no currency to enumerate → render the finance card's empty state (§5), not a crash, not a blank card.

**Acceptance criteria**
1. A single-currency event (the common/realistic case) renders identically in shape to the prototype's mock.
2. A two-currency fixture (USD + GBP paths, orders in both) renders two independent, correctly-scoped sets of money rows — a GBP order's `totalMinor` never contributes to the USD "Paid" figure or vice versa (the one behavior this section exists to guarantee).
3. Zero `RegistrationPath` docs → finance card empty state, not a crash.

## 5 — Loading, empty, error states

- **Loading:** skeleton shapes for both cards (bar-row skeletons for the chart, key-value-row skeletons for finance) rendered while the parallel aggregate reads are in flight — same skeleton-on-server-fetch convention as the attendees/emails screens (this page is a Server Component per §7, so "loading" in practice means the Suspense/streaming boundary around the aggregate reads, not a client-side spinner after an API round-trip — FS's implementation call, consistent with how `event-attendees` and `event-emails` pages are already built).
- **Empty — zero ticket types:** chart card shows an explanatory empty state ("No ticket types yet — create one to start tracking registrations", linking to the Tickets screen) instead of an empty chart shell.
- **Empty — zero orders of any kind:** finance card shows all rows at zero (§2 AC-5) — this is a valid, common early-event state, not treated as an "empty state" requiring a different layout (the zero values *are* the answer).
- **Error:** either card's data source failing (a thrown error from the aggregate reads) renders that card's own retryable error panel — same "each card degrades independently, one failure doesn't blank the whole page" pattern the attendees page already uses (`loadError` boolean wrapping a `try/catch` around the parallel `Promise.all`, tabs/cards stay interactive). Given both cards are read at the same page load and likely share one `Promise.all`, Backend/FS should still keep the two cards' error boundaries independent in the UI even if the underlying fetch is combined, so a finance-only Firestore hiccup doesn't blank out the (unrelated) ticket-type chart.
- **Never:** a raw Firestore error, an unhandled promise rejection, a blank hole where a card should be, or `NaN`/`undefined` rendered as a value — every numeric row has a defined zero-state per §1/§2/§4 above.

**Acceptance criteria**
1. Loading skeletons render for both cards independently; both themes; responsive at 320/768/1024/1440.
2. Zero-ticket-types empty state renders with a working link to the Tickets screen; zero-orders state renders zeroed rows, not an empty-state message.
3. A forced failure in the finance-aggregation path leaves the ticket-type chart rendering correctly (independent degradation) and vice versa.
4. No card ever renders `NaN`, `undefined`, or a raw error object as visible text.

## 6 — Chart implementation (recommendation, not a new dependency)

- **No new npm dependency.** Build "Registrations by ticket type" as a small presentational component (e.g., `src/features/reports/components/ticket-type-bar-chart.tsx`) rendering the prototype's own approach: a flex row per ticket type, a track `<div>`, a fill `<div>` whose width is computed from `count / max(counts)` in the component (or precomputed server-side and passed as plain numbers/percentages — implementation detail for FS). This keeps the report screen inside the existing bundle-budget discipline (`< 300kb` JS for an app page, per this project's web performance rules) and matches YAGNI — a four-to-fifty-row horizontal bar list does not need a charting library's interaction/animation/axis machinery.
- **If a future ticket (M7-T2's tabular templates, or a later trend-over-time report) genuinely needs line/area charts, that is a separate, later library evaluation** — this ticket's one chart does not justify introducing one now, and Backend/FS should not pre-emptively add a charting dependency "for reports in general" as part of this ticket's scope.

**Acceptance criteria**
1. `package.json` gains no new charting dependency as part of this ticket.
2. The bar chart component accepts plain `{ label: string; count: number }[]` data (already-aggregated, from §3's DAL calls) — no chart-library-specific data shape leaks into `src/features/reports/`.

## 7 — Permissions & tenancy

- **Server page** (`src/app/dashboard/(event)/events/[eventId]/reports/page.tsx`, new): session → `getDashboardScope()` (org membership) → `getAdminEventForOrganization(eventId, organizationId)` → `notFound()` on null (IDOR-safe, identical shape to every existing event sub-page, e.g. the attendees page read above). **No `write:events` gate** — this is the deliberate divergence from M1–M6's mutating-route convention stated in Shared decisions: M7-T1 has no mutating routes at all, and a report screen showing counts/sums (no attendee names, emails, or line-item detail) is not the kind of surface that should require write access to merely *view*.
- **If any API route is added at all** (e.g., a future client-side "Refresh" affordance rather than a full page reload — not required by this ticket's acceptance criteria, since the Server Component pattern above needs none to satisfy §1/§2), it follows the **same org-membership-only gate**, not `write:events` — consistent with this being a read surface, and it 404s cross-org/unknown `eventId` exactly like every other route in this codebase (IDOR convention unchanged).
- **Real Viewer-vs-Editor role enforcement remains M8-T1's job** (per the M5 L-4 / M6-T2 §7 precedent this spec is following, not inventing): today, "org membership" is the only real gate this codebase enforces anywhere (the `UserPermission` enum in `src/types/collection.ts` exists but per-route granular enforcement beyond that is not yet wired — `src/features/iam/components/iam-dashboard.tsx` is still mock data, backlog M8-T1). This screen joins the same forward-obligation list as the emails/attendees screens' PII surfaces — except, notably, in the *opposite* direction: those screens will eventually need to become *more* restrictive for a true read-only Viewer once M8-T1 lands (hide PII), while this screen's numbers are already safe for any org member to see and are not expected to need further restriction.

**Acceptance criteria**
1. A signed-in user who is a member of the event's organization (any role) can view the reports page and both cards render real data.
2. A signed-in user with no membership in the event's organization gets `notFound()` (404), not a 403 with a leaked page shell — identical behavior to every existing event sub-page.
3. An unknown/cross-org `eventId` 404s (IDOR test, two-org fixture) — zero data about the other org's event leaks in any response.

## 8 — States & edge cases (cross-cutting)

1. **Both themes / responsive:** both cards, all skeleton/empty/error states, styled for light + dark; breakpoints 320/768/1024/1440 verified; the `c2` two-card grid stacks below ~1024px (matches the prototype's own `grid c2` class behavior on other event screens, e.g. M6-T2's confirmation-preview layout).
3. **Money formatting:** every currency value uses the existing minor-unit-aware money formatter from M2 (already used on the Pricing/Fees screens) — no new formatting logic, no float math anywhere in the aggregation path (Firestore `sum()` operates on the stored integer minor units directly).
4. **Attendee accepted but its linked `Order` has since vanished/mismatched (the M5 "denorm source vanished" degradation rule, `Attendee.orderId` no longer resolving):** does not affect §1 (the ticket-type count reads `Attendee.ticketTypeId`, a denormalized field on the `Attendee` doc itself, never re-joins to `Order`) — only §2's finance rows read `Order` directly, and an `Attendee` with a dangling `orderId` simply has no bearing on §2's per-`Order` aggregate queries (which iterate `Order` docs, not `Attendee.orderId` references) — no special-casing needed, noted so QA doesn't invent a test for a coupling that doesn't exist in this design.
5. **Very early-stage event (nothing configured yet):** zero ticket types AND zero registration paths AND zero orders — both cards render their respective empty states (§5 AC-2, §4 AC-3) simultaneously without conflicting or crashing.
6. **Same-org, same-event data seeded by a completely different milestone's tests (e.g., M6-T3's `unpaid-offsets` fixtures)** — this ticket's aggregate queries must not accidentally pick up cross-event data seeded under a different `eventId` in the same test run (standard tenancy discipline, restated here because reporting aggregates are exactly the kind of query where an accidental missing `eventId ==` filter silently produces a wrong-but-plausible-looking number instead of an obvious crash).

## Non-goals for T1 (explicit)

- **No report templates library** (Registration overview / Order & transaction details / Abandoned registration details / Badges printed / Email overview, with Run → tabular output → CSV export) — that is the bottom half of `event-reports.html` and is **M7-T2** in full.
- **No CSV export of anything** — the prototype's topbar "Export table" button is **M7-T2** scope (it exports the *templates* table's tabular output, not these two summary cards, which have no natural "export" shape as key-values/a bar chart).
- **No scheduled report delivery** — the prototype's topbar "Schedule" button is **M7-T3**.
- **No new payment/order state machine changes** — every finance metric reads `OrderDoc.paymentStatus`/`amounts` exactly as M2-T4 already writes them; no new status, no new field, no `dueDate`, no "mark paid" transition (that gap is separately named in M6-T3 §4 and stays open here too — unpaid orders that never get marked paid remain `outstanding` forever, and this ticket's "Outstanding" figure will correctly reflect that indefinitely; not this ticket's problem to solve).
- **No workspace-level (cross-event) aggregates** — `src/features/dashboard/mock-data.ts`'s org-wide metrics are **M8-T2**, which explicitly depends on this ticket's per-event aggregate patterns but is a separate ticket, separate screen (`index.html`), separate DAL surface (org-scoped, not event-scoped).
- **No real-time/live-updating cards** (no `onSnapshot` listeners) — this is a server-rendered summary, refreshed on page load/reload, consistent with every other admin screen in this codebase (none use live listeners).
- **No distributed-counter infrastructure** (§3) — explicitly deferred, not silently built.
