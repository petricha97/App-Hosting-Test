## Shared decisions

**D1 — `src/features/dashboard/mock-data.ts` and its 4 backing types are deleted outright, not "replaced."** Nothing imports them (grounding, exhaustive grep). The real edit surface is `organization-event-overview.tsx`'s own inline stat-card/quick-action arrays (lines 60–98, 112–152), which is where the prototype-vs-code divergence actually lives.

**D2 — Aggregation strategy splits by collection, driven by which collections have a real `organizationId` field (grounding):**
- **Draft/Published event counts:** compute in-memory from the event list `getAdminEventsForOrganization()` already returns to this page today (no new DAL method, no new Firestore query) — the page needs that full list anyway for D6's "quick actions point at the org's most-recent event," so this is not an incremental read, it's the same one read already happening, just also counted. This deliberately does **not** attempt a `count()` aggregate against `Event` for two reasons: (a) `Event` has no direct `organizationId` to filter on (only 5-way `organizationPath`), so an aggregate `count()` would need a `where("organizationPath", "in", candidates)` clause whose automatic-indexing behavior with a simultaneous `status ==` equality filter is unproven in this codebase (no existing precedent query combines `in` with another equality field on `Event`; the one registered `Event` index, `firestore.indexes.json` lines 79–86, is `status ASC, updatedAt DESC` only, with no `organizationPath`/`organizationId` field at all); (b) this product's realistic per-org event count is small (same "no defended-against scale ceiling exists anywhere for an org's event count" as `getAdminEventsForOrganization`'s own unbounded read today), so the incremental cost of counting an already-fetched list in memory is zero. If a future ticket needs `Event` to scale past what an unbounded per-org read can bear, that ticket should also backfill a real `organizationId` field onto `EventDoc` — a bigger, separate migration this spec does not attempt.
- **Registrations, Revenue:** NEW org-scoped Firestore aggregate DAL methods, direct `where("organizationId","==",X)` queries against `Attendee`/`Order` — one call each (plus one-per-currency for Revenue, D5) — no per-event fan-out (§4).

**D3 — "Registrations" reuses M7-T1's "Registered" definition verbatim, at org scope instead of event scope: `Attendee.status === "accepted"`, counted across every event the organization owns regardless of that event's current Draft/Published status.** Grounded in M7-T1's own central definitional call (`m7-reporting-summaries.md` lines 7–11: "`Attendee` is the record M5-T1 designed specifically to mean 'a real, organizer-approved registrant'"), generalized here by dropping the `eventId` filter, not by inventing a second, different "registered" concept. A `cancelled`-status `Attendee` (model-only, no cancel UI ships anywhere through M8-T1) contributes 0, same as the per-event chart. An event later being un-published (moved back to Draft, if that ever becomes possible) does not retroactively remove its historical registrations from the org total — the metric reads `Attendee` docs directly, never joins back through the owning `Event`'s current `status`.

**D4 — "Revenue (paid)" reuses M7-T1's "Paid (card)" row definition verbatim, at org scope: `sum(Order.amounts.totalMinor)` where `paymentStatus === "paid"`, across every event.** Deliberately does **not** fold in "Outstanding" or "Comped value" (the per-event Finance card's other 2 rows) — the prototype's workspace stat card shows exactly one dollar figure, "Revenue (paid)" (`index.html` line 48), not a 3-row breakdown; a single glance-level number is the right scope for a workspace stat card (YAGNI — a full org-wide finance breakdown, if ever wanted, is a different, bigger surface than 4 stat cards and not this ticket's job). `pending`/`failed` orders contribute nothing (same M7-T1 §2 exclusion, unchanged).

**D5 — Currency at org scope: enumerate distinct currencies from the org's `RegistrationPath` docs org-wide (new DAL method, no `eventId` filter), generalizing M7-T1 §4's exact per-event approach.** `RegistrationPath.organizationId` is a real, direct field (grounding) — `where("organizationId","==",X)`, no `orderBy` needed for enumeration purposes (a plain equality filter needs no composite index, single-field auto-index covers it unconditionally). Rendering:
  - **Single-currency org (expected common case, matches the prototype exactly):** one `$` stat card, `formatMoney(paidMinor, currency)`, identical shape to the prototype's `$74,250`.
  - **Multi-currency org (real, not shown in the mockup, same class of gap M7-T1 §4 flagged for its own screen):** the stat card is a single tile, not a multi-section card like the per-event Finance card has room for — render the **primary currency's total** (the currency with the most `RegistrationPath` docs org-wide; ties broken alphabetically for determinism) as the headline figure, with the other currencies' totals as a small secondary line/tooltip (exact visual treatment is UX's call, same posture as M7-T1's own OQ-1 — flagged, not decided here beyond "must not silently blend currencies into one wrong number").
  - **Zero `RegistrationPath` docs anywhere in the org** (brand-new org, or an org whose events haven't reached M3-T1 setup yet): no currency to format against — render the literal string `"$0"` (a static zero-value literal, same convention the other 3 stat cards already use for their zero-padded `"00"` values, not a `formatMoney()` call against a fabricated currency). This is always mathematically correct: zero registration paths means zero fees means zero possible orders, so the true paid total is unconditionally 0 regardless of which currency it would have been in.

**D6 — Quick actions deep-link into "the organization's most relevant event," defined as the first element of `getAdminEventsForOrganization()`'s result** (already sorted by `sortEventsByUpdatedAt`, i.e., most-recently-updated event first — `adminEvent.ts` 53, `event/utils.ts` 147–164) — reused, not reimplemented. This resolves the ambiguity the prototype's static single-event mock (`"Open 'General Counsel Summit'"`) leaves unstated for a real multi-event workspace: **most-recently-updated, not most-recently-created, not "the one Published event"** (an organizer actively shaping a brand-new draft event should see quick actions point at *that* event, not an older published one they've stopped touching). **Zero-events org:** quick actions collapse to a single "Create your first event" CTA → `/dashboard/events/new` — this is already exactly what the live empty-state code does today (`organization-event-overview.tsx` lines 216–219 for the event list, `DashboardEmptyState` primary action lines 257–260) and needs no new mechanism, just needs the *non-empty* case's quick actions to become event-scoped links (they are workspace-generic today, per grounding).

**D7 — The prototype's "Setup notes" card stays a static, non-interactive feature-availability list — it is explicitly NOT M8-T3's per-event, stateful, 6-item readiness checklist, and this ticket does not build that mechanism.** `BACKLOG.md` line 512 (M8-T3) describes a real, dynamic, per-event "readiness checklist" ("each lights a checklist item") — a genuinely different, event-scoped feature this ticket's own backlog line (504–509) does not ask for and should not accidentally half-build. The backlog goal line's "wire quick-actions/checklist deep links to the now-real sub-screens" is read here as applying its "deep links" clause to **Quick actions** (the only card the prototype actually gives `<a href>` elements, `index.html` 56–60) — "Setup notes" in the prototype has zero links (grounding) and stays that way. The only change this ticket makes to that card is refreshing its copy to describe the real, now-shipped M1–M7 feature set (ticket types, pricing & discount codes, registration types & paths, lifecycle email engine, check-in/QR, reports — matching the prototype's own updated copy, `index.html` lines 62–68) instead of the stale pre-M1 scaffold copy the live code still shows.

**D8 — No trend/delta sub-labels ("▲ 12 this week", "▲ vs early-bird," `index.html` lines 47–48) for T2.** A genuine "registrations in the last 7 days" figure needs a NEW range-filtered aggregate query (`organizationId ==`, `status ==`, `createdAt >= sevenDaysAgo`) — unlike every other query this spec proposes, this one combines an equality filter with an **inequality/range** filter on a *different* field, which Firestore's automatic equality-only index merging does not cover; it needs a real, new composite index (`Attendee: organizationId ASC, status ASC, createdAt ASC` — no existing index has this shape; every registered `Attendee` index today is `eventId`-first, `firestore.indexes.json` lines 4–31). **Default/recommendation: ship the 4 stat cards without a delta sub-label for T2** — plain value + a static hint line (reusing the existing `DashboardSummaryCard.hint` / inline-card `hint` field pattern already in `organization-event-overview.tsx`), same posture M7-T1's own D3 took toward not building distributed-counter infrastructure speculatively. A real trend feature, if wanted later, is a separate, explicitly-scoped future ticket that adds the named index deliberately — not something this ticket silently builds or silently promises and drops.

**D9 — Permissions: unchanged from today — org-membership-only gate (`getDashboardScope()`), no `write:events`/`write:user` check, same read-tier posture M7-T1 §7 already established and M8-T1 (real IAM, shipped) is fully compatible with.** A Viewer sees identical stat cards/quick actions/setup notes to every other role — this page shows counts and a revenue figure, no PII, and is not more sensitive than the per-event Reports page M7-T1 already exposed to Viewers without restriction. Quick actions deep-link into event sub-screens whose own mutating routes remain independently `write:events`/`write:user`-gated exactly as before (M8-T1's enforcement sweep already covers every one of those routes) — a Viewer clicking "Add ticket types" lands on a real, viewable-but-not-mutable page, unaffected by this ticket.

**D10 — New `loading.tsx` for the `(workspace)` route group, matching the reports page's exact convention.** `src/app/dashboard/(workspace)/loading.tsx` (new) composes skeleton versions of the 4 stat cards + Quick actions/Setup notes card shells, same pattern as `src/app/dashboard/(event)/events/[eventId]/reports/loading.tsx` (header skeleton + per-card `*Skeleton` exports). This closes a real, pre-existing gap (no loading state exists for this route today) that becomes more visible once the page performs genuine aggregate Firestore reads instead of just the one already-fast event-list read.

## 1 — Stat cards (Draft events / Published events / Registrations / Revenue)

*As an organizer, I want to see at a glance how many events I have in progress, how many are live, how many people have registered, and how much revenue has come in — across my whole workspace, not just one event.*

- Exactly 4 cards, in the prototype's order (`index.html` 44–49): **Draft Events**, **Published Events**, **Registrations**, **Revenue (paid)**. The current code's "Total events" and "Active forms" cards are **removed** — neither exists in the prototype, and "Active forms" has never had a real data source (grounding: hardcoded `"TBD"`/`"00"`).
- **Draft Events / Published Events:** `events.filter(e => e.status === "Draft"/"Published").length` over the same `getAdminEventsForOrganization()` result the page already loads (D2) — this is an unchanged computation, already correct in the live code (`organization-event-overview.tsx` 38–39), just needs its own card slot restored to match the prototype instead of being joined by "Total events."
- **Registrations:** one new org-scoped `count()` aggregate call (D3, §4).
- **Revenue (paid):** one-per-currency new org-scoped `sum()` aggregate call(s) (D4/D5, §4).
- Zero-padded 2-digit display for the two event counts (`String(n).padStart(2, "0")`, matching the existing convention both in `mock-data.ts`'s dead code and the live inline card array) — Registrations and Revenue are **not** zero-padded (a registration count or dollar figure padded to 2 digits reads oddly past 99; use plain `String(n)` / `formatMoney(...)`).

**Acceptance criteria**
1. A fixture org with 3 events (2 Draft, 1 Published) renders "Draft Events: 02", "Published Events: 01" — unchanged from the already-correct existing computation, now in the prototype's card order/labels.
2. A fixture org with 40 accepted `Attendee` docs across 3 different events (of any status mix) renders "Registrations: 40" — proves the metric is org-wide, not scoped to one event, and not double-filtered by event status.
3. Non-`"accepted"` `Attendee` fixtures (a `pending`/`reviewed` `FormData` with no `Attendee` doc yet, and a hand-seeded `"cancelled"`-status `Attendee`) contribute 0 to Registrations — same proof shape as M7-T1 §1 AC-3/AC-4, generalized to org scope.
4. A fixture org with `paid` orders totaling 50000 minor units in USD across 2 events renders "Revenue (paid): $500.00" — proves the sum is org-wide, not per-event.
5. `pending`/`failed`/`outstanding`/`comped` orders contribute 0 to Revenue — same exclusion as M7-T1 §2 AC-3, generalized (only `paid` counts here, and even `outstanding`/`comped` — which the per-event Finance card *does* show — are correctly excluded from this single-figure workspace stat, per D4).
6. A brand-new org (zero events, zero everything) renders "Draft Events: 00", "Published Events: 00", "Registrations: 0", "Revenue (paid): $0" — no crash, no `NaN`, no `undefined` (D5's zero-currency literal).
7. No stat card ever renders a raw Firestore error, `NaN`, `undefined`, or the literal string `"TBD"` (closing the current, real defect).

## 4 — Aggregation strategy & new DAL surface

**New DAL additions (Backend's exact naming call, per this loop's established convention — signatures below are the recommendation, not a mandate):**

1. **`src/lib/db/adminAttendee.ts` — `countAdminAttendeesForOrganization(input: { organizationId: string; status?: AttendeeStatus }): Promise<number>`.** Mirrors `countAdminAttendeesForEvent` (275–298) exactly, minus the (here, absent) `eventId`/`checkInState`/`ticketTypeId` filters this ticket doesn't need — a single `where("organizationId","==",X)` [+ optional `where("status","==","accepted")`] `.count()` aggregate call. Two equality filters, no `orderBy` — same "equality-only, index-merge-servable" class of query M7-T1 already used and had Backend empirically confirm against a live emulator (`m7-reporting-summaries.md` line 13); **this exact shape (org-only, no event) has not itself been run against a live emulator yet** — Backend should do the same empirical confirmation pass during Implement rather than this spec asserting it as already-proven (the mechanism generalizes, but "generalizes" and "confirmed" are different claims, per this loop's own discipline).
2. **`src/lib/db/adminOrder.ts` — `sumAdminOrderTotalsForOrganization(input: { organizationId: string; paymentStatus: PaymentStatus; currency: Currency; field: OrderAmountSumField }): Promise<number>`.** Mirrors `sumAdminOrderTotalsForEvent` (246–262) exactly, minus `eventId`. Same "confirm empirically, don't assume" note as above applies to the org-only 3-equality-filter shape (`organizationId`, `paymentStatus`, `currency`).
3. **`src/lib/db/adminRegistrationPath.ts` — `getAdminRegistrationPathsForOrganization(input: { organizationId: string; limit?: number }): Promise<WithId<RegistrationPathDoc>[]>`.** Mirrors `getAdminRegistrationPathsForEvent` (53–69) minus `eventId` and minus the `orderBy("sortOrder")` (org-wide enumeration doesn't need per-event ordering) — a single `where("organizationId","==",X)` list read, bounded by a safety-limit constant (e.g. `ORGANIZATION_REGISTRATION_PATH_LIST_LIMIT`, suggest 200 — an org's total path count across all its events is small by construction, same reasoning M7-T1 §3 applied to `EventPromotion`). Used only to enumerate D5's distinct currencies, never to render a table.
4. **No new method needed for draft/published event counts** (D2) — computed in-memory over the already-loaded `getAdminEventsForOrganization()` result.

**Orchestration:** a new `src/features/dashboard/server/load-workspace-summary.ts` (mirroring `src/features/reports/server/load-finance-summary.ts`'s shape — zero direct Firestore calls, only calls the DAL methods above and shapes results), fanning the 3 new aggregate primitives out via `Promise.all`/`Promise.allSettled` (§6 specs the exact settled/error split), called from `src/app/dashboard/(workspace)/page.tsx` alongside the existing `getAdminEventsForOrganization()` call.

**Acceptance criteria**
1. No new Firestore composite index is required by any of the 3 new query shapes above, **or**, if Backend's empirical emulator check during Implement finds one IS required for any of them, that finding is documented in `agents/docs/data-models/m8-dashboard-metrics.md` (same convention M7-T1 used for its own OQ-2 resolution) rather than silently worked around.
2. A fixture with 200 accepted `Attendee` docs spread across 6 events in one org produces an identical Registrations count whether computed via the new aggregate DAL call or a brute-force in-memory reduction over every seeded doc (cross-check test, same convention as M7-T1 §3 AC-3).

## 6 — Loading, empty, error states

- **Loading:** new `src/app/dashboard/(workspace)/loading.tsx` (D10) — skeleton stat cards (4) + Quick actions/Setup notes card shells, matching the reports page's `loading.tsx` composition pattern exactly (route-level Suspense boundary around the Server Component's data fetch, not a client spinner).
- **Whole-page load failure** (`getDashboardScope()` or the initial `getAdminEventsForOrganization()` call itself throws): a new `WorkspaceLoadError` component, same shape as `ReportsLoadError` (page-level retry panel, `router.refresh()` on retry) — this failure mode blocks the whole page since even the event-derived stat cards and quick actions need that read to succeed.
- **Independent per-stat-card degradation:** once the event list is loaded successfully, the 2 new aggregate reads (Registrations, Revenue) run inside their own `Promise.allSettled` (mirroring `reports/page.tsx` lines 76–94) — a Firestore hiccup scoped to the Attendee or Order aggregate query renders **that one stat card's** own small inline error/retry affordance (a smaller-scoped version of `EntityTableError`, or a simple "—" with a retry link — UX's call on exact treatment) without blanking Draft Events/Published Events/Quick actions/Setup notes, all of which only depend on the already-succeeded event list.
- **Empty — zero events:** Draft/Published render `00`, Registrations renders `0`, Revenue renders `$0` (§1 AC-6), Quick actions collapse to the single CTA (§2 AC-3), Setup notes render unchanged (static, D7) — this is a valid, common brand-new-org state, not an error.
- **Never:** a raw Firestore error, an unhandled promise rejection, `NaN`/`undefined` rendered as a stat value, the literal `"TBD"` (closing the current real defect named in grounding).

**Acceptance criteria**
1. Loading skeletons render for the stat-card row and the two lower cards; both themes; responsive at 320/768/1024/1440.
2. A forced failure in the Registrations aggregate path leaves Revenue, the two event-derived counts, Quick actions, and Setup notes all rendering correctly (independent degradation) — and vice versa for a forced Revenue-path failure.
3. A forced failure in the initial `getAdminEventsForOrganization()` read (or `getDashboardScope()`) renders the whole-page `WorkspaceLoadError` retry panel, not a partially-broken page.
4. No card ever renders `NaN`, `undefined`, a raw error object, or the literal string `"TBD"` as visible text.

## 8 — States & edge cases (cross-cutting)

1. **Both themes / responsive:** stat-card row, Quick actions, Setup notes, all loading/empty/error states, styled for light + dark; breakpoints 320/768/1024/1440.
