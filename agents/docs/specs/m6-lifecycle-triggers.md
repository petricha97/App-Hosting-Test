# M6-T3 — Lifecycle triggers & audience segmentation

Research Lead, 2026-07-15. Builds directly on `agents/docs/specs/m6-emails-admin.md` (M6-T2, shipped) and its data model (`agents/docs/data-models/m6-emails-admin.md`, `agents/docs/data-models/m6-email-infrastructure.md`). **This ticket invents no new trigger types, audiences, or UI surfaces.** `EmailDefinition.trigger`/`.audience` (six audiences, six trigger types) are the exact, already-stored taxonomy this spec evaluates. T2 shipped every UI affordance this ticket lights up: `src/features/emails/components/trigger-cell.tsx`'s "Automation arrives with M6-T3" tooltip, `src/features/attendees/components/abandoned-tab.tsx`'s disabled "Email all" button, and `src/lib/email/send-service.ts`'s `sendEventEmailBatch` ("T3's 'Email all' substrate", per its own header comment). Screen references are therefore inherited from T2 (`prototype/prototype/event-emails.html`) and M5-T3 (`prototype/prototype/event-attendees.html`, Abandoned tab) — no new mockup exists for a "trigger engine" because there is no new screen.

## Shared decisions

- **Two evaluation modes, cleanly split by trigger type.** `on-submit` and `on-accept` are **real-time, single-recipient, event-driven** — evaluated synchronously inline in the existing request that creates/accepts the submission, for exactly the one person involved. `abandoned-24h`, `unpaid-offsets`, and `scheduled` are **periodic, multi-recipient, segment-driven** — evaluated by a recurring job that queries an audience and enqueues zero or more sends. `manual` is **never auto-evaluated** by this engine at all (by definition); its only automated wiring in scope is M5-T3's "Email all" button (§7), which reuses the `abandoned-reminder` definition's exact dedupe scheme rather than inventing a parallel one.
- **Trigger-type ↔ eligible kind is fixed and closed.** Per T2's editability rules, `on-submit`/`on-accept`/`abandoned-24h`/`unpaid-offsets` are **locked trigger types on system definitions only** — no custom definition can ever use them (OQ-1 default: custom definitions are `manual | scheduled` only). Concretely: `on-submit` only ever fires for `approval-pending`; `on-accept` only ever fires for `confirmation-paid`/`confirmation-payment-due`; `abandoned-24h` only ever fires for `abandoned-reminder`; `unpaid-offsets` only ever fires for `payment-reminder`. **`scheduled` is the one trigger type both system kinds (`one-week-to-go`, `qr-ready`) and organizer-created custom definitions can use**, and it is the only trigger type whose audience is not hard-pinned — §4/§5 are written generically for exactly this reason.
- **The `enabled` forward obligation (T2 §8-2) is honored explicitly everywhere in this spec:** every firing path — real-time hook and periodic sweep alike — re-reads the definition's current `enabled` state immediately before enqueueing, never from a value cached earlier in the request/tick. §6 states the exact re-check granularity for batched periodic sends.
- **Dedupe is derived, not invented per-send:** every trigger type gets one deterministic `dedupeKey` formula (§6 table) built from ids that already exist in the data model (`submissionId`, `attendeeId`, `draftId`, `orderId`, `definitionId`) — no new "already sent" marker collection. `createAdminEmailMessageIfAbsent`'s existing create-if-absent transaction (T1) is the entire safety mechanism; this spec's job is only to make the `dedupeKey` formula stable and correct.
- **Scheduling mechanism is explicitly out of this document's authority.** Firebase App Hosting runs on Cloud Run under the hood and has **no built-in cron** (confirmed: `apphosting.yaml` has no scheduler config today). §8 lists the realistic options with tradeoffs as an **open question for the Backend Agent to resolve during Design/Implement** — this spec fixes only the *behavioral* requirement (what must be evaluated, how often, how stale is acceptable), never the mechanism.
- **`all-invitees` is a documented no-op segment (decision, §5).** No Invitee/contact-list entity exists anywhere in this codebase — the segment has no query definition and evaluates to zero recipients in the auto-trigger engine. This only matters for a hypothetical custom **scheduled** definition that picks `all-invitees` as its audience (the `invitation` system kind is `manual`-only and is never auto-evaluated regardless).
- **On-accept's paid-vs-invoice discriminator (decision, needed because none was written down in T2):** `accepted-paid` = `Order.paymentStatus ∈ {"paid", "comped"}`; `accepted-invoice` = `Order.paymentStatus === "outstanding"`. Comp orders are money-settled (zero balance), so they get the "paid" confirmation, not a payment-due one — this is the only sane reading of the two confirmation templates' copy ("An invoice … is on its way" would be false for a comp). A submission with `orderId: null` (legacy flat/manual-registration edge, no order exists) defaults to `accepted-paid` (fewer false "payment due" nudges than the alternative) — documented, not exercised by any current flow that creates such a submission through accept.

## 1 — Real-time trigger: `on-submit` (`approval-pending`)

*As an event organizer, I want the "Approval pending" email to go out the moment someone submits, so registrants aren't left wondering whether their submission arrived.*

- **Exact firing condition:** a new `FormData` document is created with `status: "new"`. This happens at exactly two DAL call sites today: `createAdminFormDataForDraft` (stepper flow, called from `POST /api/events/[eventId]/registration/finalize`, `src/app/api/events/[eventId]/registration/finalize/route.ts`) and `createAdminFormData` (legacy flat flow, called from `POST /api/events/[eventId]/register`, `src/app/api/events/[eventId]/register/route.ts`). **`on-submit` does NOT fire** for the admin manual-registration route (`src/app/api/dashboard/events/[eventId]/attendees/register/route.ts`) — that route creates `FormData` directly at `status: "accepted"` on comp/invoice paths (M5-T2 AC-4), skipping "new" entirely; a staff-entered registrant never needs an "under review" email.
- **Idempotency at the hook, not just the dedupeKey:** `createAdminFormDataForDraft` is already create-if-absent (a crash-replay returns `created: false`). The hook must fire **only when `created === true`** — a replayed finalize call (same draft, same idempotency key, e.g. a retried request after a network blip) must not re-fire the email even before the dedupeKey math runs. `createAdminFormData` (legacy) has no replay path (each POST mints a fresh doc), so this guard is a no-op there but costs nothing to apply uniformly.
- **Single recipient, no segment query:** the recipient is the one submission that was just created — `submission.email` (or the equivalent submission-map key) from the doc just written. `audience: "pending-approval"` on the `approval-pending` catalog entry is documentation only here (a segment field never queried for this trigger type — see Shared decisions).
- **`enabled` check:** read `approval-pending`'s current `EmailDefinition` (merged stored-or-virtual per T2) at the moment of firing; if `enabled === false`, skip — no row, no error.
- **`dedupeKey = submissionId`** (the `FormData` doc id — deterministic from the draft for the stepper flow, a fresh id for the legacy flow). One submission → at most one `approval-pending` email, ever, regardless of how many times the creating request is retried or how many times a hypothetical future re-evaluation sweep looks at old submissions (none is specified — this trigger has no periodic component).

**Acceptance criteria**
1. Completing the stepper (or the legacy flat form) creates exactly one `EmailMessage` row (`kind: "approval-pending"`, `dedupeKey: submissionId`) when the definition is enabled; a network-retried finalize call (same draft, same idempotency key) produces zero additional rows (`createAdminFormDataForDraft` returns `created:false`, hook does not run).
2. Manual admin registration (comp/invoice path) creates zero `approval-pending` rows — asserted directly against `attendees/register/route.ts`'s FormData-at-`accepted` path.
3. Disabling `approval-pending` before a submission and re-enabling it after produces zero email for that submission — the definition's `enabled` is read fresh at hook time, not cached from page-load.
4. A submission whose `email` submission-map key is blank/absent produces a typed `INVALID_RECIPIENT` rejection from `sendEventEmail` — zero outbox row, zero crash, zero effect on the FormData write that already committed.
5. Two submissions from the same browser/session (distinct drafts, distinct `submissionId`s) each get their own row — dedupeKey is per-submission, never per-visitor/per-email.

## 2 — Real-time trigger: `on-accept` (`confirmation-paid` / `confirmation-payment-due`)

*As an event organizer, I want the right confirmation email — paid or payment-due — to go out the instant a registration is accepted, exactly once.*

- **Exact firing condition:** a `FormData` document transitions to `status: "accepted"` via `transitionAdminFormDataStatus` (`src/lib/db/adminFormData.ts`). That function already calls the accept-side-effect hook (`onSubmissionAccepted`, `src/features/responses/on-submission-accepted.ts`) **after the accept transaction commits, at most once per submission** — `"accepted"` is terminal in the forward-only status machine (M3-T4), so a second accept attempt fails `INVALID_TRANSITION` before the hook is ever reachable again. **`on-accept` email evaluation is new logic added at this exact call site** (either inside `onSubmissionAccepted` itself, after step 3's `createAdminAttendeeIfAbsent`, or as a sibling step `transitionAdminFormDataStatus` invokes alongside it — Backend/Full-Stack's implementation choice; the behavioral requirement is "runs in the same at-most-once envelope the Attendee-creation hook already has").
- **Kind selection (the audience field's real job here):** once the `Attendee` doc exists (created by the same hook, same request) and its linked `Order` is resolved, pick the kind by the Shared-decisions discriminator: `paymentStatus ∈ {paid, comped}` → `confirmation-paid`; `paymentStatus === "outstanding"` → `confirmation-payment-due`; `orderId === null` → `confirmation-paid` (documented fallback). Exactly one of the two fires — never both, never neither (barring the definition being disabled, next bullet).
- **`enabled` check applies to the SELECTED kind only** — there is no fallback to the other kind if the selected one is disabled. A paid attendee whose organizer disabled `confirmation-paid` (but left `confirmation-payment-due` on) gets **no** confirmation email, not the wrong one. This mirrors T2 §8-2's contract literally: check `enabled` on the definition about to fire, at fire time.
- **Failure isolation:** per the existing hook's documented contract ("the accept commit stands even if this hook throws — the submission is NEVER un-accepted"), the email-send call must follow the same rule — an email failure (invalid recipient, transport failure) is logged and surfaced as a typed result but **never rolls back or blocks the accept**, and never blocks `attendeeCreated` from flipping true. A failed send lands a `failed` outbox row exactly like any other `sendEventEmail` failure (T1 contract, unchanged) — retryable via the existing per-row Retry button (T2 §5), not by re-running the accept hook.
- **`dedupeKey = attendeeId`** (`attendeeIdFromSubmissionId(org, event, submissionId)` — deterministic, already computed by the hook for the Attendee doc itself). Because accept is terminal and the Attendee create is itself create-if-absent, at most one confirmation email of either kind is ever possible per attendee — re-running the hook for healing purposes (the documented "manual-registration route re-invokes it directly when `attendeeCreated` is still false" path, M5-T1 review S-1) replays onto the same `dedupeKey` and is therefore also safe with zero duplicate risk.

**Acceptance criteria**
1. Accepting a card-paid submission fires exactly one `EmailMessage` (`kind: "confirmation-paid"`, `dedupeKey: attendeeId`); accepting an invoice submission fires exactly one (`kind: "confirmation-payment-due"`, same `dedupeKey` value but different `kind` — no collision, per T1's id derivation including `kind`).
2. Accepting a comped (zero-total) submission fires `confirmation-paid`, not `confirmation-payment-due` (Shared-decisions discriminator, explicitly tested).
3. Disabling `confirmation-paid` and accepting a paid submission produces zero rows of either kind; `confirmation-payment-due` staying enabled does not act as a fallback.
4. Re-invoking `onSubmissionAccepted` for healing (accept hook failure recovery, M5-T1 S-1 path) produces zero additional confirmation rows on replay — asserted with the same fixture the M5-T1 healing test already exercises.
5. A submission with `orderId: null` accepted through any path fires `confirmation-paid` (documented fallback), never crashes on the missing order.
6. An accept-hook throw (simulated transport failure) still leaves `status: "accepted"` + `attendeeCreated: true` intact — the email failure is isolated to a `failed` outbox row, never an un-accept.

## 3 — Periodic trigger: `abandoned-24h` (`abandoned-reminder`)

*As an event organizer, I want a nudge email to go out to everyone who's been sitting on an incomplete registration for a day, without ever nudging the same person twice for the same abandoned attempt.*

- **Source data:** `RegistrationDraft` docs, read via the existing `getAdminRegistrationDraftsForEvent` (`src/lib/db/adminRegistrationDraft.ts`) — already bounded, org-scoped, and already computes the exact `isAbandoned` flag this trigger needs (`ABANDONED_AFTER_MS = 24h`, the single exported constant M3-T5 mandated for exactly this reuse — never re-derive the threshold locally).
- **Eligibility:** every draft where `isAbandoned === true` AND `firstName/lastName/email` denorms are non-empty (a draft abandoned mid-step-1 before any personal fields were entered has no email to send to — `sendEventEmail`'s recipient validation already rejects a blank address as a typed, zero-write `INVALID_RECIPIENT`, so this is a safety net, not a hard precondition to implement separately).
- **Recipient: the draft's FULL, unmasked email** — not the tab's display-masked "@dentsu.com" value. M3-T5's own PII rule explicitly carves this out: "full email is available only via the draft doc to `write:events` holders for legitimate follow-up" — this trigger IS that legitimate follow-up. The masking is a UI-display rule (M5-T3), never a data-access restriction on the server-side sender.
- **`dedupeKey = draftId`.** A draft is a single lifecycle instance — created once, deleted once (either at finalize, per T3 AC-3, or via the manual purge route). One draft → at most one abandoned-reminder email, ever, no matter how many poll ticks observe it still abandoned. If the same person abandons a **second, separate** registration attempt later (a new browser/session per T3 AC-10, hence a new `draftId`), that is correctly a new, distinct nudge-eligible instance.
- **Cadence / acceptable latency:** poll on a cadence such that a draft crossing the 24h mark receives its reminder **within 1 hour** of the mark (i.e., "24h to 25h after last update", not exactly 24h00m00s) — a 15–30 minute poll interval comfortably satisfies this; see §8 for the mechanism.
- **`enabled` check:** re-read `abandoned-reminder`'s current `enabled` at the start of each poll tick (or each processed page within a tick — §6) before querying/enqueuing anything for it.

**Acceptance criteria**
1. A draft that crosses 23h59m does not fire; one crossing 24h01m fires exactly once, within the next poll tick after the boundary (mechanism-dependent exact timing, boundary logic never in question — reuses `isAbandoned` verbatim).
2. Re-evaluating the same still-abandoned draft on every subsequent poll tick produces zero additional rows (`createAdminEmailMessageIfAbsent` collapses on `dedupeKey: draftId`).
3. The email is sent to the draft's real email address; the masked "@dentsu.com" display value never leaks into this send path's inputs (a two-org test with a distinctive local-part asserts the outbox row's `recipient.email` contains it).
4. A draft with an empty `email` denorm (abandoned during step 1, before the email field was entered) produces a typed `INVALID_RECIPIENT` rejection — zero row, zero crash, the poll tick continues to the next candidate.
5. A completed-then-abandoned-again draft (M3-T5 AC-3's "abandon→resume→complete" scenario, then a fresh abandonment under a NEW draft) is treated as an entirely new eligible instance with its own `dedupeKey`.
6. Disabling `abandoned-reminder` mid-poll-cycle stops new sends on the next tick; re-enabling resumes for currently-eligible, not-yet-sent drafts only — no backlog of "missed while disabled" sends is invented or suppressed beyond normal eligibility.

## 4 — Periodic trigger: `unpaid-offsets` (`payment-reminder`, debt chase)

*As an event organizer, I want automatic payment reminders at 7, 14, and 21 days after an invoice-paying registrant is accepted, and I never want a registrant who's since paid to keep getting nudged.*

- **Source data — two-condition eligibility, not one:** the audience is `accepted-invoice`, which per §5 means **both** `Attendee.status === "accepted"` **and** the linked `Order.paymentStatus === "outstanding"`. A raw "all outstanding Orders" query is insufficient — an outstanding order whose submission has not yet been admin-accepted (still `new`/`pending`/`reviewed` in the approval workflow) has no `Attendee` yet and must **not** receive debt-chase emails (it isn't confirmed/registered yet; the org hasn't approved it).
- **Offset base (decision — documented, not invented from nothing):** the `Order` data model has no separate invoice-due-date field — only `createdAt`. The three offsets `[7, 14, 21]` are therefore measured from **`Order.createdAt`** (the moment the invoice order was finalized to `outstanding`). If BE later adds a distinct `dueDate` to `Order` (a genuine product improvement — real invoices usually have a due date separate from issue date), this spec's offsets should be re-pointed at it; until then, `createdAt` is the only available anchor and this is a deliberate, called-out simplification, not an oversight.
- **Three independent dedupe instances per order, one shared kind:** `dedupeKey = orderId + ":" + offsetDays` (i.e., three literal values per order: `"{orderId}:7"`, `"{orderId}:14"`, `"{orderId}:21"`). All three share `kind: "payment-reminder"` (there is only one catalog entry, "Payment reminder 1–3") — the three distinct dedupe keys are what produces three distinct `EmailMessage` rows over the order's life rather than one. **Re-check `Order.paymentStatus === "outstanding"` at the moment of each individual offset firing** — if the order was paid between day 7 and day 14, the day-7 reminder (already sent, dedupeKey fixed) stays sent, but the day-14 and day-21 reminders never fire (the eligibility re-query on that later tick simply no longer includes this order, because the two-condition eligibility check above is re-evaluated fresh every tick, not cached from an earlier "found eligible" snapshot).
- **No auto-repeat past day 21.** The offsets array is fixed system-catalog data in T2/T3 (system definitions cannot edit `trigger.offsetsDays`, only `subject`/`body`/`enabled`/`trigger.at`-for-scheduled per T2 §2's editability table) — there is no fourth automatic nudge; further follow-up beyond day 21 is a manual organizer action outside this engine's scope.
- **Recipient:** the `Attendee`'s denormalized `email` (the same field §2's confirmation email uses) — resolved via the `Attendee` doc already required by the eligibility check, no extra lookup.
- **Cadence / latency:** same 15–30 minute poll target as §3; "fires within roughly 1 hour of crossing the 7/14/21-day mark" is the acceptable-drift bar (ticket's own example).
- **Current-state honesty (documented, not a T3 bug):** there is no route in this codebase that marks an `outstanding` `Order` as paid post-hoc (`adminOrder.ts` has no such transition today). Until one exists, an accepted invoice order that never gets a "mark paid" action will correctly receive exactly the three reminders and then stop — it will not be perpetually re-nudged, but it also will never resolve to `confirmation-paid`-style silence; this is expected under current scope and should not be filed as a QA defect against this ticket.

**Acceptance criteria**
1. An accepted, outstanding order fires the day-7 reminder (and only that one) at the 7-day mark; days 14 and 21 fire on schedule if the order is still outstanding at those marks.
2. An order paid (hypothetically, or via test fixture manipulation) between day 7 and day 14 fires only the day-7 reminder — days 14/21 never fire, verified by re-running the eligibility query with the order's `paymentStatus` flipped.
3. An outstanding order whose submission is still `pending` (not yet accepted, no `Attendee` exists) fires zero reminders at any offset, even past day 21.
4. Re-evaluating an already-fired offset on every subsequent poll tick produces zero additional rows for that specific `orderId:offsetDays` pair.
5. `orderId + ":" + offsetDays` produces three distinct `EmailMessage` docs (three distinct ids, since `dedupeKey` differs) all under the single `kind: "payment-reminder"` — a `write:events` reader on the send-log filtering by `kind: "payment-reminder"` sees all three as separate rows with distinct `dedupeKey`s (visible via row-detail, not a new column).
6. Disabling `payment-reminder` mid-cycle stops all three offsets from firing on the next tick for anyone not yet at that offset; re-enabling resumes normally (same contract as §3 AC-6).

## 5 — Periodic trigger: `scheduled` (fixed calendar moment, one-time or catch-up)

*As an event organizer, I want a scheduled email to fire at its configured moment for everyone currently in its audience — and to keep catching newly-eligible people for a reasonable window afterward, without ever double-sending.*

- **Applies to:** the two system kinds `one-week-to-go`/`qr-ready` (audience fixed at `accepted-all`) **and** any custom definition with `trigger.type === "scheduled"` (audience organizer-selectable across all six values per T2 §2, since custom definitions are not audience-restricted — only trigger-type-restricted).
- **Null `trigger.at` never fires.** A scheduled definition whose datetime is unset ("Not scheduled", T2 §1) is simply skipped by the evaluator — no eligibility query runs for it at all. This is the periodic-engine mirror of T2's display rule, not a new decision.
- **Fire condition:** at a poll tick where `now >= trigger.at` (event-timezone-resolved, exactly as stored — no re-derivation; T2 already materializes `trigger.at` as an absolute UTC instant computed from event-local time at edit time) AND `enabled === true`, query the definition's audience (§6 generic segment queries) and enqueue for every member whose `dedupeKey` (below) has not yet produced a row.
- **Catch-up window (decision):** because audience membership can keep changing after `trigger.at` has passed (someone accepts their registration two days after "one week to go" already fired for everyone else), the evaluator does **not** stop after the nominal moment — every poll tick where `now >= trigger.at` re-queries the audience and sweeps in anyone newly eligible who hasn't been sent yet. **This catch-up stops at the event's first period start** (reusing the existing `firstPeriodDate`/`resolveEventTimeZone` helpers from `src/features/emails/default-definitions.ts` — never forked) — a "have your QR code ready" email arriving after the event has already started is worse than not arriving at all, so the evaluator must not sweep in newly-accepted registrants past that boundary. An event with no periods (so no boundary is computable) has no catch-up cutoff — acceptable, since such an event also can't have a derived scheduled `at` in the first place (T2's own "Not scheduled" fallback already means this case rarely reaches a real `trigger.at`).
- **`dedupeKey = definitionId + ":" + recipientKey`**, where `recipientKey` depends on the resolved audience (§6's segment table gives the canonical id per audience: `attendeeId` for the three `accepted-*` audiences, `submissionId` for `pending-approval`, `draftId` for `abandoned`; `all-invitees` never reaches this — zero recipients, §6). Using `definitionId` (not `kind`) means a custom definition's scheduled blast is keyed independently even though multiple custom definitions could theoretically share... they cannot (kind is unique per event by construction, T2 §2) — `definitionId` is included for clarity and because it is the value already carried on every `EmailMessage` row, not because collision is otherwise possible.

**Acceptance criteria**
1. `one-week-to-go` fires for every currently-`accepted-all` attendee at the tick that first observes `now >= trigger.at`; a second tick later the same hour produces zero additional rows for those same attendees.
2. An attendee accepted two days after `one-week-to-go`'s nominal moment, but before the event start, receives it on the next poll tick after their acceptance (catch-up).
3. An attendee accepted after the event's first period has started never receives `one-week-to-go` or `qr-ready`, even though `now >= trigger.at` remains true and `enabled` remains true (cutoff boundary tested).
4. A custom scheduled definition with audience `all-invitees` fires for zero recipients at its moment (documented no-op, not an error) — evaluator logs/flags this outcome for organizer visibility (§9 gap) rather than silently doing nothing indistinguishable from a bug.
5. A custom scheduled definition with audience `pending-approval` fires for every currently-pending submission at its moment, using `submissionId` as the dedupe recipient key, and separately catches up newly-submitted-but-still-pending people on later ticks up to the same event-start cutoff.
6. Clearing a scheduled definition's `trigger.at` back to null (T2's supported edit) after some recipients already received it does not affect their sent status (immutable outbox snapshot, T1) and simply halts all future firing for that definition (no eligibility query runs while `at` is null).

## 6 — Audience segment definitions (generic, reused by §3–§5)

Exact query/filter definition per stored `EmailDefinitionAudience` value, grounded in the actual data model (`src/types/collection.ts`, `agents/docs/data-models/m2-pricing-commerce.md`, `agents/docs/data-models/m5-attendees-checkin.md`):

| Audience | Definition | Data source | Recipient identity (`dedupeKey` component) |
|---|---|---|---|
| `all-invitees` | **No query — always zero recipients** in the auto-engine (Shared decisions: no Invitee/contact-list entity exists). Reachable only by a hypothetical custom scheduled definition. | n/a | n/a |
| `abandoned` | `RegistrationDraft` docs for the event where derived `isAbandoned === true` (§3's exact source). | `getAdminRegistrationDraftsForEvent` | `draftId` |
| `pending-approval` | `FormData` docs for the event where `status IN ["new", "pending", "reviewed"]` (i.e., submitted, not yet accepted). Served by the existing `FormData eventId+organizationId+status+submittedAt DESC` composite (M3-T4) — an `in` clause over 3 values uses the same composite (Firestore treats `in` as equality-per-value); BE to confirm at implementation, not a new index by default. | `listAdminFormDataForEvent`-family query, status-filtered | `submissionId` (the `FormData` doc id) |
| `accepted-paid` | `Attendee.status === "accepted"` AND linked `Order.paymentStatus ∈ {"paid", "comped"}` (Shared decisions discriminator). | `Attendee` query + `Order` join via `orderId` | `attendeeId` |
| `accepted-invoice` | `Attendee.status === "accepted"` AND linked `Order.paymentStatus === "outstanding"`. | same as above | `attendeeId` |
| `accepted-all` | `Attendee.status === "accepted"`, regardless of payment state. | `Attendee` query only (existing `eventId+organizationId+status+createdAt` composite, M5) — **no `Order` join needed**, cheapest of the five real segments. | `attendeeId` |

- **The `accepted-paid`/`accepted-invoice` join is the one place this spec asks Backend to consider a schema change, as a *performance recommendation, not a mandate*:** `Attendee` does not currently store `paymentStatus` — evaluating these two audiences today means an `Order` read per candidate `Attendee` (N+1) on every poll tick. **Recommended:** denormalize `paymentStatus` (or a coarser `hasBalanceDue: boolean`) onto `Attendee` at accept time (the accept hook already holds the `Order` doc in memory for the on-accept confirmation kind-selection in §2 — zero extra read there) and keep it fresh the one place it can change (a future "mark order paid" transition, if BE ever adds one, per §4's honesty note, would need to also patch the `Attendee` denorm). This is the same "denorm at write time to avoid N+1 at read time" pattern already used throughout M5 (`ticketLabel`, `registrationTypeLabel`) — Backend Agent's call on exact field name/index, not dictated here.
- **Every segment query must be bounded and paginated** (never an unbounded read) — reuse the exact pagination conventions already established for `Attendee`/`FormData`/`RegistrationDraft` admin lists (cursor + `LIMIT`), not a new unbounded scan invented for this ticket. See §8 for how this interacts with batching at volume.

## 7 — Manual "Email all" wiring (M5-T3 abandoned tab)

*As an event organizer, I want to nudge every currently-abandoned registrant right now, without double-emailing anyone the automatic 24h reminder already reached.*

- **Scope (grounded in the shipped code, `src/features/attendees/components/abandoned-tab.tsx`):** the button enables and, on click, sends the **same `abandoned-reminder` definition** (T2's rendered subject/body, current `EmailSettings` sender identity) to every row **currently visible in the tab** — i.e., every draft with `isAbandoned === true` for the event (the tab shows no other rows; there is no additional client-side filter to scope by today). This is a bulk invocation of `sendEventEmailBatch` (`src/lib/email/send-service.ts`, already built as this exact substrate) with one batch entry per visible draft.
- **Shares the SAME dedupe scheme as the automatic trigger (decision — this is the entire safety mechanism, not an extra one):** `dedupeKey = draftId`, identical to §3. Consequences, all free from the existing T1 create-if-absent contract: a draft the 24h automation already emailed is **skipped, not re-sent**, when "Email all" is clicked (the `createAdminEmailMessageIfAbsent` call for that `dedupeKey` returns `created:false`, `sendEventEmailBatch` counts it as a non-`enqueued` duplicate in its `results`, not an error). A draft the automation hasn't reached yet (e.g., `abandoned-reminder` is currently disabled, or the draft crossed 24h moments ago and the next poll tick hasn't run) gets sent for the first time via this manual click — and is thereafter also "already sent" from the automation's perspective (same `dedupeKey`), so the automation will never separately re-send it later. **This means "Email all" is not gated on `abandoned-reminder.enabled`'s automated-firing state** — but it IS still gated on `enabled` itself (§1 obligation, applied uniformly): if the organizer has turned the definition off entirely, "Email all" must also refuse (typed error, same posture as T2 §2 AC-5's test-send refusal on a disabled definition), not silently bypass the toggle they just set.
- **Safety rail against re-clicking / double-click (explicit, from the ticket):** each click submits the CURRENT visible row set as one batch call; a rapid double-click of the button must not double-submit — apply the same short client-side in-flight guard T2 §5 already established for the test-send button, plus the server-side dedupe as the real backstop (a raced double-submission of the identical batch produces the identical set of `dedupeKey`s, so the second call's every entry resolves as a duplicate — zero double sends even if the client guard somehow fails).
- **Result surfacing:** the button's completion state should reflect `sendEventEmailBatch`'s `enqueued` count vs. total visible rows (e.g., "12 sent, 3 already emailed" — some already-sent count is a normal, non-error outcome, not a partial-failure signal) — UI/UX Designer's call on exact copy, not specified further here.

**Acceptance criteria**
1. Clicking "Email all" with N abandoned drafts, none previously emailed, produces exactly N new `EmailMessage` rows (`kind: "abandoned-reminder"`, `dedupeKey: draftId` per row).
2. Clicking it again immediately after (no new abandonments) produces zero new rows — every entry resolves as a duplicate.
3. A draft the automatic 24h sweep already emailed is excluded from "Email all"'s new-row count on first click (pre-seeded fixture: an `abandoned-reminder` row already exists for that `draftId` before the click).
4. Disabling `abandoned-reminder` makes "Email all" refuse with a typed error identical in posture to T2's disabled test-send refusal — no partial send of the visible rows.
5. Double-clicking sends exactly one batch worth of NEW rows (client in-flight guard + server dedupe both verified independently — the server-side test forces two concurrent identical batch calls and asserts N rows total, not 2N).
6. The route enforces `write:events`, 404s cross-org, and is rate-limited (`src/lib/rate-limit.ts`) per the M1–M5 mutating-route convention (§9).

## 8 — Scheduling mechanism (open question for Backend) + rate/volume safety

- **Behavioral requirement (fixed by this spec, not optional):** `abandoned-24h`, `unpaid-offsets`, and `scheduled` all need a **recurring, unattended** evaluation pass — nothing in the current app has a request that runs without a human or the public registration flow triggering it. Target cadence: **every 15–30 minutes**; acceptable drift is **up to ~1 hour** past the nominal 24h/7-14-21-day/scheduled-at mark (per the ticket's own example) — this is a soft precision target the mechanism must be capable of meeting, not a hard SLA this spec enforces with a test.
- **Realistic mechanism options (Backend Agent to choose and document in the implementation's data-model note — not decided here):**
  1. **Cloud Scheduler → HTTP → an internal Next.js API route** (e.g., `POST /api/internal/email-triggers/evaluate`), authenticated by a shared secret header (same posture as `QR_TOKEN_SECRET`/`DRAFT_TOKEN_SECRET` in `apphosting.yaml` — a new secret, fail-closed if unset in production). Pros: zero new deploy artifact, reuses the existing Next.js/DAL/`server-only` module graph exactly as-is, cheapest to reason about. Cons: Cloud Scheduler itself is provisioned outside this repo's existing IaC (a manual `gcloud`/console step, or a new Terraform/script addition) and needs its own operational runbook.
  2. **Firebase Cloud Functions (2nd gen) with `onSchedule`.** Pros: native, well-documented Firebase cron primitive; longer max execution time available (up to the platform's cap) if a single tick needs to process a very large event. Cons: a second deployable unit outside the Next.js app entirely — the trigger-evaluation logic would need to be either duplicated in a Functions codebase or extracted into a shared package importable by both (the `server-only` boundary and `src/lib/db/` conventions were not designed with a second runtime in mind); doubles the deploy/secrets surface.
  3. **Opportunistic evaluation piggybacked on existing authenticated dashboard traffic** (e.g., evaluate a small due-batch whenever an organizer loads the event's Emails or Attendees screen, rate-limited to at most once per N minutes per event via a lightweight lock). Pros: zero new infra. Cons: non-deterministic latency — an event nobody's dashboard visits never fires its debt-chase emails, which defeats the purpose for exactly the events most in need of automated follow-up (organizers who've stopped checking). **Not recommended as the sole mechanism**; at best a supplementary nudge on top of one of the first two.
  - Recommendation (non-binding): option 1 is the pragmatic default given there is no existing Cloud Functions codebase in this repo today and the app is otherwise 100% Next.js/Firestore — but this is explicitly Backend Agent's architecture call to make and document.
- **Rate/volume safety — the 5,000-attendee debt-chase case (behavioral requirement, mechanism-agnostic):** `sendEventEmailBatch` (T1, already built) processes recipients **sequentially**, one full `sendEventEmail` pipeline (Zod parse → render → size-check → sender resolve → create-if-absent transaction → transport call) per entry — it is not parallelized and was not designed to accept an unbounded array. A trigger evaluator must **never** hand it (or an unbounded audience query) all of a large event's eligible recipients in one shot. Requirement: **evaluate and send in bounded pages** (cursor-based, reusing the exact pagination convention every other admin list in this codebase already uses — `Attendee`/`FormData`/`RegistrationDraft` lists all page at 50, `EmailDefinition` at up to 200) — a page's worth of candidates per invocation, with the next page picked up on the next poll tick (or the next chunk within the same tick, if the mechanism's execution-time budget allows more than one page). This is safe to resume/interrupt at any point because every send is independently idempotent (`dedupeKey`) — a chunk that only gets through 200 of 5,000 eligible attendees before a tick ends simply continues on the next tick with zero risk of re-sending the first 200.
- **`enabled` re-check granularity under batching (resolves the tension between T2's "check at fire time" obligation and not wanting a Firestore read per recipient):** re-read the definition's `enabled` flag **at the start of each processed page/chunk**, immediately before that chunk's `sendEventEmailBatch` call — not once per recipient, and not only once at the very start of a multi-page tick. Given the established ~50–200-recipient page sizes, a chunk's wall-clock processing time under the current dev (synchronous, zero-network) transport is small enough that per-chunk staleness risk is negligible; if a real provider (OQ-1, deferred) later makes per-recipient sends slow enough that a single chunk spans many minutes, tightening to a per-recipient re-check is a documented tuning knob for Backend, not a re-spec.
- **Forward-looking, not required now:** the dev outbox transport does zero real network I/O today, so there is no external throughput ceiling to respect yet. A real provider (SES/SendGrid/etc., T1's OQ-1) will have one (e.g., low tens of sends/sec on entry-level tiers) — the paging architecture specified above is deliberately provider-agnostic so a real per-provider rate limiter can be inserted at the transport layer later without touching this trigger-evaluation/dedupe contract at all.

**Acceptance criteria**
1. A fixture event with 5,000 accepted-invoice attendees crossing the 7-day mark simultaneously does not attempt a single unbounded query or a single 5,000-entry `sendEventEmailBatch` call — the evaluator's own tests assert page-bounded reads and calls (exact page size is Backend's implementation choice, but "bounded, not unbounded" is directly testable).
2. Interrupting the evaluator mid-run (simulated: process 2 of N pages, then stop) and resuming on a later invocation produces the correct total count with zero duplicates across the interruption boundary.
3. A definition disabled between chunk 1 and chunk 2 of the same tick stops chunk 2 (and any later chunk) from enqueueing anything for it, while chunk 1's already-enqueued sends stand (T1's "sent is terminal" — no attempt to un-send).
4. No mechanism-specific test is required in this ticket's own suite beyond "the evaluator can be invoked and produces the documented paging/dedupe behavior" — end-to-end verification of the actual Cloud Scheduler/Functions wiring belongs to QA testing the chosen mechanism once Backend picks one, not to this spec's acceptance criteria.

## 9 — Permissions, tenancy, and gap surfaced by this ticket

- The internal evaluation entrypoint (whatever shape §8 lands on) is **not** a normal session-authenticated `write:events` route — it runs unattended, on nobody's session. It MUST still be org/event-scoped internally (every DAL call it makes carries `organizationId`/`eventId` exactly like every other server call in this codebase) and MUST be protected from public invocation by a fail-closed shared secret (the `QR_TOKEN_SECRET`/`DRAFT_TOKEN_SECRET` posture in `apphosting.yaml` — unset in production throws/refuses, never silently runs unauthenticated). This is a new authentication pattern for this codebase (every other server route gates on a human session) and should be reviewed by Security Agent specifically for that reason.
- The "Email all" route (§7) is a normal mutating admin route and follows the unchanged M1–M5 convention exactly: session → org → `getAdminEventForOrganization` → `write:events`, 403/404-IDOR, Zod-validated, rate-limited.
- **Gap surfaced, not fixed here:** a custom scheduled definition targeting `all-invitees` (§5's documented no-op) has no organizer-facing signal today that it will never send anyone anything — T2's editor doesn't warn about this combination, and this ticket's Non-goals explicitly rule out new UI. Recorded as an open question (below) for UX/FS to pick up as a small polish item, not blocking this ticket.

## Non-goals for T3 (explicit)

- **No email designer / block rendering changes** (M6-T4, unchanged).
- **No real delivery, provider, or rate-limit implementation** — the dev outbox transport (T1) is unchanged; §8's rate/volume requirements are paging/architecture requirements for the *evaluator*, not a new transport.
- **No `Order.dueDate` field, no "mark order paid" transition** — both are named as honest gaps in §4, not delivered by this ticket. The unpaid-offsets trigger works correctly against `Order.createdAt` as specified; adding a real due-date concept is a future product decision.
- **No changes to `EmailDefinition`'s stored shape, Zod schemas, or the `EmailMessage`/`EmailDefinition` collections themselves** are *required* by this spec — every dedupeKey/audience formula above is computable from data that already exists. The one item flagged as a *recommendation* (denormalizing `paymentStatus` onto `Attendee`, §5) is explicitly optional/performance-motivated, not a hard requirement of this ticket.
