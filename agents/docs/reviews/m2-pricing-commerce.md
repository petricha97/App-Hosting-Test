## Blockers

### B-1 — M2-T4 payment lifecycle is unimplemented (spec T4 lifecycle step 2, ACs 5/6)
- `src/lib/db/adminOrder.ts:216` — `createAdminOrderWithFinalize` exists, and `src/lib/payments/simulated-payment-provider.ts` exists, but **nothing connects them and nothing calls either** (verified by grep: the only references are their own files and the provider's unit test).
- The spec's lifecycle — card: write order `pending` → `createPayment` → finalize to `paid` on success / mark `failed` on decline (counters untouched); invoice: finalize → `outstanding`; comp (`totalMinor === 0`): finalize → `comped` with **no provider call** — has no implementation anywhere. `createAdminOrderWithFinalize` takes `paymentStatus` as caller input (`adminOrder.ts:193`), and no code path in the repo produces a `pending` or `failed` order at all.
- Consequently spec **T4 AC-5** (comp orders finalize `comped`, no provider call) and **AC-6** (card success → `paid` with `providerPaymentId`; failure → `failed`, counters unchanged; invoice → `outstanding`) are unimplemented and unverifiable, as is the `method → status` column of the normative worked-examples table (AC-2 is only half-implemented: amounts yes, statuses no).
- Fix: ship the orchestration function (e.g. `src/lib/orders/finalize-order.ts` or an adminOrder-level `placeAdminOrder`) that wires provider + transaction per the lifecycle, with tests — or have the Orchestrator explicitly re-scope T4 in the spec. As written, T4's ACs fail.

### B-2 — Finalize transaction has no tests (spec T4 ACs 1, 7, 8, 10, 11; BACKLOG money-math scrutiny)
- `src/lib/db/adminOrder.ts:216-471` is the only place counters (`registeredCount`, `usedCount`) and Order docs are written, and it is **entirely untested**. The spec marks these ACs with explicit "(test: …)" requirements:
  - AC-1 tampered/ignored client amounts, AC-7 double-submit idempotency (one doc, one increment set), AC-8 two racing orders for the last seat, AC-10 snapshot frozen against later fee/tax/promo edits, AC-11 `usedCount` only mutated here.
- The pure fragments (math, availability, order-id) are well tested in `src/__tests__/pricing-math.test.ts`, but the transaction's own logic — idempotent-repeat short-circuit (`adminOrder.ts:271-283`), fee/ticket/regType/promo re-validation order (`:286-368`), recompute-and-compare (`:389-400`), and the write set (`:439-455`) — is unexercised. A fake `runTransaction`/`tx` (the route tests already mock at exactly this module boundary) or the emulator would cover it without ceremony.
- I code-read the transaction and found the structure correct — all reads precede all writes (single `Promise.all` of `tx.get`s at `:260-268`), `tx.create` (not `set`) backstops the create race, org/event tenancy is re-checked on every re-read doc, capacity/cap checks are inside the txn, and error returns commit an empty write set — but for money + counter code, "reviewer read it" is not the bar the BACKLOG sets. Tests are required before this proceeds.

## Should-fix

### S-1 — Spec T2 AC-10 unmet: client repos exist but are never exercised
- AC-10: "client `eventPromotion.ts` exists **and is exercised by at least one test**". `src/lib/db/eventPromotion.ts`, `src/lib/db/fee.ts`, `src/lib/db/tax.ts` have zero callers and zero tests (only the shared `eventPromotionDefaults.ts` is tested via `pricing-math.test.ts`). Add at least a mocked-SDK test for `eventPromotion.ts` (defaults application + org scoping on `getEventPromotionById`); ideally cover the advisory uniqueness helpers in `fee.ts`/`tax.ts` too, since they are currently dead exports.

### S-2 — `firebase-admin/firestore` import + documented double-cast in a route (DAL boundary)
- `src/app/api/dashboard/events/[eventId]/promotions/[promotionId]/settings/route.ts:13` imports `FieldValue, Timestamp` from `firebase-admin/firestore`, and `:35-42` bridges admin→client Timestamp with `as unknown as`. Not blocking because the DAL's own signature forces it (`updateAdminEventPromotion` demands `updatedAt: FieldValue`, `adminEventPromotion.ts:93`) and every sibling promotions route already does the same — but this diff had the chance to fix the pattern instead of extending it. Recommend: have `updateAdminEventPromotion` stamp `updatedAt` itself and accept `validityStartMs/validityEndMs: number | null`, converting to admin `Timestamp` inside `src/lib/db/` — the route's firebase import and the cast both disappear. Flagged for Security's DAL-boundary ledger either way.

### S-3 — `firestore.rules` Organization update is looser than the flow it serves
- `firestore.rules:94-96` lets **any signed-in user** update **any** org's `memberCount` to **any value** (the diff allow-list constrains keys, not values or caller). The join flows only ever increment by 1. Tighten to `request.resource.data.memberCount == resource.data.memberCount + 1` (or ±1 if a leave flow decrements client-side) so a stranger can't zero out or inflate another org's member count. The data-model doc flags the get/list exposure and the User-permissions self-write (both acknowledged, M8-T1), but this value-unconstrained write isn't in its flagged list — Security should adjudicate. Everything else in the rules checks out: default deny, own-doc User scoping, Event create/read gated on active-org `organizationPath` candidates, org-member read + full write denial on `EventPromotion`/`RegistrationType`/`TicketType`/`Fee`/`Tax`, full denial on `Order` and the server-only collections, and `firebase.json` now ships the rules file.

### New code — verified sound

- **Bearer-token auth on join/switch**: `resolveCallerToken` only *extracts*; verification is always `decodeUser` → `adminAuth.verifyIdToken`. The session cookie is itself a verified raw ID token (`api/auth/session/route.ts:15-22`), so one verification path covers both transports; cookie is `sameSite: lax` (CSRF-safe for these POSTs) and the bearer path is CORS-bound. Tests cover 401-no-token, bearer-accepted, expired-token.
- **Pre-auth lookup route**: deliberately unauthenticated — the invite code *is* the entitlement; response is the `OrganizationPreview` allow-list built field-by-field (`org-preview.ts` — never spreads the doc), uniform 404 for unknown/disabled/too-short codes, sub-6-char inputs refused without a Firestore read. Test asserts the exact payload and greps the JSON for `inviteCode`/link-token/ownerId absence.
- **Join route entitlements**: invite code validated server-side against `inviteCodeEnabled`; domain auto-join derives the domain from the **verified token email** (client `organizationId` is only a cross-check that must match), personal domains 403, uniform 404s. Profile fields come from the token (plus an own-profile displayName), never authorization inputs.
- **`addAdminUserToOrganization` idempotency**: roster membership pre-checked inside the transaction → `already-member` short-circuits with **no** memberCount increment; concurrent first-joins collide on `tx.create`/contention and retry into the already-member path. Roster write + permissions re-stamp + counter increment are one atomic transaction (closes the old two-write drift).
- **Tenancy trust boundary**: `resolveActiveOrganizationId` (pure, fail-closed, malformed-roster tolerant) wired into `route-scope.ts`, `get-dashboard-scope.ts`, and the promotions route's local scope; `org-membership.test.ts` locks the Finding-1 attack shape (active org rewritten to a non-member org → null → 403/redirect).
- **Deleted client flows**: zero remaining callers of `signupJoinOrg` / `addExistingUserToOrg` / `createNewUserAndJoinOrg` / `getOrganizationByInviteCode` / `updateOrganizationMemberCount` (grep-verified; only comments reference them). Dialog and signup form now go through `org-join-client.ts`; `AuthContext.switchOrganization` posts to `/api/organizations/switch` so the permissions mirror is re-stamped server-side.
- **firestore.rules**: default deny; User create locked to the exact owner-of-new-org shape (token-matched email/uid, single `created` membership, org `ownerId` back-check, verbatim OWNER_PERMISSIONS list); User update field-diff-locked with roster-constrained `organizationId`; `rosterHas` unrolled with short-circuiting size guards (documented 10-org bound); Organization get roster-only, list constrained to the caller's-own-domain auto-join query; Order and all server-only collections fully denied.

### New findings

- **NEW-1 (Should-fix — Security to adjudicate severity)** `firestore.rules:183-187` — the Organization **create** rule constrains `ownerId`/`memberCount`/`status`/`domainVerified` but not `domain` or `allowDomainAutoJoin`. Any signed-in user can client-create an org claiming `domain: "victimcorp.com", allowDomainAutoJoin: true`; `getAdminOrganizationByDomain` (`adminOrganization.ts:48-62`) and the rules list-allowance would then steer new victimcorp.com signups' auto-join suggestion into the attacker's org (domain squatting / join-phishing — requires victim opt-in, does not breach existing orgs; `limit(1)` also makes duplicate-domain resolution ambiguous). Pre-existing product design (the pre-rules client flow allowed the same), but this rewrite was the natural place to close it. Fix: add `&& (!('domain' in request.resource.data) || request.resource.data.domain == callerEmail().split('@')[1])` to create, and/or gate auto-join lookups on `domainVerified == true` once verification ships.
- **NEW-2 (Should-fix, small)** `firestore.rules:131-143` — the User update allow-list still admits `organizationId`/`organizationRole`, and the comment cites "AuthContext.switchOrganization writes organizationId + organizationRole" — but that client write path was replaced by the switch route in this same diff, and no production caller of client `updateUser`/`createUser` remains (grep-verified). `organizationRole` is value-unconstrained (a member can self-label `owner`; display-only — server authz gates on locked `permissions`). Tighten `hasOnly` to `['name','avatarUrl','updatedAt']` (server switch writes via Admin SDK and bypasses rules) or at minimum constrain `organizationRole` to the roster entry's role, and fix the stale comment.
- **N-6 (Nit)** `agents/docs/data-models/m2-pricing-commerce.md:109` says card "`pending`/`failed` records are route business BEFORE finalize" — `pending` was elided entirely (no writer exists); reword so M3-T3 implementers don't hunt for one.
- **N-7 (Nit)** `place-order.ts:30-33` TODO(M3-T3) covers void-on-finalize-failure; add one sentence that a same-key retry after such a crash **re-quotes**, so with a real provider the replayed charge amount can drift from the new quote — reconciliation, not just voiding, is the M3 contract.
- **N-8 (Nit)** `addAdminUserToOrganization` `already-member` does not re-activate the joined org (only fresh joins switch the active org); the dialog surfaces it as an error, matching old behavior — intentional asymmetry, noting for the record.
